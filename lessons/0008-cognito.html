Cognito: User Authentication for a Financial App

User Pools, JWTs, MFA, and validating tokens in ECS — without calling Cognito on every request

Your architecture has a frontend, a backend, and a database. But right now anyone can call GET /api/trades. You need authentication — a way to know who is making each request and whether they are allowed to. Amazon Cognito is the AWS-managed identity service that handles user registration, login, MFA, and token issuance.

Cognito Has Two Distinct Services

This lesson
User Pools
A managed user directory. Handles sign-up, sign-in, MFA, password reset, and issues JWT tokens. Your app users live here.
Use this for: login, registration, MFA, JWT tokens for your API
Advanced / optional
Identity Pools
Exchanges tokens (from User Pools or social providers) for temporary AWS credentials. Used when your frontend JavaScript needs to call AWS services directly (S3, DynamoDB).
Use this for: frontend code calling AWS directly — not needed when all AWS access goes through your ECS API

For a financial web app where all AWS access goes through the ECS backend, you only need a User Pool. The frontend logs in, gets a JWT, and sends it to the API. The API validates the JWT and handles all AWS calls itself using its IAM Task Role.

Azure analogy: Azure AD B2C Cognito User Pools ≈ Azure AD B2C. Both manage a user directory, issue JWT tokens (ID token + access token), support MFA, social login (Google, Apple), and OAuth2/OIDC flows. The main difference: Cognito is simpler to configure for AWS-native apps but has a less flexible UI customization story than B2C.

The Authentication Flow

Cognito uses standard OAuth2/OIDC. Here is the complete flow from user click to validated API request:

Login → JWT → API call — full flow
1. User clicks "Log In" in the React SPA → SPA redirects to Cognito Hosted UI: https://auth.finapp.com/login?client_id=...&redirect_uri=https://app.finapp.com/callback 2. User enters email + password + MFA code on Cognito's page → Cognito validates credentials → Issues three tokens and redirects to redirect_uri with an auth code → SPA exchanges auth code for tokens (PKCE flow) 3. SPA receives: · ID Token (who the user is: email, name, custom claims) · Access Token (what the user can do: sent to your API) · Refresh Token (exchange for new tokens when access token expires, ~1hr) 4. SPA stores tokens in memory (NOT localStorage — XSS risk) 5. SPA calls: GET https://app.finapp.com/api/trades Header: Authorization: Bearer <access_token> 6. ECS backend receives request → Extracts JWT from Authorization header → Fetches Cognito's JWKS (public keys) — cached, not per-request → Validates: signature ✓ · expiry ✓ · issuer ✓ · audience ✓ → Reads user_id (sub) from token payload → Queries RDS for that user's trades → returns response 7. Token expires after 1 hour → SPA uses Refresh Token to get new Access Token silently

The JWT — Three Parts

A JWT (JSON Web Token) is a base64-encoded string with three dot-separated sections. You never need to call Cognito to validate it — the signature tells you it is genuine.

Part 1
Header
alg: RS256
kid: abc123
(which key signed this)
Part 2
Payload (claims)
sub: user-uuid
email: user@…
exp: 1719999999
iss: cognito URL
aud: your-app-client-id
Part 3
Signature
RSA-signed hash
of header+payload
using Cognito's
private key

Your ECS backend verifies the signature using Cognito's public key, fetched once from the JWKS endpoint and then cached. If the signature is valid and the token is not expired, the user is authenticated — no round-trip to Cognito needed on each request.

# Cognito JWKS endpoint — fetch once at startup, cache in memory
https://cognito-idp.us-east-1.amazonaws.com/{user_pool_id}/.well-known/jwks.json

# Python example (using python-jose or PyJWT)
from jose import jwk, jwt

def validate_token(token: str) -> dict:
    header  = jwt.get_unverified_header(token)
    key     = get_jwk_for_kid(header["kid"])   # from cached JWKS
    payload = jwt.decode(
        token,
        key,
        algorithms=["RS256"],
        audience=COGNITO_APP_CLIENT_ID,
        issuer=f"https://cognito-idp.us-east-1.amazonaws.com/{USER_POOL_ID}"
    )
    return payload  # contains sub (user_id), email, custom claims
Never call Cognito to validate tokens in your hot path If you call cognito.get_user(token) on every API request, you add network latency and create a Cognito availability dependency on every trade. JWT validation is done locally using the public key — no network call required after the initial JWKS fetch.

Frontend Integration

AWS Amplify provides a JavaScript SDK that wraps the Cognito OAuth flow. You do not need to implement PKCE or token exchange yourself.

// Install: npm install aws-amplify

import { Amplify } from 'aws-amplify'
import { signIn, signOut, fetchAuthSession } from 'aws-amplify/auth'

Amplify.configure({
  Auth: {
    Cognito: {
      userPoolId:       'us-east-1_XXXXXXXX',
      userPoolClientId: 'your-app-client-id',
      loginWith: {
        oauth: {
          domain:            'auth.finapp.com',
          scopes:            ['openid', 'email', 'profile'],
          redirectSignIn:    ['https://app.finapp.com/callback'],
          redirectSignOut:   ['https://app.finapp.com/'],
          responseType:      'code'  // PKCE
        }
      }
    }
  }
})

// Get access token for API calls
async function callApi(path) {
  const session     = await fetchAuthSession()
  const accessToken = session.tokens.accessToken.toString()
  return fetch(`/api${path}`, {
    headers: { 'Authorization': `Bearer ${accessToken}` }
  })
}

Backend JWT Validation Middleware

Your ECS API validates the JWT on every request using a middleware/dependency. This runs locally — no Cognito call.

# FastAPI example — reusable auth dependency
from fastapi import Depends, HTTPException, Security
from fastapi.security import HTTPBearer

bearer = HTTPBearer()

def get_current_user(token = Security(bearer)) -> dict:
    try:
        payload = validate_token(token.credentials)
        return {"user_id": payload["sub"], "email": payload["email"]}
    except Exception:
        raise HTTPException(status_code=401, detail="Invalid token")

# Every protected endpoint gets the user injected automatically
@app.get("/api/trades")
def get_trades(user = Depends(get_current_user), db = Depends(get_db)):
    return db.query(Trade).filter(Trade.user_id == user["user_id"]).all()
Finance requirement: scope queries to the authenticated user Every database query for user-specific data — trades, positions, balances — must filter by user_id from the validated JWT. Never trust a user_id from the request body or query parameter. A user manipulating ?user_id=another_user should get their own data, not someone else's.

Where Cognito Sits in the Architecture

User browser
  → Cognito Hosted UI (auth.finapp.com)       # login + MFA
  ← Access token + ID token + Refresh token

SPA stores tokens in memory, sends:
  Authorization: Bearer <access_token>
  → CloudFront → ALB → ECS backend

ECS backend:
  → Validate JWT locally (JWKS cached)        # no Cognito call
  → Extract user_id (sub) from payload
  → Query RDS WHERE user_id = $sub
  ← Return only that user's data
Refresh the JWKS cache periodically Cognito rotates its signing keys occasionally. If you cache JWKS forever, validation will fail after a key rotation. Cache for 24 hours and refresh on a kid miss (when the JWT header references a key ID you don't have cached).

Knowledge Check

Four questions on Cognito.

1. A user's access token expires mid-session. What happens, and how is it handled without the user re-entering their password?

2. Why should you validate the JWT locally in ECS rather than calling cognito.get_user(token) on every API request?

3. A user submits GET /api/trades?user_id=another_user_uuid to try to see another user's trades. Your ECS handler uses get_current_user() from the validated JWT. What should happen?

4. For a financial app, which MFA method should you require in Cognito — and why not the other one?

Lesson takeaway Cognito User Pool = managed user directory that issues JWTs. Your SPA authenticates via the Hosted UI (OAuth2 + PKCE), stores tokens in memory, and sends the access token in the Authorization header. Your ECS backend validates the JWT locally using the cached JWKS public key — no Cognito call per request. Always use TOTP MFA (not SMS). Always query the database using the sub (user_id) from the validated token, never from request parameters.
