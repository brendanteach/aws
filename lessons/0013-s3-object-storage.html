Amazon S3: Object Storage Deep Dive

Beyond frontend hosting — buckets, storage classes, and S3 as your app's file store for uploads, backups, and data

Lesson 6 covered S3 in one narrow role: parking a built SPA behind CloudFront. S3 is much bigger than that — it's the general-purpose object store almost every AWS service quietly stands on, and it's very likely where your app will keep user uploads, generated PDFs, database backups, and log archives.

This lesson treats S3 on its own terms: what an object actually is, how storage classes trade cost for retrieval speed, and the pattern you'll reach for constantly — letting a browser upload a file directly to S3 without routing bytes through your backend.

Azure anchor S3 is Azure's Blob Storage. A bucket ≈ a storage account + container. An object ≈ a blob. A pre-signed URL ≈ a SAS token. If you've ever generated a SAS URL for a browser upload, you already understand the S3 pattern in this lesson — the mechanics map almost one-to-one.

Anatomy of a Bucket

S3 has no real directory tree underneath it. A bucket is a flat namespace of key → object pairs; the console draws slashes in keys as folders purely for your convenience.

ConceptAzure Blob StorageAmazon S3Note
Top-level container Storage account → container Bucket S3 bucket names are globally unique across every AWS account, not just yours.
The file itself Blob Object Max object size: 5 TB. Anything over 100 MB should use multipart upload.
File identifier Blob name Key uploads/u883/photo.jpg — one flat string, slashes and all.
Time-limited access URL SAS token Pre-signed URL Both are a URL with an embedded signature; no IAM credentials ever reach the browser.
Keep every revision Blob versioning S3 Versioning Off by default in both. Turn it on for anything you can't afford to lose to an overwrite.

Storage Classes: Hot to Cold

Every class trades retrieval speed for price — same shape as Azure's Hot / Cool / Archive tiers, just with more steps.

S3 classClosest Azure tierRetrievalUse it for
Standard Hot Milliseconds Actively-served files: SPA assets, live app uploads, thumbnails.
Intelligent-Tiering — (no direct equivalent) Milliseconds Unpredictable access patterns; AWS auto-moves objects between tiers for you.
Standard-IA Cool Milliseconds Backups accessed monthly at most — cheaper storage, small per-GB retrieval fee.
Glacier Instant Retrieval Cold Milliseconds Quarterly-access archives that still need instant reads — old invoices, statements.
Glacier Flexible / Deep Archive Archive Minutes → 12 hrs Compliance retention you hope to never open. Cheapest storage AWS sells.

You rarely pick a class by hand at write time — write a lifecycle rule once and let objects age from hot to cold automatically:

// lifecycle.json — auto-archive backups, then expire
{
  "Rules": [{
    "ID": "archive-old-backups",
    "Status": "Enabled",
    "Filter": { "Prefix": "backups/" },
    "Transitions": [
      { "Days": 30, "StorageClass": "STANDARD_IA" },
      { "Days": 90, "StorageClass": "GLACIER" }
    ],
    "Expiration": { "Days": 365 }
  }]
}
Finance context Regulatory retention (SEC 17a-4, SOX, etc.) often means "keep it, but you'll almost never read it." That's exactly what Glacier Deep Archive is for — pennies per GB per month for records you're legally obligated to hold, not to serve.

Use Case: The Direct-Upload Pattern

User uploads, generated PDFs, exported statements — anything binary your app produces or accepts. The standard pattern is a pre-signed URL: your backend issues a short-lived, scoped URL, and the browser uploads straight to S3. The file's bytes never pass through your server.

Direct upload — browser to S3
↓
Browser — "I want to upload statement.pdf"
↓
Your backend (ECS/Lambda)
Checks auth, decides the S3 key, asks S3 SDK to mint a pre-signed PUT URL (expires in 5 min)
↓
S3 bucket (private)
Browser PUTs the file bytes directly to the signed URL. Bucket policy never grants public access — the signature is the only key.
1
Backend mints the pre-signed URL

The signature encodes bucket, key, method, content-type, and expiry — nothing more.

import { S3Client, PutObjectCommand } from "@aws-sdk/client-s3";
import { getSignedUrl } from "@aws-sdk/s3-request-presigner";

const s3 = new S3Client({ region: "us-east-1" });

async function getUploadUrl(userId, filename, contentType) {
  const key = `uploads/${userId}/${crypto.randomUUID()}-${filename}`;
  const command = new PutObjectCommand({
    Bucket: "my-app-blobs",
    Key: key,
    ContentType: contentType,
  });
  return { url: await getSignedUrl(s3, command, { expiresIn: 300 }), key };
}
2
Browser PUTs directly to that URL 
const { url, key } = await fetch("/api/upload-url", {

3
Allow the browser origin with CORS

Because the browser talks to S3 directly, the bucket needs a CORS rule — the S3 equivalent of the CORS settings on an Azure Storage account.

[
  {
    "AllowedOrigins": ["https://app.finapp.com"],
    "AllowedMethods": ["PUT", "GET"],
    "AllowedHeaders": ["*"],
    "ExposeHeaders": ["ETag"],
    "MaxAgeSeconds": 3000
  }
]

Reading it back later works the same way — a pre-signed GET URL for private files (statements, KYC documents), or a plain CloudFront URL for public assets like avatars.

Production Checklist

  • Block Public Access enabled on every bucket by default — opt in per-bucket only when truly needed (see Lesson 6 for the CloudFront/OAC pattern)
  • Access granted via IAM + bucket policy, never legacy ACLs
  • Pre-signed URL expiry kept short (minutes, not hours) — mint a new one per upload, don't cache them
  • CORS rule scoped to your app's exact origin, not "*", for any bucket accepting browser uploads
  • Versioning on for anything you can't afford to lose to an overwrite or accidental delete
  • Server-side encryption (SSE-S3 or SSE-KMS) enabled — SSE-KMS if compliance requires customer-managed keys
  • Lifecycle rules doing the hot→cold migration, not a cron job you have to remember
  • Object Lock (WORM) considered for anything under regulatory retention

Lesson takeaway S3 is Azure Blob Storage's counterpart: buckets hold objects addressed by flat keys, storage classes trade retrieval speed for price (Standard → IA → Glacier, same shape as Hot → Cool → Archive), and the workhorse pattern for user-facing uploads is a short-lived pre-signed URL — the SAS-token equivalent — that lets the browser talk to S3 directly.
