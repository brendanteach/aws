IAM: Identity and Access in AWS

Roles, policies, and why every AWS API call goes through IAM

IAM (Identity and Access Management) is the most AWS-specific concept you will encounter. In Azure, most service-to-service permissions are handled by connection strings, Managed Identities, and RBAC roles. In AWS, every single API call — from any service, user, or resource — is authorized by IAM. Your ECS container reading from S3, your RDS backup writing to storage, your CloudWatch agent publishing metrics: all IAM.

Getting IAM right is the difference between a secure production system and one with accidental data exposure. This lesson covers the four IAM entities and the one pattern that matters most for your financial app: roles on services.

The Four IAM Entities

IAM User
A permanent identity for a human. Has a username, password for the AWS console, and optional access keys for CLI use.
≈ Azure AD User
IAM Group
A collection of IAM Users. Attach policies to the group; all members inherit them. Simplifies managing permissions for a team.
≈ Azure AD Group
IAM Role
A temporary identity assumed by a service, application, or another AWS account. No username or password — credentials are short-lived and rotated automatically.
≈ Azure Managed Identity
IAM Policy
A JSON document that defines what actions are allowed or denied on which resources. Attached to Users, Groups, or Roles.
≈ Azure RBAC Role Definition

For your financial web app, IAM Roles are what matter most. Your ECS containers, Lambda functions, and other services all operate by assuming roles — never by using hardcoded credentials.

The cardinal rule: never use access keys in application code Hardcoding an AWS Access Key ID + Secret in your ECS container, environment variables, or source code is the single most common AWS security mistake. Keys get leaked in git history, Docker image layers, or log files. Use IAM Roles instead — the AWS SDK picks them up automatically with no code changes.

How IAM Roles Work

A role has two parts:

  • Trust Policy — who is allowed to assume this role (e.g., "ECS tasks in this account")
  • Permission Policy — what the role can do once assumed (e.g., "read from this S3 bucket")
How an ECS container gets AWS credentials
ECS Task starts → ECS service sees the Task Role attached to the task definition → Calls AWS STS (Security Token Service) to assume the role → Gets back temporary credentials (expire in 1 hr, auto-rotated) → AWS SDK in your container automatically uses these credentials → Your code calls s3.get_object() — SDK signs the request with the temp credentials → S3 calls IAM: "is this role allowed to GetObject on this bucket?" → IAM checks the Permission Policy → allows or denies

Your application code never sees credentials. No AWS_ACCESS_KEY_ID in environment variables, no keys in config files. The SDK handles everything.

Azure analogy: Managed Identity This is exactly how Azure Managed Identity works — your App Service or Container Apps instance gets an identity, and the Azure SDK picks up a token automatically. IAM Roles are the AWS equivalent. The key difference: in AWS you write an explicit JSON policy defining exactly which API actions are allowed. Azure RBAC uses predefined role names like "Storage Blob Data Reader". AWS requires you to be more explicit.

Anatomy of an IAM Policy

Every IAM Policy is a JSON document. Here is the policy you would attach to your ECS Task Role for reading trade records from S3:

{
  "Version": "2012-10-17",       // always this value
  "Statement": [
    {
      "Sid":    "ReadTradeRecords",  // optional label
      "Effect": "Allow",
      "Action": [
        "s3:GetObject",
        "s3:ListBucket"
      ],
      "Resource": [
        "arn:aws:s3:::finapp-trade-records",
        "arn:aws:s3:::finapp-trade-records/*"
      ]
    }
  ]
}

Four fields in every statement:

"Effect" "Allow" or "Deny". Default is deny — nothing is permitted unless explicitly allowed. An explicit Deny always overrides an Allow. "Action" The AWS API call(s) to allow. Format: "service:Operation". Use "s3:*" to allow all S3 actions (avoid this in production — too broad). "Resource" The ARN (Amazon Resource Name) of the specific resource. * means all resources of that type — again, avoid in production. "Sid" Optional statement identifier. Use it to document intent — future you will thank present you.

ARNs — How AWS Names Everything

An ARN is the unique identifier for any AWS resource. Format:

arn:aws:s3:::finapp-trade-records
arn:aws:rds:us-east-1:123456789012:db:finapp-postgres
arn:aws:ecs:us-east-1:123456789012:task-definition/finapp-api:3
arn:aws:iam::123456789012:role/finapp-ecs-task-role

You will see ARNs everywhere. The account ID (123456789012) identifies your AWS account. When writing policy "Resource" fields, you are writing ARNs. Note that S3 ARNs have no region or account ID — because S3 bucket names are globally unique.

The Two ECS Roles You Always Need

ECS Fargate uses two distinct roles. Confusing them is one of the most common ECS mistakes:

Role Who uses it What it does Azure equivalent
Task Execution Role The ECS agent (AWS infrastructure) Pulls your Docker image from ECR, writes logs to CloudWatch, fetches secrets from Secrets Manager at startup Like the Azure Container Apps system identity for pulling images
Task Role Your application code inside the container Calls S3, RDS (via IAM auth), Secrets Manager, SES, etc. — whatever your app needs at runtime Like an Azure Managed Identity assigned to your app

Think of it this way: the Execution Role gets your container running. The Task Role is what your container uses once it is running.

IAM Roles for the Financial App — Full Picture
ECS Task Execution Role (used by ECS agent): → ecr:GetDownloadUrlForLayer # pull Docker image → logs:CreateLogStream # write to CloudWatch → secretsmanager:GetSecretValue # inject DB password at startup ECS Task Role (used by your Python/Node API code): → s3:GetObject, s3:PutObject # trade records, statements → secretsmanager:GetSecretValue # fetch Alpaca API key at runtime → ses:SendEmail # trade confirmation emails → cloudwatch:PutMetricData # custom app metrics CloudFront Origin Access Control (used by CloudFront): → s3:GetObject # serve frontend SPA from S3 RDS Monitoring Role (used by RDS): → logs:CreateLogGroup # enhanced monitoring metrics

Principle of Least Privilege

Every policy should grant only the minimum permissions required. This is especially important for financial applications where data exposure or unauthorized trading operations carry real consequences.

In practice:

Instead ofUseWhy
"Action": "s3:*" "Action": ["s3:GetObject", "s3:PutObject"] A compromised container can read but cannot delete trade history
"Resource": "*" "Resource": "arn:aws:s3:::finapp-prod/*" Scope to exactly the bucket your app needs, not all S3 in the account
One role for everything Separate Task Role per service Your market-data service doesn't need permission to write user statements
IAM User with access keys in code IAM Role on the ECS task Roles use short-lived credentials; a leaked key is a permanent breach
Finance requirement: Condition keys for extra control IAM policies support "Condition" blocks. For a financial app, useful examples:

• Require MFA for humans accessing production AWS console
• Restrict S3 access to encrypted-in-transit only (aws:SecureTransport: true)
• Lock Secrets Manager access to the ECS task's specific VPC (aws:SourceVpc)

These are advanced — but they exist, and they matter for compliance.

Azure → AWS IAM Map

ConceptAzureAWSKey difference
Human identity Azure AD User IAM User AWS IAM Users are account-local; not a full directory service like Azure AD
Service identity Managed Identity IAM Role Nearly identical concept; both provide auto-rotated temp credentials
Permission definition RBAC Role Definition IAM Policy (JSON) AWS requires you to write JSON; Azure has named built-in roles you can assign directly
Permission assignment Role Assignment Attach policy to role Same idea; AWS calls it "attaching" a policy
Cross-service trust Managed Identity binding Trust Policy on Role AWS makes the trust relationship explicit in JSON; Azure manages this implicitly
Resource identifier Resource ID ARN Similar concept; ARNs include service, region, account, and resource name
Default access Some implicit access within subscriptions Deny everything by default AWS denies every API call unless there is an explicit Allow. Nothing is inherited.

Knowledge Check

Four questions on IAM.

1. Your ECS Fargate container needs to read trade records from an S3 bucket. What is the correct way to grant it access?

2. Your ECS task fails to start — logs show it cannot pull the Docker image from ECR. Which IAM role is missing a permission?

3. An IAM policy has both an Allow statement for s3:DeleteObject and a Deny statement for s3:DeleteObject on the same resource. What happens when the role tries to delete an object?

4. Applying least privilege, which policy is correct for an ECS service that only needs to write user trade confirmations to one specific S3 bucket?

Lesson takeaway IAM Roles replace credentials for every service in AWS. Your ECS containers get a Task Role (what your code can do) and a Task Execution Role (how ECS starts the container). Policies are JSON with Effect / Action / Resource. Default is deny-all. Explicit Deny always wins. For finance: scope every policy to the exact actions and exact ARNs needed — nothing broader.
