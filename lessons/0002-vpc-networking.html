VPC: The Network Foundation of Your Financial App

Subnets, Availability Zones, gateways, and security groups — from scratch

Every AWS resource you deploy lives inside a VPC (Virtual Private Cloud). It is the network boundary that separates your app from the internet and from other AWS customers. If you get VPC wrong, your database is exposed or your containers can't reach the internet. Get it right once, and everything else sits safely inside it.

This is the single most important foundational concept in AWS. Azure has VNets — VPC is the same idea, but with a few structural differences that matter.

The Six Building Blocks

1. VPC

A VPC is a logically isolated network inside AWS. You define a CIDR block — e.g. 10.0.0.0/16 — which gives you 65,536 IP addresses to assign to subnets and resources. One VPC spans one AWS Region.

Azure analogy: Azure VNet Nearly identical concept. One key difference: AWS VPCs have no internet access by default. An Azure VNet has outbound internet by default. In AWS you must explicitly attach an Internet Gateway — nothing gets in or out until you do.

2. Subnets

A subnet is a slice of your VPC CIDR assigned to one specific Availability Zone. A subnet with a route to an Internet Gateway is public. A subnet without that route is private. That's the entire definition — it's about the route table, not a setting on the subnet itself.

The three-tier pattern for a financial app:

TierWhat lives hereCan reach internet?
PublicALB, NAT GatewayYes — bidirectional via Internet Gateway
PrivateECS containers (your API)Outbound only — via NAT Gateway
DBRDS, ElastiCacheNo internet access at all

3. Internet Gateway (IGW)

The IGW is what makes a VPC reachable from the internet. You attach one per VPC. Public subnets have a route 0.0.0.0/0 → IGW in their route table. Without that route, the subnet is private.

4. NAT Gateway

Private subnet resources (like your ECS containers) often need to make outbound calls — pulling Docker images from ECR, calling the Alpaca API, fetching market data. But they must not be reachable from the internet inbound.

The NAT Gateway solves this: it sits in a public subnet and translates private IPs to its own public IP for outbound calls. Private subnets route 0.0.0.0/0 → NAT Gateway. The internet can never initiate a connection back.

Cost note NAT Gateways cost ~$0.045/hr + $0.045/GB of data processed. For high-throughput financial apps pulling large market data sets, this adds up. VPC Endpoints for S3 and Secrets Manager bypass the NAT Gateway entirely — free traffic on the AWS backbone.

5. Security Groups

A Security Group is a stateful firewall attached to a resource (an ECS task, an RDS instance, an ALB). It has inbound and outbound rules. Stateful means if you allow inbound port 443, the return traffic is automatically allowed — you don't need an outbound rule for it.

The security group chain for your financial app:

Security Group Rules
[Internet] → ALB Security Group: allow inbound 443 from 0.0.0.0/0 → ECS Security Group: allow inbound 8080 from ALB Security Group only → RDS Security Group: allow inbound 5432 from ECS Security Group only → Redis Security Group: allow inbound 6379 from ECS Security Group only

You reference security groups by ID in rules, not by IP. So "allow from ECS Security Group" means any resource that has that SG attached. This is more flexible and maintainable than CIDR-based rules.

Azure analogy: NSG (Network Security Group) Security Groups work like Azure NSGs attached per-resource (NIC level), not per-subnet. One major difference: AWS Security Groups are deny-by-default with no explicit deny rules — you only add allow rules. Azure NSGs have an explicit deny rule at the bottom, but the model is similar.

6. VPC Endpoints

A VPC Endpoint lets resources in private subnets reach specific AWS services (S3, Secrets Manager, ECR) privately — without going through the NAT Gateway or the public internet. Traffic stays on the AWS internal network.

For a financial app, two endpoints are non-negotiable:

EndpointWhy you need it
com.amazonaws.us-east-1.s3 ECS containers reading/writing to S3 (audit logs, statements) without NAT costs
com.amazonaws.us-east-1.secretsmanager ECS containers fetching DB passwords at startup — must not traverse public internet
Azure analogy: Private Endpoint / Service Endpoint Azure has both Service Endpoints (similar to VPC Gateway Endpoints for S3) and Private Endpoints (similar to VPC Interface Endpoints for Secrets Manager). The AWS terminology differs but the concept — keeping traffic off the public internet — is identical.

How Traffic Actually Flows

Two flows matter most. Trace through the diagram above as you read each one.

Flow 1 — User's browser → Your API
User browser → DNS (Route 53) resolves api.yourapp.com → CloudFront (TLS termination, WAF) → ALB in public subnet (HTTPS → HTTP internally) → ECS Fargate task in private subnet (port 8080) → RDS in DB subnet (port 5432) ← Response travels back the same path
Flow 2 — ECS container calls Alpaca API (external)
ECS Fargate task (private subnet, 10.0.3.x) → Route table: 0.0.0.0/0 → NAT Gateway (in public subnet) → NAT Gateway translates to its public IP → Internet Gateway → Alpaca API at api.alpaca.markets ← Response comes back to NAT Gateway → ECS task (Alpaca API never sees your private IP — only the NAT Gateway's public IP)

Finance requirement: No DB subnet ever routes to the internet RDS and ElastiCache subnets must have no route to the Internet Gateway and no route to the NAT Gateway. Their only routes are local VPC traffic. Database engines should only be reachable from the ECS security group on the specific port — nothing else. This is the baseline for any financial or PCI-DSS-adjacent deployment.

The Minimum VPC Checklist

Before deploying anything to production, verify:

#CheckWhy
1At least 2 AZs used (public + private subnets in each)Single-AZ = single point of failure; unacceptable for finance
2RDS and ElastiCache in DB subnets with no internet routeData stores must never be internet-reachable
3Security group chain references SG IDs, not CIDRsIP-based rules break when containers scale; SG-to-SG rules scale automatically
4VPC Endpoint for S3 and Secrets Manager createdAvoids NAT costs and keeps sensitive traffic off the internet
5NAT Gateway in each AZ (one per AZ if you need cross-AZ HA)A NAT Gateway is AZ-specific; if that AZ fails, the other AZ's private subnet has no outbound

Lesson takeaway VPC = your private network. Subnets = tiers (public → ALB, private → ECS, DB → RDS). Internet Gateway = inbound/outbound for public subnets. NAT Gateway = outbound-only for private subnets. Security Groups = stateful firewalls chained by SG ID, not IP. VPC Endpoints = keep AWS service traffic off the internet. With this layout, your financial app data never touches the public internet between your backend and your database.
