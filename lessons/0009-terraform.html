Lesson 09 · Infrastructure as Code

Terraform: Infrastructure as Code for AWS

Declaring your entire architecture in code — VPC to CloudFront, reproducible and reviewable

Every service in Lessons 1–8 was described in words and diagrams. Terraform lets you describe it in code — files that you run to create, update, or destroy AWS infrastructure. The same code creates your staging environment and your production environment. Changes go through pull request review. Infrastructure is never a mystery again.

The Five Core Concepts

provider
Provider
The plugin that knows how to talk to AWS. You declare which provider to use and which region. Terraform downloads it on init.
resource
Resource
A single AWS object — one S3 bucket, one RDS instance, one security group. The main unit of Terraform.
variable
Variable
An input parameter. Different values for prod vs staging (db instance size, replica count). Never hardcode environment-specific values.
output
Output
A value Terraform exposes after apply — e.g. the RDS endpoint, the ALB DNS name. Used by other modules or CI/CD pipelines.
state
State — the most important concept
Terraform tracks what it has created in a state file (terraform.tfstate). This is the source of truth for what exists. It must live in a shared, remote location (S3) — never on a developer's laptop. Protect it like a secret: it contains resource IDs and may contain sensitive values.

The Workflow

init
Download providers, configure S3 backend for remote state
plan
Show what will be created, changed, or destroyed — without doing it
apply
Execute the plan — creates or updates real AWS resources
destroy
Tear down everything Terraform created (use carefully)

The golden rule: always run plan before apply. Read the plan output carefully — a -/+ next to a resource means it will be destroyed and recreated (destructive). A ~ means in-place update (safe). Never apply without reviewing the plan.

Remote State — Non-Negotiable for Teams

If state lives on your laptop, nobody else can run Terraform safely. Configure an S3 backend with a DynamoDB lock table — this is the AWS standard.

backend.tf
terraform {
  backend "s3" {
    bucket         = "finapp-terraform-state"   # versioning enabled
    key            = "prod/terraform.tfstate"
    region         = "us-east-1"
    encrypt        = true                       # state encrypted at rest
    dynamodb_table = "finapp-terraform-locks"   # prevents concurrent runs
  }

  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.0"
    }
  }
}
Create the S3 bucket and DynamoDB table manually once Terraform cannot create its own backend with Terraform (chicken-and-egg). Create the state bucket and lock table once via the AWS console or AWS CLI, then configure the backend block above. Enable S3 versioning on the state bucket — it lets you recover from accidental state corruption.

Module Structure for the Financial App

Organize Terraform into modules — one per architectural layer. Each module can be applied independently and reused across environments.

infrastructure/ ├── backend.tf # S3 remote state config ├── providers.tf # AWS provider + region ├── variables.tf # top-level inputs (env, region, app_name) ├── outputs.tf # top-level outputs │ ├── modules/ │ ├── vpc/ # VPC, subnets, IGW, NAT, route tables, SGs, VPC endpoints │ ├── iam/ # ECS task role, execution role, policies │ ├── ecr/ # container registry │ ├── rds/ # RDS PostgreSQL, subnet group, parameter group, proxy │ ├── elasticache/ # Redis cluster │ ├── ecs/ # cluster, task definition, service, ALB, target group │ ├── cognito/ # user pool, app client, hosted UI domain │ ├── frontend/ # S3 bucket, CloudFront, OAC, ACM cert, Route 53 │ └── secrets/ # Secrets Manager secrets (values set separately) │ └── envs/ ├── prod/ # prod variable values └── staging/ # staging variable values (smaller instances)

Real Terraform — Key Resources

Provider and variables

providers.tf
provider "aws" {
  region = var.aws_region
  default_tags {
    tags = {
      Project     = "finapp"
      Environment = var.environment
      ManagedBy   = "terraform"
    }
  }
}

# Second provider — us-east-1 for ACM cert (CloudFront requirement)
provider "aws" {
  alias  = "us_east_1"
  region = "us-east-1"
}
variables.tf
variable "environment"  { type = string }   # "prod" or "staging"
variable "aws_region"   { type = string; default = "us-east-1" }
variable "db_instance"  { type = string }   # "db.t3.medium" (prod) / "db.t3.micro" (staging)
variable "ecs_cpu"      { type = number }   # 512 (prod) / 256 (staging)
variable "ecs_memory"   { type = number }   # 1024 (prod) / 512 (staging)
variable "domain_name"  { type = string }   # "finapp.com"

VPC module

resource "aws_vpc" "main" {
  cidr_block           = "10.0.0.0/16"
  enable_dns_hostnames = true
  enable_dns_support   = true
}

resource "aws_subnet" "public" {
  for_each          = { "1a" = "10.0.1.0/24", "1b" = "10.0.2.0/24" }
  vpc_id            = aws_vpc.main.id
  cidr_block        = each.value
  availability_zone = "us-east-1${each.key}"
}

resource "aws_internet_gateway" "main" {
  vpc_id = aws_vpc.main.id
}

resource "aws_security_group" "ecs" {
  name   = "finapp-ecs-${var.environment}"
  vpc_id = aws_vpc.main.id

  ingress {
    from_port       = 8080
    to_port         = 8080
    protocol        = "tcp"
    security_groups = [aws_security_group.alb.id]  # SG ID, not CIDR
  }

  egress {
    from_port   = 0; to_port = 0; protocol = "-1"
    cidr_blocks = ["0.0.0.0/0"]
  }
}

Frontend module — ACM in us-east-1

modules/frontend/main.tf  (excerpt)
# ACM cert MUST use the us_east_1 provider alias
resource "aws_acm_certificate" "main" {
  provider          = aws.us_east_1    # the alias from providers.tf
  domain_name       = "*.${var.domain_name}"
  validation_method = "DNS"
}

resource "aws_s3_bucket" "frontend" {
  bucket = "finapp-frontend-${var.environment}"
}

resource "aws_s3_bucket_public_access_block" "frontend" {
  bucket                  = aws_s3_bucket.frontend.id
  block_public_acls       = true
  block_public_policy     = true
  ignore_public_acls      = true
  restrict_public_buckets = true
}

resource "aws_cloudfront_distribution" "main" {
  enabled             = true
  default_root_object = "index.html"
  aliases             = ["app.${var.domain_name}"]

  # Origin 1: S3 for frontend
  origin {
    domain_name              = aws_s3_bucket.frontend.bucket_regional_domain_name
    origin_id                = "s3-frontend"
    origin_access_control_id = aws_cloudfront_origin_access_control.main.id
  }

  # Origin 2: ALB for API
  origin {
    domain_name = aws_lb.main.dns_name
    origin_id   = "alb-api"
    custom_origin_config {
      http_port              = 80
      https_port             = 443
      origin_protocol_policy = "https-only"
      origin_ssl_protocols   = ["TLSv1.2"]
    }
  }

  # Route /api/* to ALB
  ordered_cache_behavior {
    path_pattern     = "/api/*"
    target_origin_id = "alb-api"
    allowed_methods  = ["DELETE", "GET", "HEAD", "OPTIONS", "PATCH", "POST", "PUT"]
    forwarded_values { query_string = true; headers = ["Authorization"]
      cookies { forward = "none" } }
    viewer_protocol_policy = "redirect-to-https"
  }

  # SPA 404 fix
  custom_error_response {
    error_code         = 403
    response_code      = 200
    response_page_path = "/index.html"
  }

  viewer_certificate {
    acm_certificate_arn      = aws_acm_certificate.main.arn
    ssl_support_method       = "sni-only"
    minimum_protocol_version = "TLSv1.2_2021"
  }
}

Plan Output — Reading It

# terraform plan output — learn to read this before every apply

  # aws_db_instance.postgres will be created
  + resource "aws_db_instance" "postgres" {
      + identifier        = "finapp-prod"
      + multi_az          = true
      + storage_encrypted = true
      ...
    }

  # aws_ecs_service.api will be updated in-place
  ~ resource "aws_ecs_service" "api" {
      ~ task_definition = "finapp-api:11" -> "finapp-api:12"
    }

  # aws_db_parameter_group.postgres must be replaced
  -/+ resource "aws_db_parameter_group" "postgres" {  # forces replacement!
      ...
    }

+  = create    ~  = update in-place    -/+  = destroy + recreate (CAUTION)
-/+ means destruction — pause and think Some AWS resources cannot be updated in-place. Changing a DB parameter group family, for example, forces RDS to destroy and recreate the parameter group (though not the database itself). Always read -/+ lines carefully and understand what is being destroyed before running apply.

Azure → Terraform Map

ConceptAzure IaCTerraformDifference
IaC language Bicep / ARM JSON HCL (HashiCorp Config Language) HCL is more readable than ARM JSON. Bicep is closer to HCL in ergonomics. Terraform works with 3000+ providers (AWS, Azure, GCP, GitHub, Datadog…).
State Azure manages state (template deployments) Explicit state file (S3 + DynamoDB) Azure ARM/Bicep is stateless — Azure itself tracks what was deployed. Terraform uses an explicit state file you manage. More control, more responsibility.
Modules Bicep modules Terraform modules Same concept — reusable, parameterized building blocks. Terraform Registry has thousands of community modules.
Preview changes az deployment what-if terraform plan Both show a diff of what will change. Terraform's output is generally more readable.
Apply changes az deployment create terraform apply Equivalent. Terraform requires explicit approval unless you pass -auto-approve (avoid in prod).
Drift detection Limited (what-if shows some drift) terraform plan always shows drift If someone manually changes a resource in the console, terraform plan shows it as a diff and apply reverts it — enforcing IaC as the single source of truth.

Knowledge Check

Four questions on Terraform.

1. A colleague manually changes the RDS instance class from db.t3.medium to db.r6g.large in the AWS console. What happens the next time someone runs terraform plan?

2. Why must the S3 remote state bucket be created manually before running terraform init?

3. Your terraform plan shows -/+ next to aws_db_parameter_group.postgres. What does this mean?

4. You need to provision the ACM TLS certificate for CloudFront, but your app region is us-west-2. How do you handle this in Terraform?

Lesson takeaway Terraform = declare resources in HCL → plan to see changes → apply to execute. Store state in S3 + DynamoDB (create these manually once). Organize into modules per layer (vpc, iam, rds, ecs, frontend). Use provider aliases for resources that must live in a specific region (ACM cert → us-east-1). The -/+ symbol in plan output means destruction — read carefully before applying. Manual console changes are overwritten on next apply — treat IaC as the only source of truth.
