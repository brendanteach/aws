Lesson 12 · Deployment

CI/CD with GitHub Actions

Automated test → build → deploy pipeline from git push to production

Right now, deploying your financial app means manually building Docker images, pushing to ECR, updating task definitions, syncing S3, and invalidating CloudFront. That is ten steps and one missed step away from a broken production deployment. GitHub Actions automates the entire pipeline: every push to main runs tests, builds, and deploys — reliably, repeatably, with a full audit log of every deployment.

OIDC Authentication — No Stored AWS Keys

The most important security decision in your CI/CD pipeline: never store AWS access keys in GitHub Secrets. Keys are long-lived credentials that can be leaked in logs, exported by a compromised action, or forgotten and never rotated.

Instead, use OIDC (OpenID Connect): GitHub Actions proves its identity to AWS using a short-lived token. AWS trusts GitHub's OIDC provider and issues temporary credentials for the duration of the job only.

Terraform — OIDC trust relationship
resource "aws_iam_openid_connect_provider" "github" {
  url             = "https://token.actions.githubusercontent.com"
  client_id_list  = ["sts.amazonaws.com"]
  thumbprint_list = ["6938fd4d98bab03faadb97b34396831e3780aea1"]
}

resource "aws_iam_role" "github_actions" {
  name = "finapp-github-actions"
  assume_role_policy = jsonencode({
    Version = "2012-10-17"
    Statement = [{
      Effect    = "Allow"
      Principal = { Federated = aws_iam_openid_connect_provider.github.arn }
      Action    = "sts:AssumeRoleWithWebIdentity"
      Condition = {
        StringLike = {
          # Only YOUR repo on YOUR branch can assume this role
          "token.actions.githubusercontent.com:sub":
            "repo:your-org/finapp:ref:refs/heads/main"
        }
      }
    }]
  })
}

# Attach least-privilege policy: ECR push + ECS deploy + S3 sync + CF invalidate
The Condition is critical — lock it to your repo and branch Without the StringLike condition, any GitHub Actions workflow on any public repo could assume your AWS role. Lock it to repo:your-org/finapp:ref:refs/heads/main — only your repo's main branch can authenticate. For PRs, add a separate condition for pull_request events if you need plan previews.

The Complete Workflow File

.github/workflows/deploy.yml
name: Deploy to Production

on:
  push:
    branches: [main]

env:
  AWS_REGION:       us-east-1
  ECR_REPOSITORY:   finapp-api
  ECS_CLUSTER:      finapp-prod
  ECS_SERVICE:      finapp-api
  CF_DISTRIBUTION:  EDFDVBD6EXAMPLE
  S3_BUCKET:        finapp-frontend-prod

jobs:

  ## ── 1. TEST ──────────────────────────────────────────
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Run backend tests
        run: |
          pip install -r requirements.txt
          pytest tests/ -v --tb=short

      - name: Run frontend checks
        run: |
          cd frontend && npm ci
          npm run type-check
          npm run lint

  ## ── 2. DEPLOY BACKEND ───────────────────────────────
  deploy-backend:
    needs: test        # only runs if tests pass
    runs-on: ubuntu-latest
    permissions:
      id-token: write   # required for OIDC
      contents: read

    steps:
      - uses: actions/checkout@v4

      - name: Configure AWS credentials (OIDC — no stored keys)
        uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::123456789012:role/finapp-github-actions
          aws-region: ${{ env.AWS_REGION }}

      - name: Login to ECR
        id: login-ecr
        uses: aws-actions/amazon-ecr-login@v2

      - name: Build, tag, push Docker image
        env:
          REGISTRY: ${{ steps.login-ecr.outputs.registry }}
          IMAGE_TAG: ${{ github.sha }}
        run: |
          docker build -t $REGISTRY/$ECR_REPOSITORY:$IMAGE_TAG .
          docker tag  $REGISTRY/$ECR_REPOSITORY:$IMAGE_TAG \
                      $REGISTRY/$ECR_REPOSITORY:latest
          docker push $REGISTRY/$ECR_REPOSITORY:$IMAGE_TAG
          docker push $REGISTRY/$ECR_REPOSITORY:latest

      - name: Update ECS task definition with new image
        id: task-def
        uses: aws-actions/amazon-ecs-render-task-definition@v1
        with:
          task-definition: task-definition.json   # checked into repo
          container-name:  api
          image: ${{ steps.login-ecr.outputs.registry }}/${{ env.ECR_REPOSITORY }}:${{ github.sha }}

      - name: Deploy to ECS (rolling update, waits for stable)
        uses: aws-actions/amazon-ecs-deploy-task-definition@v1
        with:
          task-definition: ${{ steps.task-def.outputs.task-definition }}
          service:         ${{ env.ECS_SERVICE }}
          cluster:         ${{ env.ECS_CLUSTER }}
          wait-for-service-stability: true   # fails if ECS can't stabilize

  ## ── 3. DEPLOY FRONTEND ──────────────────────────────
  deploy-frontend:
    needs: test        # parallel with deploy-backend
    runs-on: ubuntu-latest
    permissions:
      id-token: write
      contents: read

    steps:
      - uses: actions/checkout@v4

      - name: Configure AWS credentials (OIDC)
        uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::123456789012:role/finapp-github-actions
          aws-region: ${{ env.AWS_REGION }}

      - name: Build React SPA
        run: |
          cd frontend && npm ci && npm run build

      - name: Sync to S3 (changed files only)
        run: |
          aws s3 sync frontend/dist/ s3://$S3_BUCKET/ \
            --delete \
            --cache-control "max-age=31536000" \
            --exclude "index.html"

          # index.html gets short cache — must be fresh
          aws s3 cp frontend/dist/index.html s3://$S3_BUCKET/index.html \
            --cache-control "max-age=300, must-revalidate"

      - name: Invalidate CloudFront cache (index.html only)
        run: |
          aws cloudfront create-invalidation \
            --distribution-id $CF_DISTRIBUTION \
            --paths "/index.html"

Production Protection — Manual Approval Gate

For a financial app you may want a human to approve the production deployment after staging passes. GitHub Environments provide this.

GitHub UI: Settings → Environments → prod
Required reviewers: [your-username, senior-engineer]
Wait timer: 0 min (or set 5 min to allow cancellation)

# In the workflow, reference the environment:
deploy-backend:
  environment: prod    # ← this triggers the approval gate
  needs: test
Finance requirement: deployment audit trail Every GitHub Actions run is logged with: who triggered it, which commit SHA, which branch, what steps ran, and whether it succeeded. This is your deployment audit trail — a requirement for SOC 2 and most financial compliance frameworks. GitHub's run history satisfies this without any additional tooling.

IAM Policy for the GitHub Actions Role

Least privilege — the GitHub Actions role only gets the permissions it needs to deploy, nothing else:

GitHub Actions Role permissions (minimum):

ECR:
  ecr:GetAuthorizationToken
  ecr:BatchCheckLayerAvailability
  ecr:GetDownloadUrlForLayer
  ecr:PutImage
  ecr:InitiateLayerUpload
  ecr:UploadLayerPart
  ecr:CompleteLayerUpload
  Resource: arn:aws:ecr:us-east-1:123456789012:repository/finapp-api

ECS:
  ecs:DescribeTaskDefinition
  ecs:RegisterTaskDefinition
  ecs:UpdateService
  ecs:DescribeServices
  iam:PassRole          (to pass task/execution roles to new task def revision)
  Resource: specific cluster and service ARNs

S3:
  s3:PutObject
  s3:DeleteObject
  s3:ListBucket
  Resource: arn:aws:s3:::finapp-frontend-prod/*

CloudFront:
  cloudfront:CreateInvalidation
  Resource: arn:aws:cloudfront::123456789012:distribution/EDFDVBD6EXAMPLE
iam:PassRole requires careful scoping ECS needs iam:PassRole to attach task and execution roles to the new task definition. Scope this to the specific role ARNs only — iam:PassRole on * is equivalent to privilege escalation because it lets you pass any role in the account.

Azure → AWS CI/CD Map

ConceptAzure DevOps / GitHubGitHub Actions + AWSDifference

AuthenticationAzure service connection (client secret or federated)OIDC with aws-actions/configure-aws-credentialsBoth support OIDC federated identity — no stored secrets. AWS calls it "role with web identity"; Azure calls it "federated credential".
Container registryAzure Container RegistryECR via amazon-ecr-login actionamazon-ecr-login handles docker login using the OIDC-acquired credentials automatically.
Container deployAzure Container Apps update / AKS applyamazon-ecs-deploy-task-definition actionThe ECS action registers a new task definition revision and updates the service — equivalent to a rolling deploy.

Approval gatesAzure DevOps release gates / GitHub EnvironmentsGitHub Environments (required reviewers)Identical if already on GitHub. Azure DevOps has more complex gate policies (query Azure Monitor, call REST APIs).
SecretsAzure Key Vault + GitHub SecretsGitHub Secrets (non-AWS secrets only — use OIDC for AWS)Store non-AWS secrets (Slack webhook, PagerDuty key) in GitHub Secrets. Never store AWS credentials there — use OIDC.

Knowledge Check

1. Why should you never store AWS Access Key ID and Secret Access Key in GitHub Secrets for CI/CD?

2. The deploy-backend and deploy-frontend jobs both have needs: test. What does this mean for execution order?

3. After deploying new frontend assets to S3, you run aws cloudfront create-invalidation --paths "/index.html". Why only /index.html and not "/*"?

4. The ECS deploy step has wait-for-service-stability: true. Your new container has a bug and crashes on startup. What happens to the pipeline?

Lesson takeaway CI/CD pipeline: test → [deploy-backend ∥ deploy-frontend] in parallel. Use OIDC (not stored access keys) — the GitHub Actions role assumes a specific IAM role via aws-actions/configure-aws-credentials. Lock the OIDC trust condition to your exact repo and branch. Tag Docker images with git SHA (not latest) for traceability. Set wait-for-service-stability: true so a crashing container fails the pipeline visibly. Sync S3 with per-file cache headers, invalidate only /index.html. Use GitHub Environments for a prod approval gate.
