Lambda: Architecture, Local Debugging & Multi-Environment Deploys

What actually runs when a Lambda fires, how to step through it on your laptop without touching AWS, and how the same function ships to QA, UAT, and prod

Lesson 10 covered the SQS → Lambda pattern for async jobs, and Lesson 16 used Lambda as a Bedrock agent tool. This lesson steps back to Lambda itself: the execution model, how to run and debug it entirely offline, and how to organize many functions across QA / UAT / prod without hand-editing config in each place.

Language note Examples here use Node.js/TypeScript for both the Lambda handler and the CDK stack that deploys it, matching Lesson 18's TypeScript examples. Everything — the execution model, the testing ladder, the multi-environment pattern — applies identically to a Python handler (as used in Lessons 10 and 16); only the specific tool names differ (pytest+moto instead of Jest+aws-sdk-client-mock, debugpy instead of Node's built-in inspector).

Lambda architecture — what actually runs

A Lambda function is not a server you can SSH into. It's code + configuration that AWS runs inside a managed, sandboxed execution environment on demand.

Anatomy of one invocation
Event source (API Gateway, SQS, EventBridge, S3, direct SDK call…) → Lambda service receives the event → Is there a warm execution environment? Yes → reuse it (fast — a “warm start”) No → provision one: download code, start the runtime, run init code outside your handler (a “cold start”) → Runtime calls your handler function with (event, context) → Handler runs, using the attached execution role (IAM) for any AWS calls → Return value goes back to the caller (or, for async invokes, is discarded/retried) → Logs stream to CloudWatch Logs; the environment is frozen and may be reused for the next event

The pieces you configure

PieceWhat it is
HandlerThe entry point — file.export, e.g. index.handler. Everything at module scope (DB clients, AWS SDK clients) runs once per cold start and is reused across warm invocations — that's why you create clients outside the handler, not inside it.
RuntimeThe managed language runtime (Python 3.13, Node 20, Java 21…) or a container image you build yourself with the Lambda base image / Runtime Interface Client baked in.
Execution roleThe IAM role the function assumes for every invocation. Least privilege applies exactly as it does for ECS (Lesson 3) — scope it to the specific table/queue/bucket ARNs it touches.
Memory (128 MB–10,240 MB)CPU scales linearly with memory — there is no separate CPU dial. Under-provisioning memory is often the actual cause of a "slow" Lambda.
Timeout (max 15 min)Hard ceiling per invocation. A function stuck waiting on a downstream call is billed the whole time and then killed.
ConcurrencyHow many invocations run in parallel. Unset = scales to the account-wide unreserved pool. Reserved concurrency caps (and guarantees) capacity per function; provisioned concurrency keeps N environments pre-warmed to eliminate cold starts.
LayersVersioned zip bundles (shared libraries, a common AWS SDK version pin) attached to multiple functions instead of duplicated in every deployment package.
VPC attachmentOptional. Needed only if the function must reach something with no public endpoint (RDS in a private subnet). Adds an ENI attach step to cold starts and requires a NAT for any internet-bound call (e.g. Bedrock, SES) from inside the VPC.
Alias / VersionA version is an immutable, numbered snapshot of code+config. An alias (e.g. live, qa) is a named, mutable pointer to a version — and can split traffic between two versions for canary rollout.
Azure anchor Lambda ≈ Azure Functions (Consumption or Premium plan). Execution role ≈ the function's managed identity. Layers ≈ Function App shared dependencies / extension bundles. Alias+Version traffic-shifting ≈ deployment slots with traffic routing. Provisioned concurrency ≈ Premium plan's "always ready" instances.

Can I test Lambda without AWS? — yes, in layers

Same idea as the CDK lesson's local-mock ladder (Lesson 18): start with the cheapest, fastest layer and only reach for the next one when you need it.

LayerWhat it mocksNeeds Docker?Needs AWS creds?
1. Call the handler directlyNothing — it's just a function callNoNo
2. jest + aws-sdk-client-mockThe AWS SDK v3 client surface (DynamoDB, S3, SES…)NoNo
3. sam local invokeThe Lambda execution environment (real runtime container)YesNo (unless the handler calls real AWS)
4. sam local start-apiAPI Gateway + Lambda together, on localhostYesNo
5. LocalStackThe Lambda service, plus whatever other AWS APIs your handler callsYesNo (fake credentials accepted)

Layer 1 & 2 — no Docker, no AWS, milliseconds

This is a genuine unit test of your handler's business logic — no Lambda runtime, no Docker, no SAM, no LocalStack, no AWS account. You call the handler like any other function, and a mocking library intercepts whatever AWS SDK calls it makes, in-process.

LanguageTest runnerAWS-mocking library
TypeScriptJestaws-sdk-client-mock — mocks the AWS SDK v3 client
Pythonpytestmoto — mocks the boto3 API surface
 
index.ts — the handler
import { DynamoDBClient } from '@aws-sdk/client-dynamodb';
import { DynamoDBDocumentClient, GetCommand } from '@aws-sdk/lib-dynamodb';

// module scope — created once per cold start, reused across warm invocations
const ddb = DynamoDBDocumentClient.from(new DynamoDBClient({}));

export const handler = async (event: { customer_id: string }) => {
  const { Item } = await ddb.send(new GetCommand({
    TableName: process.env.TABLE_NAME,
    Key: { pk: `CUST#${event.customer_id}` },
  }));
  return Item;
};
index.test.ts
import { mockClient } from 'aws-sdk-client-mock';
import { DynamoDBDocumentClient, GetCommand } from '@aws-sdk/lib-dynamodb';
import { handler } from './index';

const ddbMock = mockClient(DynamoDBDocumentClient);

beforeEach(() => ddbMock.reset());

test('returns the profile for a known customer', async () => {
  ddbMock.on(GetCommand, { TableName: 'Customers', Key: { pk: 'CUST#1' } })
    .resolves({ Item: { pk: 'CUST#1', name: 'Ada' } });

  // No SAM, no Docker, no network — this is just calling a function
  const result = await handler({ customer_id: '1' });

  expect(result?.name).toBe('Ada');
});

Set a breakpoint in index.ts and run this test under your normal debugger (VS Code's built-in “Debug Jest Tests” / the Jest extension) — this covers the majority of Lambda debugging, since most bugs are in your business logic, not in AWS's runtime plumbing.

The Python equivalent (Lessons 10 and 16's handlers) is the same shape, just with pytest + moto:

handler.py
import os, boto3

ddb = boto3.resource("dynamodb")   # module scope — reused across warm invocations

def lambda_handler(event, context):
    table = ddb.Table(os.environ["TABLE_NAME"])
    resp = table.get_item(Key={"pk": f"CUST#{event['customer_id']}"})
    return resp.get("Item")
test_handler.py
import os, boto3, pytest
from moto import mock_aws
from handler import lambda_handler

@mock_aws
def test_returns_profile_for_known_customer():
    os.environ["TABLE_NAME"] = "Customers"
    ddb = boto3.resource("dynamodb", region_name="us-east-1")
    table = ddb.create_table(
        TableName="Customers",
        KeySchema=[{"AttributeName": "pk", "KeyType": "HASH"}],
        AttributeDefinitions=[{"AttributeName": "pk", "AttributeType": "S"}],
        BillingMode="PAY_PER_REQUEST",
    )
    table.put_item(Item={"pk": "CUST#1", "name": "Ada"})

    # No SAM, no Docker, no network — this is just calling a Python function
    result = lambda_handler({"customer_id": "1"}, None)

    assert result["name"] == "Ada"

Layer 3 & 4 — run the real handler in a real container, attach a debugger

Reach for SAM CLI when you need to reproduce something environment-specific: a cold-start timing issue, a runtime version quirk, or the exact event shape API Gateway sends.

terminal — invoke with a sample event
sam local invoke GetCustomerProfileFunction \
  -t template.yaml \
  -e events/api_gateway_get.json \
  --env-vars env.json
terminal — run API Gateway + Lambda on localhost
sam local start-api -t template.yaml --env-vars env.json
# curl http://127.0.0.1:3000/customers/1
terminal — attach a real debugger (step through code)
sam local invoke GetCustomerProfileFunction \
  -t template.yaml -e events/api_gateway_get.json \
  -d 5858    # SAM starts the Node runtime with --inspect-brk=5858 automatically
# then attach VS Code's Node debugger (or chrome://inspect) to localhost:5858 — breakpoints
# work exactly as if the code were running natively, but it's actually inside the Lambda container
Container images: use the Runtime Interface Emulator directly If you build a container-image Lambda, you don't need SAM at all to test locally — the public base images ship with the Runtime Interface Emulator (RIE). docker run -p 9000:8080 my-lambda-image, then curl -XPOST "http://localhost:9000/2015-03-31/functions/function/invocations" -d '{"customer_id":"1"}'. This is the same mechanism SAM uses under the hood.

Layer 5 — LocalStack, when the handler talks to several AWS services

If GetCustomerProfile reads DynamoDB, calls Bedrock, and writes to S3, wiring up aws-sdk-client-mock for all three or hand-crafting every SAM env var gets tedious. LocalStack runs an AWS-API-compatible server in Docker and lets you point the real AWS SDK at it.

terminal
docker run -d --name localstack -p 4566:4566 localstack/localstack

# seed a fake table the handler can hit
aws --endpoint-url=http://localhost:4566 dynamodb create-table \
  --table-name Customers --attribute-definitions AttributeName=pk,AttributeType=S \
  --key-schema AttributeName=pk,KeyType=HASH --billing-mode PAY_PER_REQUEST

samlocal deploy --stack-name local-agent-tools   # samlocal = SAM wrapper for LocalStack, like cdklocal for CDK
awslocal lambda invoke --function-name GetCustomerProfile out.json && cat out.json
None of this replaces a real staging deploy Layers 1–5 all catch wiring and logic bugs cheaply. They do not prove IAM permissions are correct (aws-sdk-client-mock and LocalStack don't enforce policies the way real AWS does), nor do they reproduce real cold-start latency, VPC networking, or account-level quotas. A real deploy to a QA/staging account (next section) is still the last gate before prod.

Grouping Lambdas and running them per environment (QA, UAT, prod)

Yes — this is the normal way teams run Lambda. The pattern is the same one used for every other resource in this course: one parameterized definition, deployed multiple times, not multiple copies of the code.

Option A: separate AWS accounts per environment (recommended for finance)

QA, UAT, and prod are three different AWS accounts, tied together by AWS Organizations. Same CDK app or SAM template, same function code, deployed into a different account+region per environment via CI/CD.

bin/finapp-infra.ts — CDK, one stack class, three environments
import * as cdk from 'aws-cdk-lib';
import { LambdaGroupStack } from '../lib/lambda-group-stack';

const app = new cdk.App();
const envName = (app.node.tryGetContext('env') as string) ?? 'qa';   // cdk deploy -c env=uat

const accounts: Record<string, string> = {
  qa:   '111111111111',
  uat:  '222222222222',
  prod: '333333333333',
};

new LambdaGroupStack(app, `AgentTools-${envName}`, envName, {
  env: { account: accounts[envName], region: 'us-east-1' },
});

app.synth();
lib/lambda-group-stack.ts — several related functions, one stack
import { Stack, StackProps, Duration, Tags } from 'aws-cdk-lib';
import * as lambda from 'aws-cdk-lib/aws-lambda';
import { Construct } from 'constructs';

const CONFIG: Record<string, { memory: number; logRetentionDays: number; reservedConcurrency: number }> = {
  qa:   { memory: 256,  logRetentionDays: 7,  reservedConcurrency: 5 },
  uat:  { memory: 512,  logRetentionDays: 30, reservedConcurrency: 10 },
  prod: { memory: 1024, logRetentionDays: 90, reservedConcurrency: 50 },
};

export class LambdaGroupStack extends Stack {
  constructor(scope: Construct, id: string, envName: string, props?: StackProps) {
    super(scope, id, props);

    // Config that differs per environment lives in one place, not scattered across functions
    const config = CONFIG[envName];

    // Group: every tool Lambda for the agent shares naming, tags, and defaults
    const functions: [string, string][] = [
      ['GetCustomerProfile', 'lambda/get-customer-profile'],
      ['GetAccountBalance',  'lambda/get-account-balance'],
      ['LookupTradeHistory', 'lambda/lookup-trade-history'],
    ];

    for (const [name, handlerPath] of functions) {
      const fn = new lambda.Function(this, name, {
        functionName: `${name}-${envName}`,
        runtime: lambda.Runtime.NODEJS_20_X,
        handler: 'index.handler',
        code: lambda.Code.fromAsset(handlerPath),
        memorySize: config.memory,
        timeout: Duration.seconds(10),
        reservedConcurrentExecutions: config.reservedConcurrency,
        environment: { ENV: envName },
      });
      // tag every function in the group the same way — cost allocation, ownership
      Tags.of(fn).add('team', 'agent-tools');
      Tags.of(fn).add('environment', envName);
    }
  }
}

The stack takes an environment name as a parameter, so the assertion test (same aws-cdk-lib/assertions pattern as Lesson 18) can confirm each environment actually gets the memory/concurrency it's supposed to — not just that the stack synthesizes.

test/lambda-group-stack.test.ts
import { App } from 'aws-cdk-lib';
import { Template } from 'aws-cdk-lib/assertions';
import { LambdaGroupStack } from '../lib/lambda-group-stack';

test('qa functions get qa-sized memory and concurrency', () => {
  const template = Template.fromStack(new LambdaGroupStack(new App(), 't', 'qa'));

  template.hasResourceProperties('AWS::Lambda::Function', {
    FunctionName: 'GetCustomerProfile-qa',
    MemorySize: 256,
    ReservedConcurrentExecutions: 5,
  });
});

test('prod functions get prod-sized memory and concurrency', () => {
  const template = Template.fromStack(new LambdaGroupStack(new App(), 't', 'prod'));

  template.hasResourceProperties('AWS::Lambda::Function', {
    FunctionName: 'GetCustomerProfile-prod',
    MemorySize: 1024,
    ReservedConcurrentExecutions: 50,
  });

  // three tool Lambdas defined — catches an accidental drop from the `functions` list
  template.resourceCountIs('AWS::Lambda::Function', 3);
});
Same rule as Lesson 18: cdk synth doesn't run this either This is an ordinary Jest suite (npm test / npx jest), separate from cdk synth. Each test instantiates the stack with a specific envName and synthesizes just that instance in-process via Template.fromStack(...) — useful here specifically because it lets you assert against qa/uat/prod configurations independently, without ever deploying any of them.
Promotion pipeline
git push to main → CI builds one artifact (zip/image), tags it with the commit SHA → cdk deploy -c env=qa into the QA account — automatic on every merge → automated + manual QA sign-off → cdk deploy -c env=uat into the UAT account — manual trigger / approval gate → business sign-off → cdk deploy -c env=prod into the prod account — requires a second approver

Option B: one account, environment separated by stage/alias

Smaller teams sometimes skip separate accounts and instead separate environments within one account using naming and Lambda aliases:

MechanismHow it separates environments
Function name suffixGetCustomerProfile-qa, GetCustomerProfile-uat, GetCustomerProfile-prod as three distinct function resources (what the CDK loop above does even across accounts)
Alias + VersionOne function, three named aliases (qa, uat, live) each pointing at a different published version — API Gateway stages invoke the alias, not the function directly
API Gateway stages/qa/customers/1, /uat/customers/1, /prod/customers/1 — each stage wired to the matching alias
Prefer separate accounts for a financial app Single-account, alias-only separation is cheaper to set up but means a QA IAM role, a QA test script with the wrong target, or a runaway QA load test all execute against the same account that holds production data and quotas. Account-level isolation (Option A) is the stronger blast-radius boundary and is what most bank/fintech compliance frameworks expect. Use SCPs (Service Control Policies) at the AWS Organization level so QA/UAT accounts categorically cannot reach production data stores even by mistake.

Production checklist

  • Business logic covered by handler-level unit tests (Layer 1–2 above) that need no Docker and no AWS credentials
  • At least one sam local invoke / RIE run against the packaged artifact before it ships, catching packaging and runtime-version issues unit tests can't
  • Execution role scoped to exact ARNs, one role per function (or per closely related group) — never a shared role with broad access "to be safe"
  • Memory sized from CloudWatch metrics, not guessed; timeout set with margin, not equal to the slowest observed run
  • Reserved concurrency set on anything that calls a rate-limited downstream (RDS, a third-party API) so a traffic spike can't exhaust connections
  • Function/stack code parameterized by environment (account, memory, concurrency, log retention) — never branched with if env == "prod" string checks scattered through business logic
  • CDK assertion tests cover each environment's config independently (qa/uat/prod memory, concurrency), not just that the stack synthesizes at all
  • QA and UAT in separate AWS accounts from prod, with SCPs preventing cross-account data access
  • CI/CD promotes the same built artifact through QA → UAT → prod — never rebuilds per environment
  • CloudWatch alarms on Errors, Throttles, and Duration p99 per function, per environment

Knowledge Check

Four questions on Lambda architecture, local testing, and multi-environment deploys.

1. Why do Lambda best practices say to create the AWS SDK client at module scope, outside the handler function?

2. You want to step through your Lambda handler's real logic with breakpoints, with zero AWS calls and zero Docker, in under a second per run. Which local-testing layer fits?

3. What does a Lambda alias let you do that a bare function name doesn't?

4. For a financial app, why is running QA and UAT in separate AWS accounts from prod preferred over separating them by function-name suffix in one account?

Lesson takeaway A Lambda invocation is: event in → a managed execution environment (cold or warm) runs your handler under an IAM execution role → response out, logged to CloudWatch. You can test almost all of it without AWS: call the handler directly with aws-sdk-client-mock for the fastest loop, use sam local invoke / the Runtime Interface Emulator to run the real container with a real debugger attached, and reach for LocalStack when several AWS services are involved — but a real staging deploy is still the final gate, since none of these enforce IAM the way real AWS does. To run related Lambdas across QA/UAT/prod, parameterize one stack definition by environment (memory, concurrency, log retention, account) and promote the same built artifact through each stage via CI/CD; prefer separate AWS accounts with SCPs over same-account naming/aliases for the hard isolation a financial app needs.
