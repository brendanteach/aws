Lesson 24 · Event-Driven Architecture

EventBridge, SNS → Lambda, and Direct API Polling

Three different ways code finds out that something happened in AWS — and when to reach for each one, with working Node.js/TypeScript for all three.

Lesson 22 named three paths for getting a CloudWatch alarm's state to a Lambda (or an AI agent's tool): EventBridge, SNS, and direct API calls. This lesson is the deep dive — what each one actually is, how to wire it up, and working code for all three, using the same “an agent needs to read the alarm that just fired” scenario throughout so you can compare them directly.

Azure anchor EventBridge ≈ Azure Event Grid (pattern-matched event routing). SNS ≈ Azure Service Bus Topics (or Event Grid's push model, depending on which SNS feature you're using). 1. EventBridge — pattern-matched event routing

Amazon EventBridge is a serverless event bus. AWS services emit events onto it automatically — a CloudWatch alarm changing state, an ECS task stopping, an S3 object being created — and you write rules that match a JSON pattern against those events and route matches to targets (Lambda, SQS, Step Functions, another event bus). No topic to create, no publish call to make — the event already exists the moment the underlying thing happens.

Setting up a rule → Lambda target (CDK, TypeScript)

lib/alarm-routing-stack.ts
import { Stack, StackProps, Duration } from 'aws-cdk-lib';
import * as events from 'aws-cdk-lib/aws-events';
import * as targets from 'aws-cdk-lib/aws-events-targets';
import * as lambda from 'aws-cdk-lib/aws-lambda';
import { Construct } from 'constructs';

export class AlarmRoutingStack extends Stack {
  constructor(scope: Construct, id: string, props?: StackProps) {
    super(scope, id, props);

    const fn = new lambda.Function(this, 'HandleAlarmEvent', {
      runtime: lambda.Runtime.NODEJS_20_X,
      handler: 'index.handler',
      code: lambda.Code.fromAsset('lambda/handle-alarm-event'),
      timeout: Duration.seconds(10),
    });

    // Match only ALARM-state transitions for this specific alarm — filtering with no code
    new events.Rule(this, 'OnFinappApiAlarm', {
      eventPattern: {
        source: ['aws.cloudwatch'],
        detailType: ['CloudWatch Alarm State Change'],
        detail: {
          alarmName: ['finapp-api-5xx-rate-high'],
          state: { value: ['ALARM'] },
        },
      },
      targets: [new targets.LambdaFunction(fn)],
    });
  }
}
lambda/handle-alarm-event/index.ts
interface AlarmEvent {
  detail: { alarmName: string; state: { value: string; reason: string } };
}

export const handler = async (event: AlarmEvent) => {
  const { alarmName, state } = event.detail;
  console.log(`Alarm ${alarmName} is now ${state.value}: ${state.reason}`);
  // e.g. hand off to an agent tool that pulls logs for the affected window
};
Why this beats subscribing to an SNS topic for AWS-native events There's no topic to create or wire the alarm to — every CloudWatch alarm's state change is already on the default event bus, for every alarm in the account, automatically. The rule's eventPattern does the filtering (down to matching one specific alarm's transition to ALARM) with no code and no separate SNS topic per alarm. This is usually the better default for anything already emitting events onto EventBridge — reach for SNS when you need fan-out to non-AWS endpoints or you're publishing your own custom application events.

2. SNS → Lambda — fan-out from one publisher

SNS (see the previous lesson note) is push-based fan-out: publish once to a topic, every subscriber gets its own copy — a Lambda, an SQS queue, an email address, an HTTPS endpoint. For a CloudWatch alarm, you point the alarm's action directly at an SNS topic ARN; CloudWatch does the publishing for you.

lib/alarm-routing-stack.ts — SNS instead of / alongside EventBridge
import * as sns from 'aws-cdk-lib/aws-sns';
import * as subs from 'aws-cdk-lib/aws-sns-subscriptions';
import * as cloudwatch from 'aws-cdk-lib/aws-cloudwatch';

const topic = new sns.Topic(this, 'AlarmTopic');
topic.addSubscription(new subs.LambdaSubscription(fn));

// wire an existing alarm's action to this topic
cloudwatch.Alarm.fromAlarmArn(this, 'ExistingAlarm', 'arn:aws:cloudwatch:...:alarm:finapp-api-5xx-rate-high');
// (in practice: set alarmActions on the Alarm construct itself to topic.topicArn when you create it)
lambda/handle-alarm-sns/index.ts — SNS wraps the payload differently than EventBridge
interface SnsEvent {
  Records: { Sns: { Message: string } }[];   // Message is a JSON *string*, not a parsed object
}

export const handler = async (event: SnsEvent) => {
  for (const record of event.Records) {
    const alarm = JSON.parse(record.Sns.Message);   // { AlarmName, NewStateValue, NewStateReason, ... }
    console.log(`Alarm ${alarm.AlarmName} -> ${alarm.NewStateValue}: ${alarm.NewStateReason}`);
  }
};
The payload shape is different from EventBridge — check both An EventBridge target Lambda receives the event already parsed as an object (event.detail.state.value). An SNS-triggered Lambda receives event.Records[].Sns.Message as a JSON string you must parse yourself, and the field names are CloudWatch's classic alarm-notification schema (NewStateValue, not state.value) — a different shape from the EventBridge event for the same underlying alarm. Mixing these up is the most common bug when switching between the two.

3. Direct API polling — ask, don't wait

Sometimes you don't want to react to a push at all — an agent tool invoked on demand ("what's the current status of X?"), a health-check script, or a game-day summary run after the fact. For that, call the CloudWatch APIs directly with the AWS SDK, on your own schedule.

check-alarm.ts — DescribeAlarms, called on demand
import { CloudWatchClient, DescribeAlarmsCommand } from '@aws-sdk/client-cloudwatch';

const cw = new CloudWatchClient({});

export async function getAlarmState(alarmName: string) {
  const { MetricAlarms } = await cw.send(new DescribeAlarmsCommand({
    AlarmNames: [alarmName],
  }));
  return MetricAlarms?.[0];   // .StateValue, .StateReason, .StateUpdatedTimestamp
}

Pulling the logs from the affected window is a two-step, asynchronous API — you start a query, then poll for results:

query-logs.ts — CloudWatch Logs Insights
import {
  CloudWatchLogsClient, StartQueryCommand, GetQueryResultsCommand,
} from '@aws-sdk/client-cloudwatch-logs';

const logs = new CloudWatchLogsClient({});

export async function queryErrorLogs(logGroup: string, sinceEpochSecs: number) {
  const { queryId } = await logs.send(new StartQueryCommand({
    logGroupName: logGroup,
    startTime: sinceEpochSecs,
    endTime: Math.floor(Date.now() / 1000),
    queryString: 'fields @timestamp, @message | filter @message like /ERROR/ | sort @timestamp desc | limit 50',
  }));

  // Logs Insights queries run asynchronously — poll until status is Complete
  for (let i = 0; i < 10; i++) {
    await new Promise(r => setTimeout(r, 1000));
    const result = await logs.send(new GetQueryResultsCommand({ queryId }));
    if (result.status === 'Complete') return result.results;
  }
  throw new Error('log query timed out');
}
This is the shape of a Bedrock agent tool Wrap getAlarmState and queryErrorLogs as the body of two Lambda tools behind an AgentCore Gateway (Lesson 16), and an agent can answer “what happened to the API between 2 and 2:15pm?” on demand — pulling the alarm's state and the matching error logs itself, without anyone having wired a push notification for that specific question in advance. Push (EventBridge/SNS) is for “tell me the moment X happens”; polling is for “tell me what X's state is, right now, because I just asked.”

IAM — least privilege per path

PathPermissions the Lambda's execution role needs
EventBridge targetNone extra for receiving — EventBridge invokes the function directly via a resource-based permission (lambda:InvokeFunction granted to events.amazonaws.com, which CDK's targets.LambdaFunction wires automatically)
SNS subscriberSame pattern — SNS is granted lambda:InvokeFunction on the function; the function itself needs no SNS permissions to receive

Production checklist

  • EventBridge preferred over a per-alarm SNS topic for anything already emitting AWS-native events; SNS reserved for fan-out to non-AWS endpoints or your own published application events
  • EventBridge rules use eventPattern filtering to match only the specific alarm/state transition needed — not a catch-all rule with filtering logic pushed into the Lambda
  • SNS-vs-EventBridge payload shape difference documented and tested — event.Records[].Sns.Message (string, parse it) vs event.detail (already an object)
  • A dead-letter queue configured on both the EventBridge rule target and the SNS subscription, so a failed delivery isn't silently dropped
  • Direct-polling IAM scoped to specific alarm/log-group ARNs, never cloudwatch:*/logs:*
  • Logs Insights queries bounded with a real time window and limit — an unbounded query against a busy log group is slow and expensive
  • CloudTrail on for all three paths, so “who/what reacted to this alarm and when” is answerable during an incident review

Knowledge Check

Four questions on EventBridge, SNS, and direct API polling.

1. You want a Lambda to react only when one specific CloudWatch alarm transitions to ALARM, with no other alarms triggering it. What's the simplest way?

2. Your Lambda is subscribed to an SNS topic that a CloudWatch alarm publishes to. How do you get the alarm name out of the incoming event?

3. An agent tool needs to answer "what happened between 2:00 and 2:15pm?" when asked, not react automatically the moment something happens. Which of the three paths fits?

4. Why does a CloudWatch Logs Insights query require polling GetQueryResults in a loop instead of getting results back from StartQuery directly?

Lesson takeaway Three different jobs, not three competing options: EventBridge pattern-matches AWS-native events (like a CloudWatch alarm state change) straight to a target with no topic and no code-based filtering — the right default for anything already emitting events. SNS → Lambda is push-based fan-out, best when you need multiple independent subscribers or non-AWS endpoints (email, SMS, webhooks); remember its payload is a JSON string in event.Records[].Sns.Message, a different shape from EventBridge's already-parsed event.detail. Direct API calls (DescribeAlarms, Logs Insights' StartQuery/GetQueryResults) are for pull, on-demand questions — exactly what an agent tool needs when asked about a specific window after the fact, rather than reacting to a live push. Scope IAM to specific ARNs for every path, and wire a DLQ on both push mechanisms so a failed delivery is never silent.
