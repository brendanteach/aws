CloudWatch: Monitoring a Financial App

Logs, metrics, alarms, and dashboards — knowing what your system is doing at all times

A financial app that goes wrong silently is worse than one that fails loudly. CloudWatch is AWS's native observability platform. It collects logs from every service, tracks metrics, fires alarms when thresholds are crossed, and visualizes everything on dashboards. This lesson covers what to monitor, what thresholds to set, and how to get paged before your users notice a problem.

CloudWatch Has Three Distinct Capabilities

Logs
Every service's stdout/stderr, structured as searchable log events. ECS containers, Lambda functions, RDS, and ALB all write here.
/ecs/finapp-api
/aws/lambda/trade-confirm
Metrics
Numeric time-series data. CPU%, memory, request count, error rate, queue depth. AWS services emit metrics automatically; your app can emit custom ones.
ECS/CPUUtilization
RDS/FreeableMemory
Alarms
Rules that watch a metric and change state (OK / ALARM / INSUFFICIENT_DATA). Trigger SNS notifications, Auto Scaling actions, or EC2 recovery.
CPU > 80% for 5 min
→ SNS → email / PagerDuty
Azure analogy: Azure Monitor + Application Insights CloudWatch Logs ≈ Azure Monitor Logs (Log Analytics workspace). CloudWatch Metrics ≈ Azure Monitor Metrics. CloudWatch Alarms ≈ Azure Monitor Alerts. AWS X-Ray ≈ Application Insights distributed tracing. The main difference: Azure splits monitoring across multiple products; CloudWatch does it all in one place with a consistent API.

Structured Logging — Do This from Day One

Log lines as plain text are hard to query. Log as JSON and CloudWatch Logs Insights can query them like a database.

Python FastAPI — structured JSON logging
import json, logging, time

class JsonFormatter(logging.Formatter):
    def format(self, record):
        return json.dumps({
            "timestamp": self.formatTime(record),
            "level":     record.levelname,
            "message":   record.getMessage(),
            "logger":    record.name,
            # Add request context via middleware:
            "user_id":   getattr(record, "user_id", None),
            "trade_id":  getattr(record, "trade_id", None),
            "duration_ms": getattr(record, "duration_ms", None),
        })

# Query in CloudWatch Logs Insights:
# fields @timestamp, user_id, trade_id, duration_ms
# | filter level = "ERROR"
# | sort @timestamp desc
# | limit 50

The Complete Alarm Checklist

These are the alarms every financial app deployment must have. Configure them all before going live.

SeverityServiceMetricThresholdAction
Critical ALB HTTPCode_Target_5XX_Count > 10 in 1 min Page on-call immediately — API is returning server errors
Critical RDS FreeableMemory < 200 MB Database about to OOM — immediate scale-up or query investigation
Critical SQS DLQ ApproximateNumberOfMessagesVisible > 0 Failed trade event — investigate immediately, do not let accumulate
Critical RDS DatabaseConnections > 80% of max_connections Connection exhaustion imminent — check RDS Proxy or scale instance
Warning ECS CPUUtilization > 70% for 5 min Scale out ECS service — approaching saturation
Warning ECS MemoryUtilization > 80% for 5 min Risk of OOM task kill — scale out or increase task memory
Warning RDS CPUUtilization > 70% for 10 min Slow queries or insufficient instance size — check Performance Insights
Warning Lambda Errors > 0 Lambda function failed — check logs before DLQ fills
Warning ALB TargetResponseTime > 2 seconds (p99) API latency degrading — investigate slow queries or ECS saturation
Info ECS RunningTaskCount < desired count Tasks crashing or failing health checks — deployment issue
Info RDS FreeStorageSpace < 10 GB Disk filling — enable storage autoscaling or increase allocated storage

Creating an Alarm in Terraform

modules/monitoring/alarms.tf  (excerpt)
resource "aws_cloudwatch_metric_alarm" "api_5xx" {
  alarm_name          = "finapp-api-5xx-${var.environment}"
  alarm_description   = "API returning 5xx errors"
  namespace           = "AWS/ApplicationELB"
  metric_name         = "HTTPCode_Target_5XX_Count"
  dimensions          = { LoadBalancer = aws_lb.main.arn_suffix }

  statistic           = "Sum"
  period              = 60     # 1-minute window
  evaluation_periods  = 1
  threshold           = 10
  comparison_operator = "GreaterThanThreshold"
  treat_missing_data  = "notBreaching"  # no data = no traffic = OK

  alarm_actions = [aws_sns_topic.oncall.arn]
  ok_actions    = [aws_sns_topic.oncall.arn]  # notify on recovery too
}

resource "aws_cloudwatch_metric_alarm" "rds_freeable_memory" {
  alarm_name         = "finapp-rds-low-memory-${var.environment}"
  namespace          = "AWS/RDS"
  metric_name        = "FreeableMemory"
  dimensions         = { DBInstanceIdentifier = aws_db_instance.postgres.id }
  statistic          = "Average"
  period             = 300
  evaluation_periods = 2
  threshold          = 209715200   # 200 MB in bytes
  comparison_operator = "LessThanThreshold"
  alarm_actions      = [aws_sns_topic.oncall.arn]
}

SNS — The Alarm Notification Router

Alarms don't notify humans directly — they publish to an SNS Topic (Simple Notification Service). SNS then fans out to email, PagerDuty, Slack, or any HTTPS endpoint.

SNS Topic: finapp-oncall-prod
  Subscriptions:
    → Email: oncall@finapp.com
    → HTTPS: https://events.pagerduty.com/integration/xxx/enqueue
    → Email: slack-alerts-webhook (via email-to-Slack integration)

Custom Metrics from Your Application

AWS services emit metrics automatically, but your application logic can emit its own. These are the most valuable signals for a financial app:

Python — emitting custom CloudWatch metrics
import boto3
cw = boto3.client("cloudwatch")

def record_trade_metric(symbol: str, quantity: int, latency_ms: float):
    cw.put_metric_data(
        Namespace="FinApp/Trading",
        MetricData=[
            {
                "MetricName": "TradeSubmitted",
                "Value": 1, "Unit": "Count",
                "Dimensions": [{"Name": "Symbol", "Value": symbol}]
            },
            {
                "MetricName": "TradeLatencyMs",
                "Value": latency_ms, "Unit": "Milliseconds"
            }
        ]
    )

# Now alarm on FinApp/Trading TradeSubmitted dropping to 0 during market hours
# → indicates broken trade flow before users report it

X-Ray — Distributed Tracing

CloudWatch tells you that something is slow. X-Ray tells you where the latency is. It traces a request through CloudFront → ALB → ECS → RDS, showing a waterfall of every segment and its duration.

FastAPI + X-Ray instrumentation
# pip install aws-xray-sdk
from aws_xray_sdk.core import xray_recorder, patch_all
patch_all()  # auto-instruments boto3, requests, psycopg2, SQLAlchemy

# Now every outbound call (RDS query, S3 call, SQS send)
# appears as a subsegment in the X-Ray trace

# In X-Ray console: see exactly which SQL query took 800ms
# out of a 900ms total API response time

Azure → AWS Observability Map

ConceptAzureAWSDifference
Log aggregationAzure Monitor Logs (Log Analytics)CloudWatch LogsBoth use query languages (KQL vs CloudWatch Logs Insights). CloudWatch Logs Insights is simpler but less powerful than KQL.
MetricsAzure Monitor MetricsCloudWatch MetricsSame concept. AWS default retention: 15 months. Custom metrics: 14 days (free tier), longer with extended retention.
AlertsAzure Monitor AlertsCloudWatch Alarms + SNSAzure alerts send directly to action groups. AWS alarms send to SNS, which routes to email/PagerDuty/Slack.
DashboardsAzure Monitor Workbooks / DashboardsCloudWatch DashboardsBoth are widget-based. CloudWatch dashboards are simpler; Workbooks are more flexible for multi-step analysis.
Distributed tracingApplication InsightsAWS X-RayApp Insights has richer APM features (dependency tracking, user flows). X-Ray is simpler but integrates deeply with Lambda, ECS, and API Gateway.
Log query languageKQL (Kusto Query Language)CloudWatch Logs InsightsKQL is more expressive. CloudWatch Logs Insights covers 80% of real-world queries with a simpler syntax.
Notification routingAction GroupsSNS TopicsBoth fan out to email, webhooks, PagerDuty. SNS can also trigger Lambda for custom routing logic.

Knowledge Check

1. Your CloudWatch alarm for RDS FreeableMemory has treat_missing_data = "notBreaching". At 3 AM, RDS has no traffic and CloudWatch receives no data points. What state is the alarm in?

2. You want to alert when your API p99 latency exceeds 2 seconds. Which CloudWatch metric and statistic should you use?

3. Why should you emit a custom CloudWatch metric for TradeSubmitted count and alarm when it drops to 0 during market hours?

4. X-Ray shows your API p99 latency is 1,800ms. The X-Ray waterfall shows the ECS segment takes 50ms and a "psycopg2" subsegment takes 1,700ms. What does this tell you?

Lesson takeaway CloudWatch = Logs (structured JSON, queryable) + Metrics (time-series, AWS-native and custom) + Alarms (threshold rules → SNS → on-call). The non-negotiable alarms: 5XX_Count, FreeableMemory, DLQ depth, DatabaseConnections. Add custom metrics for business signals (TradeSubmitted count). Use X-Ray to locate latency — it tells you whether slowness is in your code, a database query, or an external API call. Log as structured JSON so CloudWatch Logs Insights can query across fields.
