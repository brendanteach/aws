Lesson 01 · AWS Architecture

The AWS Map for a Financial Web App

From Azure mental model to AWS architecture in one session

You already know how cloud applications are structured. You know about VNets, App Services, Blob Storage, and SQL databases from Azure. That's a significant advantage — AWS covers the same territory, just with different names and a few important structural differences.

This lesson maps the full stack of a financial web app onto AWS services. By the end, you'll be able to draw the architecture and name the right service for each layer.

The Architecture We're Building Toward

A financial web app — think a trading dashboard, portfolio tracker, or banking interface — needs these layers:

┌─────────────────────────────────────────────────────┐ │ INTERNET │ └──────────────────────┬──────────────────────────────┘ │ ┌────────▼────────┐ │ Route 53 │ DNS │ CloudFront │ CDN + edge cache └────────┬────────┘ │ ┌─────────────┴─────────────┐ │ │ ┌────────▼────────┐ ┌──────────▼──────────┐ │ S3 Bucket │ │ Application Load │ │ (Frontend SPA) │ │ Balancer (ALB) │ └─────────────────┘ └──────────┬───────────┘ │ ┌──────────▼───────────┐ │ ECS / Fargate │ │ (Backend API) │ └──────────┬────────────┘ │ ┌─────────────────────┼─────────────────────┐ │ │ │ ┌──────────▼──────┐ ┌──────────▼──────┐ ┌──────────▼──────┐ │ RDS │ │ ElastiCache │ │ S3 │ │ (PostgreSQL) │ │ (Redis) │ │ (File storage) │ └──────────────────┘ └─────────────────┘ └──────────────────┘ All backend resources live inside a VPC (Virtual Private Cloud) with public subnets (ALB) and private subnets (ECS, RDS, Redis)
Finance requirement: Defense in depth RDS and ElastiCache are never in public subnets. Only the ALB is internet-facing. This is a core security principle for financial apps — all data stores sit behind at least two network boundaries.

The Azure → AWS Service Map

Every service you used in Azure has a direct AWS counterpart. The table below is your translation dictionary.

Category Azure Service AWS Equivalent Key difference
DNS Azure DNS Route 53 Route 53 supports health-check based routing and failover natively
CDN Azure CDN / Front Door CloudFront CloudFront is tightly integrated with S3 for SPA hosting
Static hosting Azure Static Web Apps S3 + CloudFront No single "static web apps" service — you compose S3 + CloudFront yourself (or use Amplify)
Blob / Object storage Azure Blob Storage Amazon S3 S3 is the foundational storage primitive in AWS — nearly everything uses it
PaaS containers Azure Container Apps / AKS ECS Fargate / EKS ECS Fargate = managed containers without managing servers (the common choice); EKS = full Kubernetes
Serverless functions Azure Functions AWS Lambda Same model; Lambda has a 15 min max timeout vs Azure's 10 min (consumption plan)
Load balancer Azure Load Balancer / App Gateway ALB (Application Load Balancer) ALB = Layer 7 (HTTP/HTTPS); NLB = Layer 4 (TCP). ALB is the default for web apps
Relational DB Azure SQL / Azure Database for PostgreSQL Amazon RDS RDS supports PostgreSQL, MySQL, SQL Server, Oracle. Multi-AZ option = high availability
NoSQL / Document DB Azure Cosmos DB Amazon DynamoDB DynamoDB requires careful key design upfront — less flexible than Cosmos for ad-hoc queries
Cache Azure Cache for Redis ElastiCache (Redis) Near-identical feature set
Virtual network Azure VNet Amazon VPC VPC is regional; subnets are per Availability Zone. AZs ≈ Azure Availability Zones
Identity / Auth Azure AD B2C Amazon Cognito Cognito handles user pools (login/signup) + identity pools (AWS credentials for users)
IAM / RBAC Azure Active Directory + RBAC AWS IAM IAM is more granular — every API call is authorized by IAM policies attached to roles
Secrets / Key Vault Azure Key Vault Secrets Manager + KMS Secrets Manager stores secrets; KMS manages encryption keys. Two separate services
Monitoring / Metrics Azure Monitor / App Insights CloudWatch CloudWatch does logs, metrics, and alarms. Add X-Ray for distributed tracing
Container registry Azure Container Registry Amazon ECR ECR integrates natively with ECS and EKS
API Gateway Azure API Management Amazon API Gateway Used primarily with Lambda for serverless APIs; less common when using ECS+ALB

Three Things That Work Differently Than Azure

1. IAM is everywhere

In Azure, RBAC controls access to Azure resources, but your app code uses connection strings or managed identities. In AWS, IAM roles are used for everything — your ECS container gets an IAM role, your Lambda gets an IAM role, your S3 bucket has an IAM policy. You will write IAM policies constantly. Learning IAM well is non-negotiable.

2. Regions and Availability Zones are first-class

AWS makes you explicitly choose a Region (e.g., us-east-1) and deploy resources across at least two Availability Zones (AZs) for high availability. For a financial app, Multi-AZ RDS and ECS tasks spread across 2+ AZs is the baseline. This is more explicit than Azure, where HA is often a checkbox.

3. S3 is the universal substrate

In Azure, Blob Storage is one of many storage options. In AWS, S3 is everywhere — it stores your frontend, your Lambda deployment packages, your CloudWatch logs exports, your RDS backups, your audit trails. Think of it as the file system of AWS.

The Financial App Stack — Service by Service

Here is the concrete service selection for a production financial web app on AWS:

LayerServiceWhy
DNS Route 53 Health-check routing; failover to secondary region if needed
CDN / Edge CloudFront TLS termination, cache, WAF integration for DDoS/OWASP protection
Frontend S3 (static SPA) React/Vue/Next.js built output hosted as static files
Authentication Cognito User Pools Managed login, MFA, JWT tokens — required for finance
Load balancer ALB Routes HTTPS to ECS containers; handles SSL certs via ACM
Backend API ECS Fargate Containerized API (Python/Node/Go) — no server management
Primary database RDS PostgreSQL Multi-AZ ACID compliance, automatic failover, point-in-time recovery
Cache ElastiCache Redis Session store, rate limiting, market data cache
File storage S3 Trade confirmations, statements, audit documents
Networking VPC + private subnets RDS and ECS in private subnets; only ALB in public
Secrets Secrets Manager DB passwords, API keys — never hardcoded or in env files
SSL/TLS certs ACM (Certificate Manager) Free managed TLS certs for CloudFront and ALB
Monitoring CloudWatch Logs, metrics, alarms; add X-Ray for request tracing
IAM IAM Roles + Policies Every service-to-service call is authorized via IAM

Lesson takeaway for finance The pattern for a financial web app on AWS: CloudFront → S3 (frontend), CloudFront → ALB → ECS Fargate (backend API), RDS Multi-AZ in private subnets (database), Cognito (auth), IAM roles for all service-to-service calls. This covers 80% of the architecture decisions you'll face.
