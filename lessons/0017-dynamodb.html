Lesson 17 · Database

Amazon DynamoDB: Serverless NoSQL, CRUD, and Agent State

A key-value database with no servers to run and no capacity to plan — and the natural place an AgentCore agent keeps session memory, audit trails, and idempotency records.

Lesson 5 gave you RDS PostgreSQL — the relational database for your core financial data, where you need joins, transactions across many tables, and ad-hoc SQL for reporting. DynamoDB is the other half of the storage story: when you know exactly how you'll look a record up (“give me user 883's profile”, “give me this session's messages”) and you want that lookup to stay single-digit-millisecond fast whether the table holds a thousand rows or a billion.

This lesson covers three things: what DynamoDB actually is, how to do basic CRUD against it from Python, and how an AgentCore agent uses it — both as a tool it calls and as the store behind its own memory.

Azure anchor DynamoDB is Azure Cosmos DB (the core NoSQL / Table API). Both are fully managed, horizontally partitioned, single-digit-ms NoSQL stores billed by throughput. A DynamoDB table ≈ a Cosmos container; a DynamoDB partition key ≈ a Cosmos partition key; DynamoDB on-demand mode ≈ Cosmos serverless / autoscale. If you have used Azure Table Storage, DynamoDB is that idea grown up — secondary indexes, transactions, streams, TTL.

What DynamoDB is

A fully managed, serverless NoSQL database. There is no instance to size, no engine version to patch, no storage to pre-allocate. You create a table, and AWS spreads it across partitions automatically as it grows. Encryption at rest is always on. You pay for the requests you make (on-demand) or for reserved throughput (provisioned + autoscaling).

The data model

TermWhat it isRelational analogy
TableA collection of items. No fixed schema beyond the key.Table
ItemOne record. Max 400 KB. Each item can have different attributes.Row
AttributeA typed field: string, number, binary, bool, list, map, set, null.Column / cell
Partition key (PK)Hash key. Decides which partition the item lives on. Required.Part of the primary key
Sort key (SK)Optional. Orders items within a partition key and enables range queries.The rest of a composite primary key
GSIGlobal Secondary Index — a second (PK, SK) pair to query the same data a different way.A secondary index (roughly)

The primary key is either just a partition key (each value unique, like a user ID) or a partition key + sort key composite (many items share a partition key, distinguished and ordered by the sort key — e.g. PK = SESSION#abc, SK = MSG#2026-09-03T10:00:01).

You model for access patterns, not entities In RDS you design normalized tables and figure out queries later. In DynamoDB it is the reverse: write down every lookup your app will do first, then design keys and indexes so each one is a direct GetItem or Query. There are no joins, and a full-table Scan is a last resort, not a query tool.

When to reach for it (vs RDS)

Use DynamoDB forUse RDS for
User profiles, preferences, feature flagsAccounts, positions, ledger entries — anything transactional and relational
Session state, chat history, agent memoryReporting and analytics with ad-hoc SQL
Idempotency keys, rate-limit counters, locksData touched by many-table transactions
High-volume event / audit logs keyed by entityAnything where you don't yet know the query patterns
Anything needing predictable latency at large scaleComplex joins, foreign keys, constraints

Features worth knowing exist

  • On-demand vs provisioned capacity — on-demand: no planning, pay per request, good default. Provisioned + autoscaling: cheaper for steady, predictable load.
  • DynamoDB Streams — an ordered change feed of every write, consumable by Lambda. This is your hook for “when an item changes, do X” (audit, projections, notifications).
  • TTL — set a timestamp attribute and DynamoDB deletes the item automatically when it passes. Perfect for session and cache data.
  • Transactions — TransactWriteItems gives all-or-nothing writes across up to 100 items / multiple tables.
  • Conditional writes — “only write if this attribute doesn't exist / still equals X”. The basis of idempotency and optimistic locking.
  • Point-in-time recovery (PITR) — continuous backups, restore to any second in the last 35 days.
  • Global tables — multi-region active-active replication.
  • Consistency — reads are eventually consistent by default; ask for ConsistentRead=True when you must see your own last write.

Basic CRUD from Python

All examples use boto3. The resource interface (below) maps items to plain Python dicts; the lower-level client interface makes you write {"S": "..."} type descriptors by hand.

Create the table (once, usually in Terraform/CDK)

import boto3
ddb = boto3.resource("dynamodb", region_name="us-east-1")

ddb.create_table(
    TableName="customers",
    KeySchema=[
        {"AttributeName": "pk", "KeyType": "HASH"},   # partition key
        {"AttributeName": "sk", "KeyType": "RANGE"},  # sort key
    ],
    AttributeDefinitions=[
        {"AttributeName": "pk", "AttributeType": "S"},
        {"AttributeName": "sk", "AttributeType": "S"},
    ],
    BillingMode="PAY_PER_REQUEST",   # on-demand
)

C — PutItem (create or full replace)

table = ddb.Table("customers")

table.put_item(Item={
    "pk": "CUST#883",
    "sk": "PROFILE",
    "name": "Ada Lovelace",
    "tier": "private",
    "kyc_verified": True,
})

# Insert-only: fail if this item already exists (idempotency)
from botocore.exceptions import ClientError
try:
    table.put_item(
        Item={"pk": "CUST#883", "sk": "PROFILE", "name": "Ada Lovelace"},
        ConditionExpression="attribute_not_exists(pk)",
    )
except ClientError as e:
    if e.response["Error"]["Code"] == "ConditionalCheckFailedException":
        pass  # already created — safe to ignore

R — GetItem (one item by key) and Query (a range within a partition)

# GetItem — exact key, the fastest possible read
resp = table.get_item(Key={"pk": "CUST#883", "sk": "PROFILE"})
profile = resp.get("Item")   # None if not found

# Query — all items under one partition key, optionally filtered by sort key
from boto3.dynamodb.conditions import Key
resp = table.query(
    KeyConditionExpression=Key("pk").eq("CUST#883") & Key("sk").begins_with("TXN#"),
    ScanIndexForward=False,   # newest first
    Limit=20,
)
transactions = resp["Items"]
Never Scan in a hot path Scan reads every item in the table and filters after. On a big table it is slow and expensive. If you find yourself wanting a Scan, you are missing an index — add a GSI whose key matches the lookup you need.

U — UpdateItem (partial update, atomic counters)

table.update_item(
    Key={"pk": "CUST#883", "sk": "PROFILE"},
    UpdateExpression="SET tier = :t, updated_at = :u ADD login_count :one",
    ExpressionAttributeValues={
        ":t": "institutional",
        ":u": "2026-09-03T12:00:00Z",
        ":one": 1,
    },
    ConditionExpression="attribute_exists(pk)",   # don't create it if missing
)

D — DeleteItem

table.delete_item(Key={"pk": "CUST#883", "sk": "PROFILE"})

For bulk work there is batch_writer() (up to 25 puts/deletes per request, auto-retried) and TransactWriteItems when several writes must succeed or fail together.

DynamoDB in an AgentCore agentic system

There are two distinct roles, and a real system usually uses both.

Role 1 — DynamoDB behind a tool the agent calls

This is the Lesson 16 pattern. The agent decides it needs data; it calls an MCP tool exposed through AgentCore Gateway; the target Lambda reads DynamoDB and returns JSON.

Agent reads a customer profile
Model: “call get_customer_profile with customer_id=883” → Gateway invokes the target Lambda → Lambda checks the caller's entitlements → table.get_item(Key=...) → returns {"name": ..., "tier": ...} → model uses it in the answer 
def lambda_handler(event, context):
    tool = context.client_context.custom["bedrockAgentCoreToolName"].split("___", 1)[1]

    if tool == "get_customer_profile":
        caller = resolve_identity(context)              # from AgentCore Identity / session
        cust_id = event["customer_id"]                   # model-chosen — do NOT trust
        if not can_view(caller, cust_id):
            return {"error": "not authorized"}

        item = table.get_item(
            Key={"pk": f"CUST#{cust_id}", "sk": "PROFILE"}
        ).get("Item")
        return {"profile": item} if item else {"error": "not found"}
The tool Lambda enforces access, not the model The model picked customer_id. It could pick any value. Entitlement is checked in the Lambda against the authenticated caller, exactly as in Lesson 16. DynamoDB's IAM policy on the Lambda role should also be scoped — e.g. only dynamodb:GetItem / Query on the one table, no Scan, no writes if the tool only reads.

Role 2 — DynamoDB as the agent's own memory and audit store

AgentCore Memory is a managed option, but many teams back their own state in DynamoDB because it is cheap, fast, and they already trust it for durability. Common items:

WhatKey designNotes
Conversation / session historyPK SESSION#<id>, SK MSG#<timestamp>Query by PK to replay the thread. TTL attribute to expire idle sessions.
Framework checkpoints (LangGraph, Strands)PK THREAD#<id>, SK CKPT#<seq>Lets a long-running agent resume after a restart.
Tool-call audit logPK SESSION#<id>, SK TOOL#<timestamp>Every invocation: tool name, resolved caller, args, request ID. Feeds Streams → long-term audit store.
Action idempotencyPK ACTION#<hash>Conditional put_item(attribute_not_exists(pk)) so a retried agent step can't place the same trade twice.
 
# Append one message to session history (called by the agent runtime each turn)
sessions.put_item(Item={
    "pk": f"SESSION#{session_id}",
    "sk": f"MSG#{now_iso()}",
    "role": "assistant",
    "content": text,
    "ttl": int(time.time()) + 86400 * 30,   # auto-delete after 30 days
})

# Replay the thread on the next request
history = sessions.query(
    KeyConditionExpression=Key("pk").eq(f"SESSION#{session_id}") & Key("sk").begins_with("MSG#")
)["Items"]
Streams + PITR = the examiner's answer Turn on DynamoDB Streams on the audit table and fan every change to a Lambda that writes an immutable record to S3 (Object Lock / WORM, Lesson 13). Turn on PITR so an accidental delete is recoverable. Together with AgentCore Observability traces (Lesson 15) you can reconstruct “which user, via which agent, read or changed which record, when.”

How it fits the 10-step build (Lesson 16)

DynamoDB shows up at step 5 (give it memory) — as the store behind session/checkpoint state — and at step 6 (give it tools) — as the database a Gateway target Lambda reads and writes. It is not the reasoning engine and not the vector store (that is OpenSearch / Aurora pgvector for RAG); it is the fast operational store for everything the agent needs to remember or look up by key.

Configuring a table

There are no instances, nodes, or clusters to place — nothing here is about hardware. The settings that matter:

Split or consolidate? Table design

DynamoDB has no instances, so “split vs. consolidate” means one multi-purpose table or several single-purpose tables. The classic expert advice is single-table design — every entity type in one table with generic pk/sk, overloaded keys, and GSIs. The advice has since softened to “it depends,” and one question decides it:

Do you need to fetch multiple entity types together in one request? If yes — “this customer plus their last 20 orders plus their open tickets” — a single table lets one Query on a shared partition key return them pre-joined, with no extra round trips. If your reads are all single-entity lookups by key, a single table buys you nothing and costs you clarity.

When to consolidate (single table)

  • Queries routinely need related items of different types together.
  • Access patterns are well understood and stable.
  • You are optimising a hot path where round-trip count is the cost.

When to split (multiple tables) — often the agent case

The four stores from the section above have genuinely different profiles:

DataTraffic shapeTTLSizeNatural table
Customer profilesread-heavy, tiny itemsnonesmallcustomers
Session / chat historyper-session Query, balanced R/W~30 daysgrowssessions
Tool-call audit logwrite-heavy append, never updatednone / yearshugeaudit (Standard-IA, Streams on)
Idempotency keyswrite-once, checked onceminutes–hourssmallidempotency

Each wants a different capacity mode, TTL, table class, PITR setting, and set of alarms. One table cannot express that cleanly. Split also gives you simpler code, per-table cost attribution, isolated GSI blast radius, and easy exports. And you lose nothing on atomicity: TransactWriteItems and BatchGetItem both work across tables (up to 100 items / 4 MB).

Rule of thumb Consolidate for tightly-coupled, well-known access patterns on a hot path. Split when entities have different lifecycles, when patterns are still evolving, or when each service / agent tool owns its own data — which is most of the time.

Capacity mode & the metrics that decide

On-demand vs. provisioned

Start on-demand — no planning, pay per request, absorbs spikes instantly. Move a table to provisioned + auto-scaling only once its traffic is steady and measured; the rough crossover is sustained utilisation above ~15–20% of a sensible provisioned level. Spiky or low-volume tables stay on-demand.

Signals to watch (CloudWatch)

MetricWhat it tells you
ReadThrottleEvents / WriteThrottleEvents, ThrottledRequestsUnder-provisioned, or a hot partition — fix with better key distribution (write-sharding), not more tables.
Contributor Insights (most-accessed keys)Which partition keys are hot; whether one tenant or entity dominates traffic.

Per-GSI consumed capacity, OnlineIndexConsumedWriteCapacityWrite amplification from too many GSIs — a reason to split a table.
TableSizeBytes, ItemCountWatch item collections approaching the 10 GB per partition-key hard limit.

The partition ceiling One physical partition tops out near 3,000 RCU / 1,000 WCU / 10 GB. Hot-partition throttling is always solved by key design — adding a shard suffix, choosing a higher-cardinality partition key — never by adding tables or raising table-level capacity.

Production checklist

  • Access patterns written down first; keys and GSIs designed to make each one a GetItem or Query
  • Table boundary chosen deliberately: consolidate only where reads need multiple entity types together, otherwise one table per entity/lifecycle
  • On-demand billing to start; move a table to provisioned + autoscaling only once utilisation is steady above ~15–20%
  • Every table tagged for per-table cost attribution; Contributor Insights on for hot-key detection
  • No Scan in request paths — add a GSI instead
  • Conditional writes for every create-once / idempotent operation (agent actions, trades, signups)
  • TTL attribute on all ephemeral data (sessions, caches, locks)
  • Point-in-time recovery enabled on any table holding customer or audit data
  • Streams enabled on audit/state tables, fanning to an immutable S3 record
  • Tool Lambda's IAM policy scoped to specific actions on specific tables; entitlement checked in code against the authenticated caller, never the model's arguments
  • ConsistentRead=True where the agent must observe its own last write in the same turn

Lesson takeaway DynamoDB is AWS's serverless NoSQL database — Cosmos DB's counterpart. You design keys around known access patterns, then CRUD is put_item / get_item / query / update_item / delete_item, with conditional writes for idempotency and Query (never Scan) for ranges. In an AgentCore system it plays two parts: the database a Gateway tool Lambda reads on the agent's behalf (with entitlement checks in the Lambda), and the store behind the agent's own session memory, checkpoints, and audit trail — hardened with TTL, PITR, and Streams. Split into separate tables per entity/lifecycle unless reads genuinely need several entity types together; start on-demand and let CloudWatch throttle, latency, and utilisation metrics tell you when to change capacity mode or fix a hot key.
