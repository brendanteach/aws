Lesson 19 · Methodology

AWS AI-DLC: The AI-Driven Development Lifecycle

A way of running software delivery where AI agents do the production work — requirements, code, tests, IaC — and humans spend their time deciding, validating, and owning the outcome.

Every lesson so far has been about what to build on AWS. This one is about how a team works when AI does most of the typing. AI-DLC (AI-Driven Development Life Cycle) is a methodology AWS published in 2025, along with an open reference implementation (awslabs/aidlc-workflows) that runs inside coding agents like Claude Code, Kiro, Q Developer, and Cursor.

Azure anchor — there isn't one, and that's the point AI-DLC isn't an AWS service you provision; it's a process, and it's deliberately tool- and cloud-agnostic. The thing it replaces is Scrum / SAFe — sprints, story points, backlog grooming, solo authorship followed by async pull-request review. Those ceremonies were designed around the rate a human can read, write, and reason about code. AI-DLC's claim is that once an agent writes the first draft of everything, that rate is no longer the binding constraint, so the process should change shape.

What it is

The core thesis: Agile's bottleneck is human cognitive throughput. A team of seven can only elaborate, write, and review so much per sprint, so work queues up in a backlog that grows faster than it drains. AI-DLC restructures delivery around a different division of labour:

  • AI agents generate the plans, user stories, code, tests (unit, integration, security), infrastructure-as-code, and documentation.
  • Humans supply business intent, resolve ambiguity, make architectural and risk decisions, and validate output continuously — reviewing as the work is produced, not weeks later.

AWS frames it as the middle path between two failures: fully autonomous AI development (too unreliable for regulated work) and AI-as-autocomplete (captures a fraction of the available leverage).

“Bolt” is the load-bearing idea A bolt is one full pass of the lifecycle on one unit of work: intent in, validated increment out, hours later. You are not planning a two-week batch of work — you are running many tiny lifecycles, each with its own requirements, plan, code, tests, and human sign-off, each small enough to reason about and cheap to reverse.

The three phases

AI-DLC's conceptual model has three phases. (The aidlc-workflows reference implementation has since expanded to five — adding Initialization and Ideation — but the mental model below is the framework.)

Phase 1

Inception — “mob elaboration”

The team and the AI turn a business intent into a buildable plan. The agent drafts requirements and surfaces its assumptions as explicit questions (often multiple-choice, with an “other” escape); humans answer, the agent checks for contradictions, and the loop repeats until the spec is solid.

Produces: a requirements document, user stories, a domain model, and a set of small units of work with an execution plan.

Phase 2

Construction — “mob construction”

For each unit of work the agent produces a numbered, checkbox-tracked code-generation plan, gets it approved, then executes it step by step: functional design, code, tests (including security/pen tests), infrastructure-as-code, build and test instructions. Developers review in flight — validating each increment as it lands rather than writing then reviewing.

Produces: well-tested increments, IaC, and continuously-updated documentation, every artifact traceable back to a user story.

Phase 3

Operation

The generated IaC deploys through your CI/CD pipeline (Lesson 12). AI agents assist with incident root-cause analysis and monitoring. Production signals — incidents, metrics, user behaviour — feed back into the next Inception cycle.

Produces: deployed software, operational feedback, and the inputs to the next bolt.

One bolt, end to end
Business intent → agent drafts requirements + asks clarifying questions → human answers & approves spec → agent proposes execution plan → human approves plan → agent generates code + tests + IaC, self-correcting on test/steering-file failures → human validates increment → deploy via CI/CD → operational feedback into next bolt

How to use it

1

Add the workflow rules to your repo. Clone awslabs/aidlc-workflows and copy its rules files into your project (e.g. .amazonq/rules/ for Q Developer, or the equivalent for your agent). They load as steering rules the agent follows.

2

Start a bolt with an intent. In your coding agent: /aidlc Build a statement-export API for the client portal (or “Using AI-DLC, let's build…”). The workflow engine takes over and enters Inception.

3

Do the elaboration loop. The agent writes requirement-verification-questions.md. You answer inline, mark them answered, type “Done”. It reconciles contradictions and produces requirements.md.

4

Clear the approval gates. At each gate you pick: approve & continue, request changes, or (for the spec) add user stories. Nothing proceeds without your explicit approval — requirements gate, plan gate, code gate, build/test gate.

5

Let construction run, reviewing as it goes. The agent works the checkbox plan, generating code and tests. You read each step as it completes, not at the end.

6

Ship and feed back. Approve the build/test summary, deploy the IaC through CI/CD, and let operational signals seed the next bolt.

Rules / steering filesYour standards as machine-readable constraints: security policy, architecture rules, approved-dependency list, regulatory guidance. The agent must satisfy these and self-corrects when it violates one.
Adaptive rigor The workflow sizes itself to the change. A one-line bug fix skips requirements analysis and planning; a new customer-facing feature runs the full Inception. You are not forced through ten stages for a typo — the engine proposes a streamlined path and you approve it.

AI-DLC in a financial-services context

Steering files are where compliance lives Encode the rules the code must never break: approved dependency allowlist, data-residency and encryption standards, architecture guardrails, and regulatory constraints (the AWS guidance explicitly names things like the EU AI Act and responsible-AI principles). The agent generates against them and self-corrects on violation — controls shift from “caught in review” to “enforced during authoring.”
End-to-end traceability from intent to production Because every artifact is generated in-repo and linked — a failing test traces to a requirement traces to a user story traces to the original business intent, with audit.md recording each human decision — you get the paper trail an examiner asks for as a by-product, not a separate documentation effort.
Give risk and audit their own KPIs AWS's guidance pairs velocity metrics with opposing assurance metrics — mean time to recovery, change-failure rate, percentage of failed deployments — so a faster pipeline stays measurable. Combine with risk-based change categorization: low-risk changes flow through with automated checks; high-risk changes require named human sign-off. Without that split, mandatory human approval on everything becomes the new bottleneck.

Pros and cons

ProsCons / risks
Throughput — delivery loop drops from weeks to hours; AWS and Amazon-internal case studies cite 5–10× feature output and dramatic team-size reductions. Amplifier, not a fix — AWS is explicit: AI-DLC “amplifies existing capabilities, it does not compensate for foundational gaps.” Weak testing, slow CI/CD, or immature DevSecOps get amplified too.
Traceability — intent→story→code→test links and a timestamped decision log come for free; strong fit for audit and regulatory review. CI/CD must keep up — small reversible releases many times a day demand fast, trustworthy pipelines and evolved security tooling. Most orgs need infrastructure investment first.
Governance by construction — standards encoded as steering files are enforced while code is written, not discovered in review. Synchronous and co-located — mob elaboration assumes the team is available at the same time; hard for distributed teams and deep-focus cultures.
Smaller blast radius — bolt-sized units are individually easy to reason about, test, and roll back. Review load shifts, not disappears — humans now validate a high volume of AI output continuously. Reviewer fatigue and rubber-stamping are real failure modes; you lean on LLM reviewers plus humans.
Tool-agnostic — the reference implementation runs across Claude Code, Kiro, Q Developer, Cursor, Copilot; not a lock-in. Young and moving — published 2025, still evolving (3 phases → 5 in the reference impl). Limited independent long-run evidence; case studies are largely vendor-reported.
Keeps humans accountable — approval gates and decision logging preserve a clear line of ownership. Org-chart disruption — moving from 7-person Scrum teams to 2–3-person AI Pods is a real people change, not just a process tweak.

Adoption checklist

  • DevSecOps baseline in place first — automated tests, fast CI/CD, IaC, security scanning — before adopting, not after
  • Standards written as machine-readable steering files (security, architecture, dependency allowlist, regulatory constraints)
  • Risk-based change categorization defined — which changes auto-flow, which need named sign-off
  • Velocity KPIs paired with assurance KPIs (MTTR, change-failure rate) visible to risk and audit
  • Start with one pod, one low-risk service; run real bolts before rolling wider
  • aidlc-docs/, aidlc-state.md, and audit.md committed with the code, not kept out of version control
  • Reviewers trained for continuous in-flight validation; guard against rubber-stamping (LLM review + human review both wired in)
  • Approval gates never bypassed for speed — the gate is the control

Lesson takeaway AI-DLC is a delivery methodology, not an AWS service: AI agents produce requirements, code, tests, and IaC; humans supply intent, clear approval gates, and own the result. Sprints become bolts (hours–days), epics become units of work, solo authoring becomes mob elaboration/construction, and Scrum teams shrink to 2–3-person AI Pods. Three phases — Inception, Construction, Operation — loop continuously. You run it by adding the aidlc-workflows rules to your repo and driving bolts from your coding agent. For finance, its strengths are governance-by-steering-file and intent-to-code traceability; its risks are that it amplifies a weak DevSecOps baseline, demands fast CI/CD and synchronous teams, and is still young.
