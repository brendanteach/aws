AWS FIS & JMeter: Resilience and Load Testing

Two different questions about the same system — “does it survive failure?” (FIS) and “does it survive traffic?” (JMeter) — and how to ask both at once in a game day.

Lesson 11 covered observing your system. This lesson covers deliberately breaking it to find out what happens before a real incident does. Two tools, two different jobs:

AWS FISApache JMeter
Question it answersIf a dependency fails, does my system degrade gracefully?If traffic spikes, does my system hold up and stay fast?
What it isA managed AWS service that injects real faults into real resourcesAn open-source Java load-testing tool (not AWS-specific)
What it doesStops an EC2 instance, throttles an API, kills an ECS task, forces an RDS failover, injects latencyFires many concurrent HTTP/gRPC/JDBC requests and measures latency, throughput, and error rate
DisciplineChaos engineering / resilience testingLoad / performance testing
Azure anchor AWS FIS ≈ Azure Chaos Studio — both are managed fault-injection services with an "experiment" object, targets, and a safety/abort mechanism. JMeter has an even closer Azure mapping: Azure Load Testing is Microsoft's managed service built directly on Apache JMeter — you upload the same .jmx script either place. Knowing JMeter transfers 1:1 between clouds.

AWS FIS — Fault Injection Service

FIS is AWS's managed chaos-engineering service. Instead of writing ad-hoc scripts that kill instances (risky, untracked, easy to forget to clean up), you define an experiment template — a declarative description of what to break, for how long, and when to stop — and FIS runs it, logs it, and reverts it.

Core concepts

ConceptWhat it is
Experiment templateThe reusable definition: actions, targets, stop conditions, IAM role. Analogous to a CloudFormation template, but for chaos instead of infrastructure.
ActionThe specific fault, e.g. aws:ec2:stop-instances, aws:ecs:stop-task, aws:ssm:send-command (for CPU/memory/disk stress via SSM), aws:lambda:invocation-error, aws:rds:failover-db-cluster, aws:network:disrupt-connectivity.
TargetWhich resources the action applies to — selected by resource ARNs, tags, or a filter (e.g. "50% of instances tagged Environment=staging").
Stop conditionA CloudWatch alarm FIS watches during the experiment. If it fires, FIS automatically halts and rolls back — the single most important safety feature.
Experiment roleThe IAM role FIS assumes to perform the action — scoped narrowly to exactly the resources and API calls the experiment needs.

Sample experiment: kill a random ECS task and watch it self-heal

fis-ecs-task-stop.json
{
  "description": "Stop one running ECS task in the finapp-api service and verify auto-recovery",
  "targets": {
    "ecsTasks": {
      "resourceType": "aws:ecs:task",
      "resourceTags": { "Service": "finapp-api", "Environment": "staging" },
      "selectionMode": "COUNT(1)"
    }
  },
  "actions": {
    "stopTask": {
      "actionId": "aws:ecs:stop-task",
      "parameters": {},
      "targets": { "Tasks": "ecsTasks" }
    }
  },
  "stopConditions": [
    { "source": "aws:cloudwatch:alarm", "value": "arn:aws:cloudwatch:us-east-1:111111111111:alarm:finapp-api-5xx-rate-high" }
  ],
  "roleArn": "arn:aws:iam::111111111111:role/FisExperimentRole",
  "tags": { "purpose": "resilience-test" }
}
1

Create the experiment role with only the permissions the target action needs (e.g. ecs:StopTask, ecs:DescribeTasks) — least privilege, exactly like a Lambda execution role.

2

Create a CloudWatch alarm for the stop condition first (e.g. 5xx error rate, ALB target unhealthy count) — an experiment without a stop condition is not allowed to be safe by default.

3

Create the template: aws fis create-experiment-template --cli-input-json file://fis-ecs-task-stop.json

4

Start it: aws fis start-experiment --experiment-template-id EXTxxxxx. Watch ECS replace the killed task and CloudWatch/X-Ray for any error spike during the gap.

5

Review: did the ALB stop routing to the dead task fast enough? Did in-flight requests error? Did the new task start before the deployment's min-healthy-percent was violated? Fix what you find, then re-run to confirm.

Common FIS actions for a financial app

What you're testingFIS action
Does ECS recover if a task dies mid-request?aws:ecs:stop-task
Does the app survive an AZ or instance failure?aws:ec2:stop-instances / aws:ec2:terminate-instances
Does RDS Multi-AZ failover actually happen transparently?aws:rds:failover-db-cluster
Does the app handle a slow/unreachable downstream (payment processor, market data feed)?aws:network:disrupt-connectivity or aws:ssm:send-command running tc to add latency/packet loss
Does the Lambda-based trade confirmation path handle a broken dependency?aws:lambda:invocation-error / aws:lambda:invocation-http-integration-response (inject errors or added latency into invocations)
Does the app survive a noisy-neighbor CPU spike?aws:ssm:send-command running the SSM stress-ng document
Never run your first experiment in prod Start in staging, with a stop condition wired to a real alarm, a small blast radius (COUNT(1), one AZ, 10% of a fleet), and someone watching a dashboard live. Only promote a proven-safe experiment to a scheduled "game day" in prod, with the whole on-call team aware in advance — chaos engineering builds confidence deliberately, it isn't meant to surprise anyone.

Apache JMeter — load and performance testing

JMeter is an open-source Java application (not AWS's) that simulates many concurrent users hitting your API, measuring response time, throughput, and error rate under load. A test plan is either built in the JMeter GUI or authored as XML (.jmx) and driven from the CLI.

A minimal test plan

trade-api-loadtest.jmx (excerpt)
<ThreadGroup testname="TradeApiUsers">
  <stringProp name="ThreadGroup.num_threads">200</stringProp>   <!-- 200 virtual users -->
  <stringProp name="ThreadGroup.ramp_time">60</stringProp>    <!-- ramp up over 60s, not all at once -->
  <stringProp name="ThreadGroup.duration">300</stringProp>   <!-- run for 5 minutes -->
  <HTTPSamplerProxy testname="POST /api/trades">
    <stringProp name="HTTPSampler.domain">staging-api.finapp.com</stringProp>
    <stringProp name="HTTPSampler.path">/api/trades</stringProp>
    <stringProp name="HTTPSampler.method">POST</stringProp>
  </HTTPSamplerProxy>
</ThreadGroup>
terminal — run headless (CLI mode), never the GUI for a real test
jmeter -n -t trade-api-loadtest.jmx \
  -l results.jtl \
  -e -o report/       # -e -o generates an HTML dashboard report from the results
Never run a real load test from the GUI The JMeter GUI itself consumes significant CPU/memory rendering live results, which skews your numbers and caps how many threads you can realistically simulate from one machine. Build/debug the plan in the GUI with a handful of threads, then always execute the real test headless (-n) from the CLI, ideally from a dedicated machine or fleet, not your laptop.

Running JMeter at real scale on AWS

ApproachWhen to use it
Single EC2 instance, CLI modeSmall tests; a few hundred to a few thousand concurrent threads depending on instance size
Distributed JMeter (1 controller + N worker EC2 instances, -R flag)Need more concurrent load than one box can generate; workers run headless and report back to the controller
Distributed Load Testing on AWS (AWS Solutions Library reference architecture)Want a managed, containerized (ECS Fargate) JMeter fleet with a web console, without hand-building the distributed setup yourself
AWSMeter pluginLoad-testing AWS-native async services directly — publish to SQS, Kinesis, SNS, or Cognito from a JMeter sampler instead of only HTTP
Locust / k6 (alternatives)Prefer Python or JS test scripts over XML/GUI-authored .jmx — same load-testing role, different authoring ergonomics
Load-test from inside AWS's policy, not around it Large-scale load testing against your own AWS-hosted endpoints from your own AWS account is generally fine, but sustained high-volume testing that could look like a DDoS (especially against endpoints fronted by CloudFront/Shield, or targeting someone else's infrastructure) requires prior authorization from AWS. Review the AWS simulated-event policy before a large test, and always target a non-prod endpoint first.

Putting them together: the Game Day pattern

The two tools answer their strongest question when combined: does the system stay fast while it's also failing? A clean FIS experiment against an idle system, or a clean JMeter run against a fully healthy system, both under-test what actually happens in production — failures and traffic spikes correlate (a slow downstream causes both retries and load).

A staging game day
1. Start a JMeter test generating realistic steady-state load against staging → confirm baseline latency/error rate on the CloudWatch dashboard (Lesson 11) 2. Mid-test, start an FIS experiment: stop an ECS task, or inject RDS failover, or add downstream latency → watch the same dashboard for the failure's actual impact — not the theoretical impact 3. FIS stop condition (or a human) halts the experiment if the alarm fires 4. Let JMeter keep running after the experiment ends — measure time-to-recovery, not just impact 5. Record: peak error rate, p99 latency during the fault, time to full recovery — this becomes your resilience baseline for next quarter's game day

Production checklist

  • Every FIS experiment template has a stop condition wired to a real CloudWatch alarm — no template is allowed to run unattended without one
  • FIS experiment IAM roles scoped to the exact resources/actions the experiment needs, tagged and reviewed like any other IAM role
  • First run of any new experiment is in staging, small blast radius, with someone watching live
  • JMeter tests always run headless (-n) for real numbers; GUI is for authoring/debugging only
  • Load tests ramp up gradually (ramp_time) rather than firing all threads instantly, to avoid a self-inflicted thundering herd
  • Large-scale load tests against AWS-hosted endpoints checked against AWS's simulated-event / DDoS-testing policy before running
  • Game days scheduled with the on-call team informed in advance, and combine both tools rather than testing failure and load in isolation
  • Results captured as a baseline (p99 latency, error rate, recovery time) and compared release over release, not just checked once and forgotten

Lesson takeaway AWS FIS is a managed chaos-engineering service: define an experiment template (actions + targets + a CloudWatch-alarm stop condition + a scoped IAM role), run it against a small blast radius in staging first, and use it to prove your system actually self-heals rather than assuming it does. Apache JMeter is an open-source load-testing tool (mirrored by Azure's managed Load Testing service) that fires many concurrent requests and reports latency/throughput/error rate — author in the GUI, always execute headless (-n) at scale, distributed across EC2/Fargate for real load. Run them together in a staging game day — inject a fault mid-load-test — because real incidents combine failure and traffic, and that's the only way to find out if your system survives both at once.
