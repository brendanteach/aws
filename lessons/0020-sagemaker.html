Amazon SageMaker AI: Train, Host, and Fine-Tune Your Own Models

Bedrock hands you a model behind an API. SageMaker hands you the machine shop — to train a fraud model from scratch, or host and fine-tune an open-weight LLM that stays entirely inside your account.

Lesson 14 was Bedrock: call a foundation model over an API, no infrastructure, pay per token. That's the right tool when someone else's model already does what you need. SageMaker AI is for when it doesn't — when you need to train a model on your own labelled data (fraud, credit risk, churn), or run a specific open-weight LLM on hardware you control, or fine-tune one on proprietary data that can't leave your account.

Azure anchor SageMaker AI is Azure Machine Learning, almost feature-for-feature. SageMaker Studio ≈ the Azure ML Studio workspace; training jobs ≈ AML command jobs on compute clusters; real-time endpoints ≈ AML managed online endpoints; SageMaker Pipelines ≈ AML pipelines; Model Registry, Feature Store, and drift monitoring all have direct counterparts. JumpStart ≈ the Azure AI Foundry model catalog.
A naming note In December 2024 AWS renamed the original service to Amazon SageMaker AI (the ML platform this lesson covers) and gave the name Amazon SageMaker to a broader umbrella — a unified studio spanning data, SQL analytics, and AI, wrapping SageMaker AI together with EMR, Glue, Redshift, and Athena. When someone says “SageMaker” and means model training, they mean SageMaker AI.

What it is

A managed platform for the full ML lifecycle. The through-line: you bring the code (a training script or a container); SageMaker runs the infrastructure — provisioning instances for a job, running it, copying the result to S3, and tearing the instances down.

The core loop
Explore data in a Studio notebook → launch a training job (ephemeral GPU/CPU instances, script + data from S3) → model artifact lands in S3 → register it in the Model Registry → deploy to an endpoint → your app calls the endpoint → Model Monitor watches for drift

The component map

ComponentWhat it does
StudioThe web IDE — notebooks, job dashboards, the visual tools. Your workbench.
JumpStartA hub of pre-trained models, including open-weight LLMs (Llama, Mistral, DeepSeek, etc.). One call to deploy or fine-tune.
Training jobsEphemeral compute for training. Bring a script or container; SageMaker runs it on instances it manages, then shuts them down. Managed Spot cuts cost up to ~90%.
Automatic Model TuningHyperparameter search — runs many training jobs to find the best config.
Inference endpointsReal-time, serverless, asynchronous, or batch. Where your model actually serves predictions.
PipelinesML workflow orchestration — data prep → train → evaluate → register → deploy, as a repeatable DAG. The CI/CD of ML (Lesson 12 analogy).
Model RegistryVersioned model catalogue with an approval workflow (pending → approved → deployed).
Feature StoreA central store of computed features, shared between training and inference so they stay consistent.
Model MonitorScheduled checks for data-quality and prediction drift against a baseline.
ClarifyBias detection (pre- and post-training) and feature-attribution explainability (SHAP).
HyperPodPersistent, self-healing GPU clusters for large-scale distributed training / fine-tuning / inference of foundation models. (Standard training jobs are ephemeral; HyperPod clusters persist.)

SageMaker AI vs Bedrock — the decision

For anything AI-shaped, this is the first fork in the road.

Bedrock (Lesson 14)SageMaker AI
What you getA model behind an APIInfrastructure to build, host, and tune models
Infra to manageNone (serverless)Instances, endpoints, autoscaling (or serverless inference)
BillingPer token / per requestPer instance-hour the endpoint runs, plus training time
Model choiceThe curated Bedrock catalogueAny open-weight model, your own trained model, or a fine-tune
Custom / classical MLNo — FMs onlyYes — XGBoost, PyTorch, scikit-learn, anything
Fine-tuningLimited, managed, per-modelFull control — LoRA/QLoRA, full fine-tune, your recipe
Reach for it whenA catalogue model already does the jobYou need a custom model, a specific open model, or data/infra isolation Bedrock can't give
They compose A common finance pattern: Bedrock (or an AgentCore agent, Lesson 15) for the conversational layer, calling a SageMaker endpoint as a tool for the thing only your model can do — score this transaction for fraud, predict this customer's default probability. Same tool-Lambda pattern as Lesson 16, with the Lambda calling invoke_endpoint instead of a database.

How to use it — track A: a classical model for the app

Fraud scoring, credit risk, churn prediction, document classification — supervised learning on your labelled data. The SageMaker Python SDK is three moves: fit, deploy, predict.

train + deploy an XGBoost fraud model
import sagemaker
from sagemaker.xgboost import XGBoost

sess = sagemaker.Session()
role = "arn:aws:iam::123456789012:role/SageMakerExecutionRole"

# 1. Training job — ephemeral instance runs train.py, model goes to S3
est = XGBoost(
    entry_point="train.py",
    framework_version="1.7-1",
    instance_type="ml.m5.xlarge",
    instance_count=1,
    role=role,
    use_spot_instances=True,        # up to ~90% cheaper
    max_run=3600, max_wait=7200,
    hyperparameters={"max_depth": 6, "eta": 0.2, "num_round": 200},
)
est.fit({"train": "s3://fin-ml/fraud/train/", "validation": "s3://fin-ml/fraud/val/"})

# 2. Deploy — serverless so you pay only per request, not per idle hour
from sagemaker.serverless import ServerlessInferenceConfig
predictor = est.deploy(
    serverless_inference_config=ServerlessInferenceConfig(memory_size_in_mb=2048, max_concurrency=20),
    endpoint_name="fraud-scorer",
)

# 3. Predict (from the app: boto3 sagemaker-runtime.invoke_endpoint)
score = predictor.predict([[1, 0, 419.50, 3, 1]])   # -> P(fraud)
from the API service — no SDK, just boto3
import boto3, json
rt = boto3.client("sagemaker-runtime")

resp = rt.invoke_endpoint(
    EndpointName="fraud-scorer",
    ContentType="application/json",

How to use it — track B: host or fine-tune an LLM

When you need a specific open-weight model, or a fine-tune on data that can't go to a third-party API, JumpStart deploys it to your own endpoint in a couple of lines.

deploy an open-weight LLM to a private endpoint
from sagemaker.jumpstart.model import JumpStartModel

model = JumpStartModel(model_id="meta-textgeneration-llama-3-1-8b-instruct")
predictor = model.deploy(instance_type="ml.g5.2xlarge")   # runs in your VPC, your account

out = predictor.predict({
    "inputs": "Summarise this disclosure in two sentences: ...",
    "parameters": {"max_new_tokens": 120, "temperature": 0.2},
})

Fine-tuning is the same object with training data: JumpStartEstimator(model_id=...).fit({"training": "s3://.../instructions/"}) — JumpStart applies a LoRA recipe by default, and the result registers like any other model.

When track B beats Bedrock Choose SageMaker hosting for an LLM when: the model you want isn't in the Bedrock catalogue; you need the weights pinned to an exact version for reproducibility/audit; you have steady high volume where a reserved instance beats per-token pricing; or policy requires the model and all inference to sit inside your VPC with no shared-service data path. Otherwise Bedrock is less to run.

Inference options — pick per workload

OptionShapeUse for
Real-time endpointAlways-on instances, ms latencySynchronous app calls: score a login, a transaction, a chat turn
Serverless inferenceScales to zero, pay per requestSpiky or low/uneven traffic; dev and internal tools
Asynchronous inferenceQueue + S3 in/out, near-real-timeLarge payloads or long inferences (documents, big batches of rows)
Batch transformNo endpoint; job over a whole S3 datasetNightly scoring of every account; back-testing
The cost trap: real-time endpoints bill 24/7 Unlike Bedrock's per-token model, a real-time endpoint charges for every instance-hour it exists, busy or idle — a single ml.g5.2xlarge left running is real monthly money. Defences: prefer serverless inference for anything not constantly hit; set autoscaling (including scale-in) on real-time endpoints; use Managed Spot for training; and shut down Studio notebook instances when you leave. Put an alarm on endpoint InvocationsPerInstance so an idle endpoint gets noticed.

Finance-context callouts

Model governance is a first-class feature Use the Model Registry approval workflow so no model reaches production without a named sign-off, and attach a Model Card recording intended use, training data, evaluation results, and limitations — the documentation model-risk-management reviews (SR 11-7) will ask for.
Clarify for fair lending and adverse-action For any model influencing a credit decision, run Clarify pre-training (dataset bias across protected classes) and post-training (outcome disparity), and keep the SHAP feature-attribution reports — they are the basis for the specific-reasons an adverse-action notice must give under ECOA / Reg B.
Keep it in the VPC Run training jobs and endpoints in VPC-only mode with network isolation — no internet route, traffic to S3 / ECR over VPC endpoints. Training data, model weights, and inference traffic never leave your account. Encrypt volumes and artifacts with a customer-managed KMS key.
Drift is a risk event Wire Model Monitor to compare live inputs and predictions against the training baseline on a schedule, alarming to CloudWatch on breach. A credit or fraud model silently degrading as the world shifts is both a loss problem and a model-risk finding — you want it paged, not discovered in an audit.

Production checklist

  • Bedrock-vs-SageMaker decision made deliberately per use case — SageMaker only where a catalogue model, per-token pricing, or shared-service inference genuinely doesn't fit
  • Real-time endpoints have autoscaling with scale-in; everything else on serverless inference or batch transform
  • Managed Spot enabled for training jobs; Studio notebook instances auto-shut-down configured
  • Training jobs and endpoints in VPC-only mode with network isolation; S3/ECR via VPC endpoints
  • Volumes and model artifacts encrypted with a customer-managed KMS key
  • Every production model goes through the Model Registry approval workflow with a Model Card
  • Clarify bias + explainability reports generated and retained for any decisioning model
  • Model Monitor schedules active with CloudWatch alarms on drift
  • Training/deploy wrapped in a SageMaker Pipeline so runs are repeatable and lineage is tracked
  • Endpoint IAM scoped; CloudTrail on for the full train→register→deploy→invoke audit trail

Lesson takeaway SageMaker AI is the managed ML platform — Azure ML's counterpart: you bring a script or container, it runs the training and hosting infrastructure. Use it over Bedrock when you need a custom or classical model (fraud, credit, churn), a specific open-weight LLM, or fine-tuning and isolation Bedrock can't provide. The loop is fit → register → deploy → monitor; JumpStart makes hosting or fine-tuning an open LLM a two-liner. Watch the cost model — real-time endpoints bill 24/7, so reach for serverless inference, autoscaling, and Managed Spot. In finance: Model Registry approvals and Model Cards, Clarify for fair-lending and adverse-action, VPC-only isolation, and Model Monitor drift alarms.
