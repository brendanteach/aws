ECS Fargate: Running Your Containerized Backend

Clusters, task definitions, services, and how everything wires together

You have a VPC with private subnets, an ALB in the public subnet, and IAM roles ready to attach. Now you need something to actually run your containerized FastAPI or Node backend. That is ECS Fargate.

ECS (Elastic Container Service) is AWS's container orchestrator. Fargate is the compute engine underneath it — serverless, meaning AWS manages the underlying servers and you only define what your container needs. You never SSH into a box or patch an OS.

The Four ECS Concepts

ECS has a strict four-level hierarchy. Understand this and the rest falls into place.

Cluster
A logical boundary grouping your services and tasks. One cluster per environment (e.g. finapp-prod, finapp-staging). Does not provision servers — with Fargate it is just a namespace.
≈ Azure Container Apps Environment
Task Definition
The blueprint for your container: which Docker image, how much CPU and memory, which ports to expose, environment variables, secrets, IAM roles, and logging config. Versioned — each update creates a new revision.
≈ Azure Container App configuration / ACI container group
Task
A running instance of a Task Definition. Like a single pod in Kubernetes. Fargate provisions compute for it, runs it, and cleans up when it stops. Tasks can run one-off (a migration, a batch job) or be kept running by a Service.
≈ A single ACI container instance
Service
Keeps a desired number of Tasks running at all times. Replaces failed tasks, integrates with the ALB, handles rolling deployments, and drives auto-scaling. This is what you deploy your API as.
≈ Azure Container App (with min/max replicas)

Each Task gets its own Elastic Network Interface (ENI) — its own IP address and security group in the private subnet. This is the awsvpc network mode, mandatory for Fargate. Traffic from the ALB hits the Task directly on its private IP — no port remapping, no shared host networking.

ECR — Where Your Docker Images Live

Before ECS can run your container, the image needs to live in a registry that ECS can pull from. ECR (Elastic Container Registry) is AWS's private Docker registry — the equivalent of Azure Container Registry.

Deploy flow: code → ECR → ECS
docker build -t finapp-api:v1.8 . → docker tag finapp-api:v1.8 123456789012.dkr.ecr.us-east-1.amazonaws.com/finapp-api:v1.8 → docker push 123456789012.dkr.ecr.us-east-1.amazonaws.com/finapp-api:v1.8 → Update Task Definition to point to :v1.8 → Update ECS Service → triggers rolling deployment → ECS starts new Tasks with new image, drains old Tasks from ALB

ECR images live in the same AWS account and region as your ECS cluster. The Task Execution Role needs ecr:GetDownloadUrlForLayer, ecr:BatchGetImage, and ecr:GetAuthorizationToken — AWS provides a managed policy (AmazonECSTaskExecutionRolePolicy) that covers all of these.

The Task Definition — Annotated

The Task Definition is the most important configuration object in ECS. Here is a realistic one for the financial app backend, with the key fields explained:

{
  "family": "finapp-api",          // name; each update = new revision
  "networkMode": "awsvpc",       // mandatory for Fargate
  "requiresCompatibilities": ["FARGATE"],
  "cpu": "512",                   // 0.5 vCPU
  "memory": "1024",              // MB

  "executionRoleArn": "arn:aws:iam::…:role/finapp-execution-role",
  "taskRoleArn":      "arn:aws:iam::…:role/finapp-task-role",

  "containerDefinitions": [{
    "name":  "api",
    "image": "123456789012.dkr.ecr.us-east-1.amazonaws.com/finapp-api:v1.8",
    "portMappings": [{ "containerPort": 8080 }],

    // Plain env vars — non-sensitive config only
    "environment": [
      { "name": "APP_ENV",    "value": "production" },
      { "name": "LOG_LEVEL",  "value": "info" }
    ],

    // Secrets — injected from Secrets Manager at task startup
    "secrets": [
      {
        "name":      "DATABASE_URL",
        "valueFrom": "arn:aws:secretsmanager:…:secret:finapp/db-url"
      },
      {
        "name":      "ALPACA_API_KEY",
        "valueFrom": "arn:aws:secretsmanager:…:secret:finapp/alpaca-key"
      }
    ],

    // All logs go to CloudWatch automatically
    "logConfiguration": {
      "logDriver": "awslogs",
      "options": {
        "awslogs-group":  "/ecs/finapp-api",
        "awslogs-region": "us-east-1",
        "awslogs-stream-prefix": "api"
      }
    },

    // Health check — ECS restarts container if this fails 3x
    "healthCheck": {
      "command":     ["CMD-SHELL", "curl -f http://localhost:8080/health"],
      "interval":    30,
      "timeout":     5,
      "retries":     3,
      "startPeriod": 60   // grace period on cold start
    }
  }]
}
Secrets injection — never put credentials in "environment" The "secrets" field fetches values from Secrets Manager at task startup and injects them as environment variables inside the container. They never appear in the Task Definition JSON in plaintext, they are not visible in the AWS console, and they do not end up in CloudWatch logs. Always use "secrets" for DATABASE_URL, API keys, and any credential.

ECS Service — The Deployment Manager

The Service is the layer that makes ECS production-ready. It does three things:

1. Keeps desired count healthy

If a Task crashes, the Service starts a replacement. If an AZ goes down, it starts Tasks in the healthy AZ. You set desiredCount: 2 (minimum for HA) and the Service enforces it.

2. Rolling deployments

When you update the Task Definition (new image, new env var), the Service replaces Tasks one at a time. The default rolling strategy keeps at least 100% of desired capacity running, adding new Tasks before draining old ones — so your API has zero downtime during deployment.

Rolling deployment sequence
Service detects new Task Definition revision → Starts new Task (revision 13) in AZ-1a → registers with ALB Target Group → ALB health check passes → starts sending traffic to new Task → Deregisters old Task (revision 12) from ALB → connection draining (30s) → Stops old Task → Repeats for AZ-1b Task → Deployment complete — zero downtime

3. Auto-scaling

Attach an Application Auto Scaling policy to the Service. Common triggers:

MetricScale out whenGood for
ECS CPU utilization> 70% for 2 minutesCPU-bound workloads (computation, heavy queries)
ECS Memory utilization> 80% for 2 minutesMemory-heavy workloads (data processing)
ALB RequestCountPerTarget> 1000 req/min per taskI/O-bound APIs (most financial backends)

Set a minimum of 2 Tasks (spans 2 AZs) and a maximum based on your expected peak load and budget.

Fargate CPU and Memory Sizing

Fargate uses fixed CPU/memory combinations — unlike EC2 where you pick any instance type. Valid combinations for a backend API:

CPUMemory optionsGood for
256 (0.25 vCPU)512 MB – 2 GBLow-traffic services, background workers
512 (0.5 vCPU)1 GB – 4 GBTypical REST API — start here
1024 (1 vCPU)2 GB – 8 GBHigher-traffic API, moderate data processing
2048 (2 vCPU)4 GB – 16 GBHeavy computation, ML inference, large market data processing
Start small and measure Start at 512 CPU / 1024 MB. Check CloudWatch metrics after a week of production traffic. Scale up only if CPU consistently exceeds 60% or memory exceeds 75%. Fargate costs per vCPU-hour and GB-hour — oversizing 4 Tasks wastes money fast.

Azure → AWS Container Map

ConceptAzureAWSKey difference
Container registry ACR (Azure Container Registry) ECR (Elastic Container Registry) ECR is per-region; ACR is global. ECR integrates natively with ECS via the Execution Role.
Serverless containers Azure Container Apps ECS Fargate Very similar model. ECS requires more explicit configuration (Task Definitions, Services). Container Apps is more opinionated/managed.
Container environment Container Apps Environment ECS Cluster ECS Cluster with Fargate is just a namespace — no infra to manage.
Replica management Min/max replicas on Container App ECS Service desiredCount + Auto Scaling Same concept; ECS auto-scaling is configured separately as an Application Auto Scaling policy.
Secret injection Key Vault reference in Container App secretsmanager ARN in Task Definition "secrets" Nearly identical — both inject secrets as env vars at startup without storing them in config.
Container networking VNet integration per replica awsvpc mode — own ENI per task Each ECS Fargate task gets its own IP in the VPC — cleaner isolation than shared host networking.
Load balancing Built into Container Apps ingress Explicit ALB + Target Group ECS does not include load balancing — you wire the ALB to the Service's Target Group yourself. More control, more config.
Managed Kubernetes AKS EKS Use ECS Fargate for most web APIs. Only move to EKS if you need Kubernetes-specific features or have an existing Helm ecosystem.

Lesson takeaway ECS hierarchy: Cluster → Service → Task Definition → Task. The Service is what keeps your API running, wired to the ALB, and deployed with zero downtime. Always use Fargate (no EC2 to manage), awsvpc networking (each task its own IP), "secrets" for credentials (never "environment"), and awslogs driver (logs to CloudWatch automatically). Start at 512 CPU / 1024 MB and scale from there.
