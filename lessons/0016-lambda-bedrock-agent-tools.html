How Lambda Works With a Bedrock Agent

An agent can only talk. To do anything — look up a client balance, call your pricing API — it calls a tool, and that tool is almost always a Lambda function.

You have met the pieces separately: Lambda as your async job runner (Lesson 10), and AgentCore as the platform for running agents (Lesson 15). This lesson connects them. The core idea: the model decides what to do; your Lambda is how it gets done. The agent runtime sits in the middle, translating between the two.

Azure anchor This is the same shape as Azure AI Agent Service (or the Assistants API) calling a function tool you back with an Azure Function. The model emits a structured "call this function with these args" request; your compute runs it; the result goes back into the model's context. AWS's version wires the plumbing through IAM and a resource-based policy instead of a connection string.

The loop, end to end

One tool call inside an agent turn
User asks a question → agent runtime sends the prompt + list of available tools to the model → model replies "call get_balance with account_id=123" → runtime invokes your Lambda with those args → Lambda queries RDS, returns JSON → runtime feeds the result back to the model → model writes the final answer for the user

Your Lambda never talks to the model. It only ever receives arguments and returns a result. The model never touches your database. That separation is the whole point — and in a finance context, it is also the audit boundary.

Two ways to wire it

There are two integration paths, matching the two eras from Lesson 15. Same principle, different contract.

AgentCore Gateway (current)Bedrock Agents Classic — action groups (legacy)
How the tool is definedA tool schema (JSON: name, description, inputSchema) attached to a Gateway target pointing at your LambdaAn action group on the agent, with an OpenAPI schema or function definitions, linked to your Lambda
What the agent seesAn MCP tool over one stable endpoint — any MCP client can use itAn action the built-in orchestrator can invoke
Event your Lambda receivesA flat map of inputSchema properties → valuesAn event with actionGroup, function, parameters[], session attributes
Response shapeAny valid JSON the Gateway can parseA specific { messageVersion, response: { functionResponse: { responseBody: { TEXT: { body }}}}} envelope
Permission wiringGateway's IAM execution role granted lambda:InvokeFunction; Lambda resource policy trusts the GatewayResource-based policy on the Lambda trusting bedrock.amazonaws.com for that agent ARN

For anything new, use Gateway. The rest of this lesson works through that path.

“Do I still need an action group to let an agent call a Lambda?” — no Action groups are the Classic wiring. They are still supported and not deprecated, so keep them if you already run a Classic agent — and Classic did get lighter over time (plain function definitions instead of a full OpenAPI schema, plus return of control so your own code runs the call instead of a Lambda). But nothing new requires them. On the current path you attach a tool schema to an AgentCore Gateway target and the Lambda is exposed as an MCP tool — no action group, no per-agent binding. Rule of thumb: new build → Gateway target; recognise action groups when you meet them in existing projects, don't reach for them.

Path 1 — AgentCore Gateway (build on this)

Step by step

1

Write the Lambda that does the real work — query RDS, call an internal API, whatever the tool is for.

2

Write a tool schema — JSON with name, a good description (the model reads this to decide when to call it), and inputSchema listing the arguments and which are required.

3

Add a Gateway target pointing at the Lambda ARN, with that schema inline or from S3. The Gateway now exposes it as an MCP tool named <target>___<tool>.

4

Grant permissions — the Gateway's execution role gets lambda:InvokeFunction on your function; the function's resource policy allows the Gateway to invoke it.

5

Point your agent at the Gateway endpoint. Strands / LangGraph / your own code connects over MCP, discovers the tool, and the model can now call it.

What the Lambda actually receives

When the Gateway invokes your function, the event is just the arguments — a flat map from your inputSchema properties to the values the model chose:

# event  (for inputSchema with properties: account_id, as_of_date)
{
  "account_id": "ACC-10029",
  "as_of_date": "2026-08-27"
}

The metadata lives on the context object instead — message version, request ID, gateway ID, target ID, and the full tool name. Because the visible tool name is prefixed with the target name, you strip the prefix to learn which tool was called:

def lambda_handler(event, context):
    ctx = context.client_context.custom
    tool = ctx["bedrockAgentCoreToolName"]           # e.g. "accounts___get_balance"
    tool = tool.split("___", 1)[1]                 # -> "get_balance"

    if tool == "get_balance":
        bal = query_rds(event["account_id"], event["as_of_date"])
        return {"balance": bal, "currency": "USD"}     # any JSON the Gateway can parse

    return {"error": f"unknown tool {tool}"}

Return plain JSON. The Gateway relays it back to the agent, which feeds it to the model as the tool result.

Importing an existing Lambda? A function you already use elsewhere won't work unchanged. The event and context schema is different from a normal invoke, and you must strip the tool-name prefix yourself. Plan a small adapter layer rather than repointing a shared function.

Path 2 — Classic action groups (recognise it, don't build it)

You will see this in older projects and most tutorials. The agent has action groups; each maps to a Lambda. The event is richer and the response must follow a fixed envelope:

# response your Lambda must return for a Classic action group
{
  "messageVersion": "1.0",
  "response": {
    "actionGroup": "accounts",
    "function": "get_balance",
    "functionResponse": {
      "responseBody": { "TEXT": { "body": "Balance is 42,101.55 USD" } }
    }
  }
}

Permission-wise, Classic needs a resource-based policy on the Lambda allowing bedrock.amazonaws.com to invoke it, scoped to the specific agent ARN via the AWS:SourceArn condition — the same pattern you saw for SNS/S3 invoking Lambda in Lesson 10, just a different principal.

Zoom out — building the whole agentic system in Bedrock

This lesson is about one wire (Lambda as a tool). Here is where that wire sits in the full build. On the current AWS stack an “agentic AI system” means AgentCore (Lesson 15) hosting an agent you wrote in any framework — Strands, LangGraph, CrewAI — not the Classic managed orchestrator.

1

Enable a foundation model. In the Bedrock console, request model access (e.g. Claude). This is the reasoning engine — the part that decides what to do.

2

Write the agent. Pick a framework, write the system prompt / instructions, and decide single-agent vs. supervisor + sub-agents (Lesson 15). Keep it runnable locally first.

3

Host it on AgentCore Runtime. Package the agent and deploy it to a Runtime endpoint — serverless, session-isolated, framework-agnostic. This replaces standing up your own container/ASG for the agent loop.

4

Give it knowledge (RAG). Create a Bedrock Knowledge Base over an S3 corpus with a vector store (OpenSearch Serverless or Aurora pgvector). The agent retrieves grounding context instead of hallucinating.

5

Give it memory. Use AgentCore Memory for short-term (conversation) and long-term (across sessions) state, rather than stuffing everything into the prompt.

6

Give it tools — this lesson. Wrap each Lambda / internal API as an MCP tool via an AgentCore Gateway target with a tool schema. Gateway is the one endpoint the agent connects to for every tool.

7

Wire identity. AgentCore Identity handles inbound auth (who is allowed to call the agent) and outbound auth (the agent calling downstream APIs as that user). Identity flows through session context — never as a model-chosen argument.

8

Add guardrails. Attach a Bedrock Guardrail for denied topics, content filters, and PII redaction on both the user input and the model output.

9

Turn on observability. AgentCore Observability emits traces (model calls, tool calls, latencies) to CloudWatch. Combined with the per-tool audit log from your Lambda, this is your “which user did what” record.

10

Expose and iterate. Put the Runtime endpoint behind your app (API Gateway / your backend). Evaluate tool-calling accuracy, tune tool descriptions and the system prompt, repeat.

Classic shortcut If you don't need a custom framework, Bedrock Agents Classic does steps 2–3, 6, and part of 4–5 for you: you configure an agent with instructions, action groups, and a knowledge base in the console, and AWS runs the orchestration loop. Less control, faster to a demo. New production systems generally go the AgentCore route above.

Finance-context callouts

The Lambda is your control point, not the model Never trust the arguments blindly — the model chose them. Validate account_id against the authenticated user's entitlements inside the Lambda before you query. Pass user identity through AgentCore Identity / session context, not as a tool argument the model could fabricate.
Every tool call is an audit event Log, from inside the Lambda: the tool name, the resolved caller identity, the arguments, and a request ID from context. Combined with AgentCore Observability traces (Lesson 15), that gives you "which user, via which agent, read which account, when" — the record an examiner will ask for.
Least privilege per tool Give each tool Lambda its own IAM role with only the RDS / API access that one tool needs — exactly the Task Role discipline from Lesson 3. A compromised or mis-prompted agent can then only reach what its narrowest tool allows.

Production checklist

  • New build → AgentCore Gateway + Lambda target, not Classic action groups
  • Tool description written for the model — clear enough that it calls the right tool at the right time
  • Lambda strips the <target>___ prefix before dispatching on tool name
  • Arguments validated against the authenticated user's entitlements inside the Lambda
  • User identity taken from session/Identity context, never from a model-supplied argument
  • Each tool Lambda has its own least-privilege IAM role
  • Resource policy / Gateway invoke permission scoped to the specific Gateway or agent ARN
  • Tool name, caller, args, and request ID logged for audit on every invocation

Knowledge Check

Four questions on how Lambda connects to a Bedrock agent.

1. In the tool-call loop, what does your Lambda function directly exchange messages with?

2. With an AgentCore Gateway Lambda target, what does the event object passed to your handler contain?

3. Why must you strip a prefix from the tool name your Gateway Lambda sees?

4. A finance app tool takes account_id as an argument. Where should you enforce that the caller is allowed to see that account?

Lesson takeaway A Bedrock agent reasons; a Lambda acts. The agent runtime translates the model's "call this tool with these args" into a Lambda invoke and relays the JSON result back. On the current path, AgentCore Gateway wraps your Lambda as an MCP tool: the event is a flat map of arguments, metadata is on context, permissions are an IAM invoke grant plus a resource policy. Classic action groups do the same job with a richer event and a fixed response envelope. In finance, the Lambda — not the model — is where you validate entitlements, apply least privilege, and write the audit log.
