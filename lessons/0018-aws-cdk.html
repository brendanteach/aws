Lesson 18 · Infrastructure as Code

AWS CDK: Infrastructure as Real Code

Define your AWS stack in Python (or TypeScript) with loops, functions, and type-checking — the CDK compiles it down to CloudFormation and deploys it.

Lesson 9 taught Terraform: infrastructure described in HCL, a purpose-built configuration language. The AWS Cloud Development Kit (CDK) takes a different bet — you write infrastructure in a general-purpose programming language you already know, and it synthesizes a CloudFormation template that AWS then deploys. Same goal (declarative, version-controlled, repeatable infra), different authoring experience.

This lesson shows you how to use it end to end: the mental model, the project layout, the six commands you'll actually run, and a real stack that provisions the DynamoDB + Lambda tool from Lesson 17.

Azure anchor CloudFormation is Azure's ARM / Bicep — a declarative template the platform reconciles. The CDK is the layer above it, like using Azure Bicep modules plus the imperative power of Pulumi or the Azure SDK: you write code, it emits the template. If you've written Bicep modules with parameters and loops, CDK constructs will feel familiar — just in Python instead of a DSL.

The mental model

Three nested concepts, plus one compile step.

ConceptWhat it is
AppThe root of your CDK program. Contains one or more stacks. This is the app.py entry point.
StackA unit of deployment = one CloudFormation stack. Maps to one account + region. You deploy, update, and delete a stack as a whole.
ConstructA reusable building block representing one or more AWS resources. Constructs nest inside stacks and inside each other.
synthThe compile step: cdk synth runs your code and writes CloudFormation JSON/YAML to cdk.out/.
What happens on deploy
Your Python code → cdk synth runs it → CloudFormation template in cdk.out/ → assets (Lambda zips, Docker images) uploaded to the bootstrap bucket/ECR → cdk deploy hands the template to CloudFormation → CloudFormation creates / updates / deletes resources to match

Construct levels — L1, L2, L3

LevelNamingWhat you get
L1 (CFN resources)CfnBucket, CfnTableA raw 1:1 mapping of a CloudFormation resource. Every property, no defaults, no help. Escape hatch when an L2 doesn't exist yet.
L2 (curated)Bucket, Table, FunctionSensible defaults, helper methods, and grants (table.grant_read_data(fn)). This is what you use 95% of the time.
L3 (patterns)ApplicationLoadBalancedFargateServiceA whole architecture in one construct — wires many resources together for a common use case.
Grants are the reason to use L2 Instead of hand-writing an IAM policy JSON document (Lesson 3) and attaching it, you call table.grant_read_data(my_function). The CDK generates the least-privilege policy — exact ARNs, exact actions — and attaches it to the function's role. Get the wiring right in one line, no copy-pasted policy blobs.

Setup — one time per machine, one time per account

1

Install the CLI. npm install -g aws-cdk (the CLI is Node-based even if your project is Python). Check with cdk --version.

2

Init the project. mkdir finapp-infra && cd finapp-infra && cdk init app --language python. Then python -m venv .venv, activate it, pip install -r requirements.txt.

3

Bootstrap the account/region. cdk bootstrap aws://123456789012/us-east-1. This creates a small CDKToolkit stack — an S3 bucket and ECR repo for assets, plus deploy roles. Do it once per account+region combination.

Writing a stack

Here is a real stack: the DynamoDB table and tool Lambda from Lesson 17, wired together with a grant.

finapp_infra/agent_tools_stack.py
from aws_cdk import Stack, Duration, RemovalPolicy
from aws_cdk import aws_dynamodb as dynamodb
from aws_cdk import aws_lambda as _lambda
from constructs import Construct


class AgentToolsStack(Stack):
    def __init__(self, scope: Construct, cid: str, **kwargs):
        super().__init__(scope, cid, **kwargs)

        # L2 DynamoDB table — on-demand, PK+SK, encryption on by default
        table = dynamodb.Table(self, "Customers",
            partition_key=dynamodb.Attribute(name="pk", type=dynamodb.AttributeType.STRING),
            sort_key=dynamodb.Attribute(name="sk", type=dynamodb.AttributeType.STRING),
            billing_mode=dynamodb.BillingMode.PAY_PER_REQUEST,
            point_in_time_recovery=True,
            removal_policy=RemovalPolicy.RETAIN,   # keep the data if the stack is deleted
        )

        # L2 Lambda — code bundled from a local dir and uploaded automatically
        fn = _lambda.Function(self, "GetCustomerProfile",
            runtime=_lambda.Runtime.PYTHON_3_13,
            handler="handler.lambda_handler",
            code=_lambda.Code.from_asset("lambda/get_customer_profile"),
            timeout=Duration.seconds(10),
            environment={"TABLE_NAME": table.table_name},
        )

        # The grant — generates a least-privilege IAM policy and attaches it
        table.grant_read_data(fn)
app.py
import aws_cdk as cdk
from finapp_infra.agent_tools_stack import AgentToolsStack

app = cdk.App()

# One stack per environment — different account/region, same code
AgentToolsStack(app, "AgentTools-staging",
    env=cdk.Environment(account="111111111111", region="us-east-1"))
AgentToolsStack(app, "AgentTools-prod",
    env=cdk.Environment(account="222222222222", region="us-east-1"))

app.synth()
“Real code” means real code Need five identical queues with different names? A for loop. Need a value computed from another? A function. Want to stop a footgun? Raise an exception in your construct. Config that Terraform expresses with count, for_each, and locals, CDK expresses with the language itself — and your editor autocompletes every property and flags typos before synth.

The workflow — six commands

cdk bootstrap  — one-time per account/region; creates the asset bucket + deploy roles
cdk synth  — run your code, emit the CloudFormation template to cdk.out/. Catches code errors early.
cdk diff  — compare your code against what's deployed. Read this every time before deploy.
cdk deploy  — upload assets, submit the template, watch CloudFormation apply it. --require-approval prompts on IAM changes.
cdk watch  — dev-loop mode: redeploy automatically on file save (hotswaps Lambda code without a full CFN update)
cdk destroy  — delete the stack. Resources with RETAIN removal policy survive.

A typical change

1

Edit the stack code, add the new resource or property.

2

cdk diff AgentTools-staging — confirm the change list is exactly what you expect (watch for unintended replacements).

3

cdk deploy AgentTools-staging — apply to staging, test.

4

In CI, on merge to main: cdk diff as a PR comment, then cdk deploy AgentTools-prod --require-approval never after approval.

Testing infrastructure

Because it's code, you can unit-test the synthesized template with assertions — catch a missing encryption flag or an over-broad policy before it ships.

tests/unit/test_agent_tools_stack.py
from aws_cdk import App
from aws_cdk.assertions import Template, Match
from finapp_infra.agent_tools_stack import AgentToolsStack

def test_table_has_pitr_and_retain():
    template = Template.from_stack(AgentToolsStack(App(), "t"))

    template.has_resource_properties("AWS::DynamoDB::Table", {
        "PointInTimeRecoverySpecification": {"PointInTimeRecoveryEnabled": True},
    })
    template.has_resource("AWS::DynamoDB::Table", {"DeletionPolicy": "Retain"})

def test_lambda_cannot_write_the_table():
    template = Template.from_stack(AgentToolsStack(App(), "t"))
    # grant_read_data must NOT include PutItem / UpdateItem / DeleteItem
    template.resource_count_is("AWS::IAM::Policy", 1)

CDK vs Terraform vs raw CloudFormation

Authoring languagePython, TS, Java, Go, C#HCLJSON / YAML
Logic (loops, conditionals)The language itselfcount, for_each, functionsVery limited
StateCloudFormation manages itYou manage a state file (Lesson 9)AWS manages it
Multi-cloudAWS onlyAny providerAWS only

Lambda/Docker assetsBundled & uploaded automaticallyManual (zip, S3, hash) or extra modulesManual
Drift & importWeaker story than TerraformStrong (import, plan shows drift)Basic drift detection

Rule of thumb: CDK if your team is app developers, the stack is AWS-only, and you lean on Lambda / containers / lots of IAM wiring. Terraform if you need multi-cloud, a strong import/drift story, or an ops team already fluent in HCL. They can coexist — CDK for the app-adjacent stacks, Terraform for the network/account foundation.

Finance-context callouts

Removal policy on every stateful resource Databases, buckets, and log groups holding customer or audit data get removal_policy=RETAIN (and RETAIN_ON_UPDATE_OR_DELETE for buckets). A fat-fingered cdk destroy or a logical-ID change then can't take the data with it. Pair with deletion_protection where the resource supports it.
cdk diff is a control, not a courtesy Require it as a reviewed artifact in the deploy pipeline — posted on the PR, read by a second person — before any prod deploy. The dangerous line in a diff is a replacement ([-/+]): CloudFormation will delete and recreate the resource, which for a database or queue means data loss or an outage.
Policy-as-tests with cdk-nag Add the cdk-nag AwsSolutions pack to your app and synth fails if a resource violates a rule — unencrypted storage, a wildcard IAM action, a public bucket, missing log retention. It's the CDK equivalent of a compliance checklist, enforced at build time instead of found in an audit.

Production checklist

  • One stack per environment, parameterised by env account/region — never branching on a string inside the stack for prod vs staging differences that matter
  • L2 constructs by default; L1 (Cfn*) only as a documented escape hatch
  • IAM wired with .grant_*() methods, not hand-written policy documents
  • removal_policy=RETAIN + deletion protection on every database, bucket, and audit log group
  • cdk diff generated in CI and reviewed before every prod deploy; replacements ([-/+]) treated as blocking until understood
  • Assertion tests on the synthesized template for the invariants that matter (encryption, PITR, no wildcard policies)
  • cdk-nag AwsSolutions rules wired into synth
  • Bootstrap stack version kept current; deploy role permissions scoped, not AdministratorAccess, once past initial setup
  • Stateful resources (RDS, DynamoDB) in a separate long-lived stack from fast-changing compute, to limit blast radius

Knowledge Check

Four questions on using the AWS CDK.

1. What does cdk synth actually produce?

2. You want a Lambda to read (but not write) a DynamoDB table. What's the idiomatic CDK way?

3. In a cdk diff before a prod deploy, why is a resource marked [-/+] (replacement) the line to stop on?

4. When does cdk bootstrap need to be run?

Lesson takeaway The CDK lets you author AWS infrastructure in Python or TypeScript: an App holds Stacks (one CloudFormation stack each), which hold Constructs (L2 curated ones by default). cdk synth compiles code to a template; cdk diff shows the change (stop on replacements); cdk deploy applies it via CloudFormation; cdk bootstrap is a one-time per account/region setup. The payoff over Terraform is language-native logic, autocompletion, testable templates, automatic Lambda/Docker asset bundling, and .grant_*() methods that write least-privilege IAM for you. In finance: RETAIN removal policies, reviewed diffs as a deploy gate, and cdk-nag rules enforced at build time.
