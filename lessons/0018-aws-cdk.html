Lesson 18 · Infrastructure as Code

AWS CDK: Infrastructure as Real Code

Define your AWS stack in TypeScript (or Python) with loops, functions, and type-checking — the CDK compiles it down to CloudFormation and deploys it.

Lesson 9 taught Terraform: infrastructure described in HCL, a purpose-built configuration language. The AWS Cloud Development Kit (CDK) takes a different bet — you write infrastructure in a general-purpose programming language you already know, and it synthesizes a CloudFormation template that AWS then deploys. Same goal (declarative, version-controlled, repeatable infra), different authoring experience.

This lesson shows you how to use it end to end: the mental model, the project layout, the six commands you'll actually run, and a real stack that provisions the DynamoDB + Lambda tool from Lesson 17.

Language support Every example here is TypeScript — CDK's original and primary language; the CLI itself runs on Node.js regardless of which language your stack is written in. If your team runs a Python stack instead, cdk init app --language python gives you the identical App/Stack/Construct model and the same synth/diff/deploy/destroy commands; only the syntax and package manager (pip vs. npm) differ. Java, C#, and Go are supported too.
Azure anchor CloudFormation is Azure's ARM / Bicep — a declarative template the platform reconciles. The CDK is the layer above it, like using Azure Bicep modules plus the imperative power of Pulumi or the Azure SDK: you write code, it emits the template. If you've written Bicep modules with parameters and loops, CDK constructs will feel familiar — just in TypeScript instead of a DSL.

The mental model

Three nested concepts, plus one compile step.

ConceptWhat it is
AppThe root of your CDK program. Contains one or more stacks. This is the bin/*.ts entry point.
StackA unit of deployment = one CloudFormation stack. Maps to one account + region. You deploy, update, and delete a stack as a whole.
ConstructA reusable building block representing one or more AWS resources. Constructs nest inside stacks and inside each other.
synthThe compile step: cdk synth runs your code and writes CloudFormation JSON/YAML to cdk.out/. Pure local execution — no AWS account, credentials, or bootstrap required.
What happens on deploy
Your TypeScript code → cdk synth runs it → CloudFormation template in cdk.out/ → assets (Lambda zips, Docker images) uploaded to the bootstrap bucket/ECR → cdk deploy hands the template to CloudFormation → CloudFormation creates / updates / deletes resources to match

CDK and Lambda are not the same thing

Worth stating plainly, because the two get used together constantly in this course: Lambda (Lesson 21) is a compute service — it actually runs your function code when an event fires, and it exists independently of how it was created. CDK is an infrastructure-as-code tool — you write code describing AWS resources, and CDK compiles it into a CloudFormation template that provisions them. A Lambda function is just one of the ~200+ resource types (alongside S3 buckets, DynamoDB tables, VPCs, ECS services…) that a CDK stack can declare.

CDK doesn't run your Lambda, and Lambda doesn't need CDK to exist — the exact same function could be created via the Console, the CLI, Terraform, SAM, or raw CloudFormation. A CDK app can also deploy zero Lambdas at all. Treat them as two separate lessons on purpose: one is how AWS runs your code, the other is how you declare and ship AWS resources.

Where CDK actually lives

Three different places — and bootstrapping (below) only matters for the third one.

WhereWhat's thereWhen it appears
Your local repoYour actual CDK source code (.ts files) — the real source of truth, tracked in gitAlways — it's just code
Local cdk.out/The compiled CloudFormation template(s), produced by cdk synthEvery synth — pure local compilation, no AWS contact at all
AWS (S3 + ECR + CloudFormation)The deployed stack: assets in the bootstrap S3 bucket/ECR, the template and stack state in CloudFormationOnly on cdk deploy

So you do not need to bootstrap before you start developing. You can write a stack, run cdk synth repeatedly, and run unit/assertion tests all day with zero AWS account involvement. Bootstrap only becomes required the moment you run your first cdk deploy into a given account+region — see the callout further down for exactly what it creates and why.

Construct levels — L1, L2, L3

LevelNamingWhat you get
L1 (CFN resources)CfnBucket, CfnTableA raw 1:1 mapping of a CloudFormation resource. Every property, no defaults, no help. Escape hatch when an L2 doesn't exist yet.
L2 (curated)Bucket, Table, FunctionSensible defaults, helper methods, and grants (table.grant_read_data(fn)). This is what you use 95% of the time.
L3 (patterns)ApplicationLoadBalancedFargateServiceA whole architecture in one construct — wires many resources together for a common use case.
Grants are the reason to use L2 Instead of hand-writing an IAM policy JSON document (Lesson 3) and attaching it, you call table.grant_read_data(my_function). The CDK generates the least-privilege policy — exact ARNs, exact actions — and attaches it to the function's role. Get the wiring right in one line, no copy-pasted policy blobs.

Setup — one time per machine, one time per account

1

Install the CLI. npm install -g aws-cdk. Check with cdk --version.

2

Init the project. mkdir finapp-infra && cd finapp-infra && cdk init app --language typescript. This also runs npm install for you (aws-cdk-lib, constructs, typescript, jest are added to package.json).

3

Bootstrap the account/region. cdk bootstrap aws://123456789012/us-east-1. This creates a small CDKToolkit stack — an S3 bucket and ECR repo for assets, plus deploy roles. Do it once per account+region combination.

Bootstrap is required, not optional — but only before you deploy cdk deploy needs the bootstrap bucket to exist so it has somewhere to upload assets (Lambda zips, Docker images) before handing the template to CloudFormation. Skip it, and your first cdk deploy into a fresh account/region fails outright, telling you to bootstrap. It's a one-time setup per account+region — not per stack, not per deploy — so once it's done you never think about it again until AWS ships a newer bootstrap template version. cdk synth, by contrast, needs none of this: it never touches AWS at all (see below), so you can write and validate stacks long before you ever bootstrap anything.

Writing a stack

Here is a real stack: the DynamoDB table and tool Lambda from Lesson 17, wired together with a grant.

lib/agent-tools-stack.ts
import { Stack, StackProps, Duration, RemovalPolicy } from 'aws-cdk-lib';
import * as dynamodb from 'aws-cdk-lib/aws-dynamodb';
import * as lambda from 'aws-cdk-lib/aws-lambda';
import { Construct } from 'constructs';

export class AgentToolsStack extends Stack {
  constructor(scope: Construct, id: string, props?: StackProps) {
    super(scope, id, props);

    // L2 DynamoDB table — on-demand, PK+SK, encryption on by default
    const table = new dynamodb.Table(this, 'Customers', {
      partitionKey: { name: 'pk', type: dynamodb.AttributeType.STRING },
      sortKey: { name: 'sk', type: dynamodb.AttributeType.STRING },
      billingMode: dynamodb.BillingMode.PAY_PER_REQUEST,
      pointInTimeRecovery: true,
      removalPolicy: RemovalPolicy.RETAIN,   // keep the data if the stack is deleted
    });

    // L2 Lambda — code bundled from a local dir and uploaded automatically
    const fn = new lambda.Function(this, 'GetCustomerProfile', {
      runtime: lambda.Runtime.NODEJS_20_X,
      handler: 'index.handler',
      code: lambda.Code.fromAsset('lambda/get-customer-profile'),
      timeout: Duration.seconds(10),
      environment: { TABLE_NAME: table.tableName },
    });

    // The grant — generates a least-privilege IAM policy and attaches it
    table.grantReadData(fn);
  }
}

import * as cdk from 'aws-cdk-lib';
import { AgentToolsStack } from '../lib/agent-tools-stack';

const app = new cdk.App();

// One stack per environment — different account/region, same code
new AgentToolsStack(app, 'AgentTools-staging', {
  env: { account: '111111111111', region: 'us-east-1' },
});
new AgentToolsStack(app, 'AgentTools-prod', {
  env: { account: '222222222222', region: 'us-east-1' },
});

app.synth();
The Lambda's runtime is still a separate choice from the CDK's language This stack's runtime: lambda.Runtime.NODEJS_20_X handler is the same index.handler shown in Lesson 21, so both the infra and the function here are TypeScript/Node end to end. That's a choice, not a requirement — CDK's authoring language and a Lambda's execution runtime are independent decisions, and this exact stack would deploy just as well pointing runtime at PYTHON_3_13 (or Java, or Go) with a handler written in that language instead.
“Real code” means real code Need five identical queues with different names? A for loop. Need a value computed from another? A function. Want to stop a footgun? Raise an exception in your construct. Config that Terraform expresses with count, for_each, and locals, CDK expresses with the language itself — and your editor autocompletes every property and flags typos before synth.

The workflow — six commands

cdk bootstrap  — one-time per account/region; creates the asset bucket + deploy roles
cdk synth  — run your code, emit the CloudFormation template to cdk.out/. Catches code errors early.
cdk diff  — compare your code against what's deployed. Read this every time before deploy.
cdk deploy  — upload assets, submit the template, watch CloudFormation apply it. --require-approval prompts on IAM changes.
cdk watch  — dev-loop mode: redeploy automatically on file save (hotswaps Lambda code without a full CFN update)
cdk destroy  — delete the stack. Resources with RETAIN removal policy survive.
What cdk deploy actually does It's the one command in this list that changes real infrastructure, and it's really CloudFormation doing the work under the hood, in four steps: (1) synth your code, exactly like cdk synth; (2) upload any assets — Lambda zips, Docker images — to the bootstrap S3 bucket/ECR, keyed by content hash, so unchanged assets aren't re-uploaded; (3) submit the template to CloudFormation as a change set — a preview of exactly what CloudFormation intends to add/modify/remove, which is the same computation cdk diff shows you, just executed instead of only displayed; (4) execute the change set — CloudFormation calls the underlying service APIs (CreateTable, CreateFunction, etc.) to reconcile real resources to match, and if any step fails, it automatically rolls back the whole stack to its last good state. --require-approval broadening (the default) pauses for a manual yes/no before executing a change set that adds IAM or security-group permissions; --require-approval never skips that prompt, which is what an automated CI pipeline needs since nobody is there to type "y".
What cdk destroy actually does It synths your stack one more time, then calls CloudFormation's DeleteStack and walks every resource in reverse dependency order — deleting the Lambda before the table it reads from, for instance, mirroring the order they were created in. For each resource, CloudFormation checks the DeletionPolicy that your CDK removalPolicy compiled down to: DESTROY (CDK's default) maps to Delete — the resource is actually deleted, data and all; RemovalPolicy.RETAIN maps to Retain — the resource is detached from the stack but left running, orphaned, still billing; RemovalPolicy.SNAPSHOT (RDS, EBS) takes a final snapshot first, then deletes. This is exactly what the [-/+] replacement callouts elsewhere in this lesson are warning about — a replacement runs this same delete-then-recreate path on a single resource mid-deploy, not just on a full destroy.
What cdk watch actually does It's a dev-loop shortcut, not a fifth deployment mechanism: cdk watch deploys once normally, then monitors the files listed under "watch" in cdk.json (defaults to everything except cdk.out, node_modules, and similar) and, on save, tries a hotswap first — pushing just the changed Lambda code, Step Functions definition, or ECS task image straight to the running resource via its own service API (UpdateFunctionCode, etc.), skipping CloudFormation entirely. That's what makes it fast: seconds, not a full stack update. If the change isn't hotswap-eligible — a new resource, a changed IAM policy, a renamed construct — it falls back to a normal cdk deploy change set instead.
Hotswap is a dev tool, not a deploy path A hotswap update bypasses CloudFormation, which means the stack's recorded template goes out of sync with what's actually running until the next real cdk deploy reconciles them — and it skips the safety checks CloudFormation would otherwise run (rollback on failure, drift tracking, `cdk diff` visibility). Use cdk watch for your own dev-loop iteration only; never in CI, and never as how staging or prod gets updated.

A typical change

1

Edit the stack code, add the new resource or property.

2

cdk diff AgentTools-staging — confirm the change list is exactly what you expect (watch for unintended replacements).

3

cdk deploy AgentTools-staging — apply to staging, test.

4

In CI, on merge to main: cdk diff as a PR comment, then cdk deploy AgentTools-prod --require-approval never after approval.

Testing infrastructure

Because it's code, you can unit-test the synthesized template with assertions — catch a missing encryption flag or an over-broad policy before it ships. This is a different kind of test than unit-testing a Lambda handler (Lesson 21): there's nothing to mock here, because a CDK stack makes no AWS calls of its own — you're asserting on the template it produces, not on any runtime behavior.

LanguageTest runnerAssertion library
TypeScriptJest (scaffolded automatically by cdk init --language typescript)aws-cdk-lib/assertions — the Template class
Pythonpytestaws_cdk.assertions — the same Template class, Python API

Either way, you instantiate the stack in-memory and call Template.fromStack(...), which does its own in-process synth of just that stack — no CLI, no AWS account, no network. Then you assert on the resulting template: does this resource exist, does it have this property, is this policy scoped the way you expect.

cdk synth does not run your tests They're two separate steps. cdk synth just renders your bin/*.ts entry point to CloudFormation — it happens to run your TypeScript, so it'll surface an import error or a bad construct property, but it never discovers or executes test/*.test.ts. The assertion tests below are run separately with Jest (scaffolded automatically by cdk init --language typescript); each one calls Template.fromStack(...) itself, which does its own in-process synth of that one stack. Wire both into CI as independent commands — cdk synth catches code errors, npm test catches the specific invariants (encryption, PITR, IAM) you assert on. 
test/agent-tools-stack.test.ts
import { App } from 'aws-cdk-lib';
import { Template } from 'aws-cdk-lib/assertions';
import { AgentToolsStack } from '../lib/agent-tools-stack';

test('table has PITR and RETAIN', () => {
  const template = Template.fromStack(new AgentToolsStack(new App(), 't'));

  template.hasResourceProperties('AWS::DynamoDB::Table', {
    PointInTimeRecoverySpecification: { PointInTimeRecoveryEnabled: true },
  });
  template.hasResource('AWS::DynamoDB::Table', { DeletionPolicy: 'Retain' });
});

test('lambda cannot write the table', () => {
  const template = Template.fromStack(new AgentToolsStack(new App(), 't'));
  // grantReadData must NOT include PutItem / UpdateItem / DeleteItem
  template.resourceCountIs('AWS::IAM::Policy', 1);
});

Validating a stack before you deploy

Nothing here requires an AWS account. Run all four before you ever run cdk deploy:

1

cdk synth — runs your TypeScript and renders CloudFormation. Catches import errors, bad construct props, and typos. If it doesn't synth, it can't deploy.

2

Assertion tests (shown above) — assert on the synthesized template: encryption on, PITR on, exact IAM actions granted. Runs in CI on every PR, no AWS calls.

3

cdk-nag — a library of compliance rules (AwsSolutions, HIPAA, PCI-DSS packs) that runs during synth and fails the build on violations, with a suppression mechanism for accepted exceptions.

4

cdk diff — the only one of the four that talks to AWS (read-only, to compare against the deployed stack). Run against staging before every prod deploy; treat any [-/+] replacement as blocking until explained.

What cdk diff actually does It's a template-to-template comparison, not a live-resource scan: cdk diff synths your code locally, fetches the currently deployed CloudFormation template for that named stack (one read-only API call), and diffs the two resource-by-resource — additions, removals, property changes, and replacements. It reads the deployed template, never any actual resource's live state, so it will not notice if someone hand-edited a resource in the Console outside of CloudFormation (that's a different feature, CloudFormation's own drift detection). The output uses CloudFormation's own change-set symbols: [+] add, [-] remove, [~] modify in place, and the one to stop on, [-/+] — a replacement, where CloudFormation destroys the resource and creates a new one because an immutable property changed.
What cdk-nag actually is cdk-nag is a third-party (now AWS-labs-maintained) open-source npm/pip package — not a built-in CDK feature. Mechanically, it's a CDK Aspect: a visitor that CDK calls once for every construct in your app's tree during synth. Each rule pack (AwsSolutionsChecks, HIPAA, PCI-DSS, NIST 800-53…) is just a set of functions that inspect a construct's synthesized properties and raise an error if one violates the rule — an S3 bucket with no encryption, an IAM policy with a wildcard action, a log group with no retention set. Because it hooks into synth itself, a violation fails the build immediately, in the same place and at the same speed as any other synth error — no separate scan step, no extra CI job. 
bin/finapp-infra.ts — wiring cdk-nag in
import * as cdk from 'aws-cdk-lib';
import { AwsSolutionsChecks, NagSuppressions } from 'cdk-nag';
import { AgentToolsStack } from '../lib/agent-tools-stack';

const app = new cdk.App();
const stack = new AgentToolsStack(app, 'AgentTools-staging', {
  env: { account: '111111111111', region: 'us-east-1' },
});

// Fails `cdk synth` if any resource violates the AwsSolutions rule pack
cdk.Aspects.of(app).add(new AwsSolutionsChecks({ verbose: true }));

// Documented, reviewed exception — not a silent bypass
NagSuppressions.addResourceSuppressions(stack, [
  { id: 'AwsSolutions-IAM4', reason: 'Lambda basic execution managed policy is acceptable here' },
]);

app.synth();
Type-check it too CDK stacks are ordinary TypeScript (or Python) — run tsc --noEmit and your linter (eslint) over the infra package in CI exactly as you would application code. A wrong property name on a construct is a typo the type checker catches before synth even runs.

Running it on your laptop with mocks — no AWS account touched

Four layers, from “fully offline” to “emulates real AWS locally.” Use the cheapest one that answers your question.

1. Unit-test the Lambda handler with aws-sdk-client-mock

This tests your business logic, decoupled entirely from CDK — fastest feedback loop, runs in plain jest (see Lesson 21 for the full local-testing ladder this handler is used in).

lambda/get-customer-profile/index.ts
import { DynamoDBClient } from '@aws-sdk/client-dynamodb';
import { DynamoDBDocumentClient, GetCommand } from '@aws-sdk/lib-dynamodb';

const ddb = DynamoDBDocumentClient.from(new DynamoDBClient({}));

export const handler = async (event: { customer_id: string }) => {
  const { Item } = await ddb.send(new GetCommand({
    TableName: process.env.TABLE_NAME,
    Key: { pk: `CUST#${event.customer_id}` },
  }));
  return Item;
};
lambda/get-customer-profile/index.test.ts
import { mockClient } from 'aws-sdk-client-mock';
import { DynamoDBDocumentClient, GetCommand } from '@aws-sdk/lib-dynamodb';
import { handler } from './index';

const ddbMock = mockClient(DynamoDBDocumentClient);
beforeEach(() => ddbMock.reset());

test('returns the profile for a known customer', async () => {
  ddbMock.on(GetCommand, { TableName: 'Customers', Key: { pk: 'CUST#1' } })
    .resolves({ Item: { pk: 'CUST#1', name: 'Ada' } });

  const result = await handler({ customer_id: '1' });

  expect(result?.name).toBe('Ada');
});
No CDK, no CloudFormation, no Docker aws-sdk-client-mock intercepts the SDK v3 client in-process to fake the DynamoDB API. This test runs in milliseconds and is exactly what you'd write for a non-Lambda function — the CDK-specific piece (does the real IAM grant work, is the table configured right) is covered separately by the assertion tests on the synthesized template shown earlier.

2. Invoke the real handler locally with SAM CLI

What SAM CLI actually is The AWS Serverless Application Model CLI is a separate AWS tool, not part of CDK — its own install, its own command (sam), originally built to work with hand-written SAM/CloudFormation templates. The reason it shows up here: sam local invoke runs a Lambda in an actual Docker container matching the real Lambda runtime image, purely for local testing — it never deploys anything. And conveniently, it can read CDK's own synthesized output directly (any cdk.out/*.template.json), so you get real-container local testing without writing a separate SAM template or adopting SAM as your deploy tool. CDK still does all the actual deploying via cdk deploy; SAM CLI's only job in this lesson is running the Lambda locally.

SAM CLI reads CDK's own synthesized output (it understands cdk.out/ directly) and runs your Lambda in a Docker container using the actual runtime image — closer to production than aws-sdk-client-mock, because your code executes for real, just against a local or mocked endpoint.

terminal
cdk synth                                          # writes cdk.out/AgentTools-staging.template.json
sam local invoke GetCustomerProfile \
  -t cdk.out/AgentTools-staging.template.json \
  -e events/get-customer.json \
  --docker-network host                            # so the container can reach LocalStack on localhost

3. Deploy the whole stack to LocalStack

LocalStack runs an AWS-API-compatible server in a Docker container on your laptop; cdklocal (the aws-cdk-local npm package) is a drop-in wrapper for the CDK CLI that points bootstrap/deploy/destroy at it instead of real AWS. You get a genuinely deployed stack — a real (emulated) DynamoDB table, a real (emulated) Lambda invoked over the network — for $0 and no account.

terminal
docker run -d --name localstack -p 4566:4566 localstack/localstack

npm install -g aws-cdk-local aws-cdk
cdklocal bootstrap aws://000000000000/us-east-1     # LocalStack accepts any account id
cdklocal deploy AgentTools-staging

# hit the emulated table directly to sanity-check
aws --endpoint-url=http://localhost:4566 dynamodb scan --table-name Customers
LocalStack is a fidelity trade, not a guarantee The community edition emulates the common APIs well but not every service, IAM enforcement nuance, or quota behavior — it catches wiring bugs (wrong table name, malformed event, broken handler logic) cheaply, but a clean LocalStack deploy is not proof a real AWS deploy will behave identically. Keep a real staging account (step 4 of the six-command workflow above) as the final gate before prod.

The full pipeline — local, DEV, and QA

Putting the pieces above in order answers a question worth asking directly: unit tests are what you can run with zero AWS environment, but they're not the only thing you can run locally — LocalStack integration-tests real, deployed resources talking to each other, still with no real account. And no, you can't fully close the gap to a real AWS environment from local alone: LocalStack doesn't enforce IAM the way real AWS does and doesn't emulate every service perfectly, so a DEV account is still where you validate the last 10% — real IAM enforcement, real latency, real service quirks. The goal of everything before DEV is to make sure DEV is only ever validating that 10%, not re-discovering a typo.

A clean LocalStack run is a pre-DEV gate, not a DEV replacement Never read "it deployed and passed integration tests on LocalStack" as "ready for QA." The first real signal that something is QA-ready is a passing DEV deploy plus its own integration tests against real AWS — LocalStack's job is to make that DEV deploy boring by catching everything cheaper beforehand.

Finance-context callouts

Removal policy on every stateful resource Databases, buckets, and log groups holding customer or audit data get removal_policy=RETAIN (and RETAIN_ON_UPDATE_OR_DELETE for buckets). A fat-fingered cdk destroy or a logical-ID change then can't take the data with it. Pair with deletion_protection where the resource supports it.
cdk diff is a control, not a courtesy Require it as a reviewed artifact in the deploy pipeline — posted on the PR, read by a second person — before any prod deploy. The dangerous line in a diff is a replacement ([-/+]): CloudFormation will delete and recreate the resource, which for a database or queue means data loss or an outage.
Policy-as-tests with cdk-nag Add the cdk-nag AwsSolutions pack to your app and synth fails if a resource violates a rule — unencrypted storage, a wildcard IAM action, a public bucket, missing log retention. It's the CDK equivalent of a compliance checklist, enforced at build time instead of found in an audit.

Production checklist

  • One stack per environment, parameterised by env account/region — never branching on a string inside the stack for prod vs staging differences that matter
  • L2 constructs by default; L1 (Cfn*) only as a documented escape hatch
  • IAM wired with .grant_*() methods, not hand-written policy documents
  • removal_policy=RETAIN + deletion protection on every database, bucket, and audit log group
  • cdk diff generated in CI and reviewed before every prod deploy; replacements ([-/+]) treated as blocking until understood
  • Assertion tests on the synthesized template for the invariants that matter (encryption, PITR, no wildcard policies)
  • cdk-nag AwsSolutions rules wired into synth; suppressions documented with a reason, never silent
  • Lambda handler logic unit-tested with aws-sdk-client-mock, independent of the CDK stack that deploys it
  • Bootstrap stack version kept current; deploy role permissions scoped, not AdministratorAccess, once past initial setup
  • Stateful resources (RDS, DynamoDB) in a separate long-lived stack from fast-changing compute, to limit blast radius
  • Secrets and DB passwords referenced from Secrets Manager / SSM Parameter Store at deploy time — never hard-coded in stack code
  • The same built artifact promoted local → DEV → QA → prod — never rebuilt per environment — with LocalStack treated as a pre-DEV gate, not a DEV/QA replacement

Knowledge Check

Four questions on using the AWS CDK.

1. What does cdk synth actually produce?

2. You want a Lambda to read (but not write) a DynamoDB table. What's the idiomatic CDK way?

3. In a cdk diff before a prod deploy, why is a resource marked [-/+] (replacement) the line to stop on?

4. When does cdk bootstrap need to be run?

Lesson takeaway The CDK lets you author AWS infrastructure in TypeScript or Python: an App holds Stacks (one CloudFormation stack each), which hold Constructs (L2 curated ones by default). cdk synth compiles code to a template; cdk diff shows the change (stop on replacements); cdk deploy applies it via CloudFormation; cdk bootstrap is a one-time per account/region setup. The payoff over Terraform is language-native logic, autocompletion, testable templates, automatic Lambda/Docker asset bundling, and .grant_*() methods that write least-privilege IAM for you. In finance: RETAIN removal policies, reviewed diffs as a deploy gate, and cdk-nag rules enforced at build time.
