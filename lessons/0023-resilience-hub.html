Lesson 23 · Resilience & Performance

AWS Resilience Hub

Turn “we think we could survive an AZ outage” into a measured score, a gap list, and the FIS experiments that prove it — before an incident does.

Lesson 22 covered proving resilience by deliberately injecting failure with FIS. This lesson covers the step before that: Resilience Hub assesses your architecture against a target recovery objective, tells you exactly which resources fall short, and can generate the FIS experiments and CloudWatch alarms to close the gap and then verify it.

What Resilience Hub actually does

You point it at an application (a CloudFormation stack, Terraform state, an EKS/App Runner resource, or a plain resource group), set a target for how fast and how completely it must recover from different kinds of disruption, and it runs a static assessment of the architecture — Multi-AZ or not, backups configured or not, auto-scaling present or not — and produces a resiliency score plus specific, actionable recommendations.

Azure anchor There is no exact one-to-one Azure service. The closest partial matches are the Azure Well-Architected Framework Review (a scored assessment, but manual/consultative rather than continuously computed from live resource config) and Azure Business Continuity Center for tracking DR/backup posture. Resilience Hub is closer to a hybrid of both, automated: it reads your actual deployed resource graph and computes the score itself.

Core concepts

ConceptWhat it is
ApplicationThe set of resources Resilience Hub assesses together — imported from a CloudFormation stack, Terraform state file, an App Runner/EKS resource, or resource-group tags.
Resiliency PolicyYour target RTO (Recovery Time Objective — how long you can be down) and RPO (Recovery Point Objective — how much data you can afford to lose), set per disruption type: Software, Hardware, Availability Zone, and Region.
AssessmentA run that compares the application's actual configuration against the policy and produces a score, per-resource findings, and recommendations.
Resiliency ScoreA 0–100% score, broken down per disruption type, showing how close the architecture is to meeting the policy.
RecommendationsConcrete fixes — "enable Multi-AZ on this RDS instance," "add a DLQ to this queue" — each with an estimated score improvement, plus ready-to-run alarm (CloudWatch) and test (FIS experiment template) recommendations.
Drift detectionRe-checks the deployed application against the last assessed version and flags when infrastructure has changed in a way that could have silently lowered the score.

RTO and RPO, concretely

RTO
Recovery Time Objective
RPO
Recovery Point Objective

RTO answers "how long can the trading API be down before it's unacceptable?" RPO answers "how much data can we lose — the last 5 minutes of trades, or none?" These aren't abstract SRE jargon in a financial app: they are usually already written down somewhere as a compliance or business-continuity requirement. Resilience Hub's whole job is turning that written-down number into a measured, continuously re-checked score against real infrastructure.

resiliency-policy.json
{
  "policyName": "finapp-trading-api-tier1",
  "tier": "MissionCritical",
  "policy": {
    "Software":          { "rtoInSecs": 300,   "rpoInSecs": 0 },
    "Hardware":          { "rtoInSecs": 300,   "rpoInSecs": 0 },
    "AZ":                { "rtoInSecs": 600,   "rpoInSecs": 60 },
    "Region":            { "rtoInSecs": 14400, "rpoInSecs": 900 }
  }
}
The policy is your DR tier, written as numbers Zero RPO for a Software/Hardware disruption means "we cannot lose a single confirmed trade to a process crash" — which pushes you toward synchronous replication and idempotent retries, not just backups. A non-zero AZ RPO of 60 seconds means "async replication lag up to a minute is acceptable" during an AZ failure. Write the policy to match what your compliance/business-continuity plan already promises, not what's convenient to hit — a policy your infrastructure passes but that's looser than the real requirement is a false sense of safety.

Running an assessment end to end

1

Define the application — import resources from your existing CloudFormation stack or Terraform state. No re-modeling: Resilience Hub reads what's already deployed.

2

Attach (or create) a resiliency policy with your RTO/RPO targets per disruption type.

3

Publish the app version and run an assessment. Resilience Hub statically analyzes the resource graph: is RDS Multi-AZ? Does the SQS queue have a DLQ? Is the ASG spread across AZs? Is there a backup plan?

4

Read the score and recommendations, ranked by impact. Each recommendation names the exact resource and the exact config change.

5

Implement the top recommendations in your CDK/Terraform code (Lessons 9 & 18), redeploy, and re-run the assessment to confirm the score moved.

6

Generate and run the recommended FIS experiments (Lesson 22) to prove the fix actually works under real failure, not just on paper.

terminal — CLI walkthrough
aws resiliencehub create-app \
  --name finapp-trading-api \
  --description "Trading API and its dependencies"

aws resiliencehub import-resources-to-draft-app-version \
  --app-arn arn:aws:resiliencehub:us-east-1:111111111111:app/finapp-trading-api \
  --source-arns arn:aws:cloudformation:us-east-1:111111111111:stack/finapp-api/abc123

aws resiliencehub create-resiliency-policy --cli-input-json file://resiliency-policy.json

aws resiliencehub publish-app-version --app-arn arn:aws:resiliencehub:us-east-1:111111111111:app/finapp-trading-api

aws resiliencehub create-app-assessment \
  --app-arn arn:aws:resiliencehub:us-east-1:111111111111:app/finapp-trading-api \
  --app-version release-2 \
  --assessment-name q3-assessment

aws resiliencehub list-app-assessment-resource-drifts --app-arn ... --assessment-arn ...

What a recommendation looks like

ResourceFindingRecommendation
RDS PostgreSQL instanceSingle-AZ — an AZ failure exceeds the RTO/RPO in the policyEnable Multi-AZ; estimated score impact: +12%
Trade-events SQS queueNo DLQ configuredAdd a dead-letter queue with maxReceiveCount — generates a ready-to-deploy CloudFormation snippet
ECS serviceTasks not spread across multiple AZsSet subnet placement to span ≥2 AZs; also generates a suggested FIS experiment to verify it
No CloudWatch alarm foundNo alarm covers RDS failover eventsGenerates a CloudFormation template for the missing alarm, ready to add to your stack
Resilience Hub closes the loop with FIS and CloudWatch This is the piece that ties directly to Lesson 22: recommendations aren't just prose. Resilience Hub can generate a ready-to-import FIS experiment template for exactly the failure mode it flagged (e.g. "stop this RDS instance and confirm failover completes within RTO") and a CloudWatch alarm CloudFormation snippet for gaps in monitoring coverage. You implement the infra fix, then run the generated experiment to get evidence, not just a static score, that the fix works.

Drift detection

An assessment is a snapshot. Someone changes an Auto Scaling Group's subnets, a teammate removes a DLQ "temporarily" to debug something, or a Terraform apply reverts a Multi-AZ setting — and your actual resilience posture silently degrades below what was last measured. Resilience Hub's drift detection re-compares the live resource graph against the assessed version and flags exactly this, so a resilience regression shows up as an alert, not as a postmortem finding.

Production checklist

  • A resiliency policy exists per application tier, with RTO/RPO numbers taken from an actual documented DR/compliance requirement — not chosen to make the score look good
  • Applications imported from the same CloudFormation/Terraform source of truth already used to deploy them — never a manually re-modeled duplicate that drifts from reality
  • Assessments re-run after every significant infrastructure change, not just once at launch
  • Top recommendations tracked as backlog items with an owner, not left as a dashboard nobody revisits
  • Generated FIS experiment templates actually run (Lesson 22), in staging first, to convert "the score says this should work" into "we watched it work"
  • Drift detection alerts routed to the same on-call channel as CloudWatch alarms — a resilience regression is an operational issue, not a quarterly review item
  • Score and RTO/RPO compliance tracked over time (release over release), not treated as a one-time certification

Lesson takeaway Resilience Hub turns a written RTO/RPO requirement into a measured resiliency policy checked against your real, deployed resource graph (imported from CloudFormation/Terraform — never manually re-modeled). Publishing an app version and running an assessment produces a scored, per-resource list of gaps with concrete fixes, and can generate the exact FIS experiment templates (Lesson 22) and CloudWatch alarms (Lesson 11) needed to close and then prove each gap. Drift detection keeps that posture honest over time as infrastructure keeps changing after the last assessment. Together with FIS and JMeter, this is the "measure it, break it on purpose, prove it recovered" loop a financial app's DR story should run on — not a document reviewed once a year.
