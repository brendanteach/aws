Amazon Bedrock: Generative AI Architecture

Adding an AI feature to your financial app — how Bedrock plugs into the three-tier architecture you already built

Everything so far — VPC, IAM, ECS/RDS, S3 — builds a conventional three-tier app. This lesson adds a new tier: a way for your backend to call a large language model without running any AI infrastructure yourself. Amazon Bedrock is AWS's managed access point to foundation models (Claude, Amazon Nova, Llama, and others) — you call an API, AWS runs the model.

Azure anchor Bedrock is AWS's counterpart to Azure OpenAI Service (now part of Azure AI Foundry). Both are a managed API in front of foundation models, both bill per token, both sit behind your cloud's standard IAM and networking rather than requiring a public API key. The difference: Bedrock is model-agnostic by design — one API shape (the Converse API) works across Anthropic, Amazon, Meta, and other providers' models, so switching models is a config change, not a rewrite.

The Core Idea: Bedrock Is Just Another AWS Service Call

This is the single tangible win for this lesson: your ECS/Lambda backend calls Bedrock exactly the way it already calls S3 or RDS — over the AWS SDK, authenticated by the task's IAM role, no API key to manage or leak.

That's the whole shape. Everything else in this lesson — Guardrails, Knowledge Bases, Agents — are optional layers you add around this one call as your use case grows.

Calling Bedrock From Your Backend

1
Scope the IAM role to specific models

Same principle as Lesson 3: least privilege. Grant InvokeModel on the exact model ARNs you use, not bedrock:*.

{
  "Effect": "Allow",
  "Action": ["bedrock:InvokeModel"],
  "Resource": [
    "arn:aws:bedrock:us-east-1::foundation-model/anthropic.claude-sonnet-5-*"
  ]
}
2
Call the Converse API from your backend

One shape works across model providers — swapping modelId is the only change needed to try a different model.

import { BedrockRuntimeClient, ConverseCommand } from "@aws-sdk/client-bedrock-runtime";

const client = new BedrockRuntimeClient({ region: "us-east-1" });

async function askAssistant(question) {
  const response = await client.send(new ConverseCommand({
    modelId: "anthropic.claude-sonnet-5",
    messages: [{ role: "user", content: [{ text: question }] }],
  }));
  return response.output.message.content[0].text;
}
3
Keep the call inside your VPC

Add a VPC interface endpoint for bedrock-runtime in your private subnets (same mechanism as any AWS PrivateLink endpoint) so the ECS task never needs a NAT gateway route to reach Bedrock.

Growing Beyond a Single Call

A raw model call only knows what's in the prompt. Real finance use cases — "summarize this client's last 6 statements," "answer questions about our fee schedule" — need the model grounded in your own data. Bedrock adds two managed layers for this, both optional and both add-ons to the same base call:

LayerWhat it doesWhen you'd add it
Knowledge Bases (RAG) Bedrock indexes your documents (from S3) into a vector store and retrieves relevant chunks before calling the model — the managed version of retrieval-augmented generation. The assistant needs to answer from your app's own documents — statements, policies, KYC files in S3 (Lesson 13) — not just general knowledge.
Guardrails A policy layer between your app and any model: content filters, PII redaction, and topic denial rules applied consistently regardless of which model is behind it. Any customer-facing finance feature — filtering PII in prompts/responses and blocking off-topic or unsafe requests is close to a hard requirement, not a nice-to-have.
Request flow once Knowledge Bases + Guardrails are added
User question → Guardrails (check input) → Knowledge Base retrieval (find relevant S3 docs) → Model (answer using retrieved context) → Guardrails (check output) → Response

These are deliberately out of scope for this lesson — they're the natural next lesson once the base invocation pattern above is solid.

Finance context: why Bedrock over calling a model API directly Three things matter for a regulated app: encryption in transit and at rest by default; private connectivity via VPC PrivateLink so prompts and responses never traverse the public internet; and — critically — your data is not shared with model providers and is not used to train the underlying models. Bedrock also integrates with CloudTrail, so every model invocation is an auditable API call like any other AWS action, not a call to an untracked third-party endpoint.

Production Checklist

  • IAM role scoped to specific model ARNs via bedrock:InvokeModel, not a wildcard
  • VPC interface endpoint for bedrock-runtime so calls stay off the public internet
  • CloudTrail logging enabled for Bedrock API activity (Lesson 3/11 pattern)
  • Guardrails applied before shipping anything customer-facing — PII redaction and topic filters, not an afterthought
  • Model invocation logs (metadata, optionally full request/response) configured to land in S3 or CloudWatch for audit
  • Cost controlled with request-level token limits — Bedrock bills per input/output token, unlike your flat-rate ECS/RDS costs

Lesson takeaway Bedrock is Azure OpenAI Service's counterpart: a managed, model-agnostic API your backend calls through the same IAM role it already uses for S3 and RDS, kept private with a VPC endpoint. That one call — ConverseCommand against a scoped model ARN — is the whole foundation. Knowledge Bases (grounding answers in your S3 documents) and Guardrails (PII/content filtering) are the next layers once a real feature needs them.
