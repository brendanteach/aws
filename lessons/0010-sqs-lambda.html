SQS + Lambda: Async Processing for a Financial App

Decoupling work from the API response — trade alerts, emails, and batch jobs

Your ECS API handles HTTP requests synchronously — a user submits a trade, the API records it in RDS, and responds immediately. But some work should not happen in that response cycle: sending a confirmation email, running compliance checks, generating a PDF statement. These are slow, failure-prone, or bursty. SQS + Lambda handles them asynchronously — your API enqueues a message and moves on, Lambda processes it in the background.

The Two Services

SQS (Simple Queue Service) is a managed message queue. Your ECS API puts a message in the queue. Lambda reads from the queue and processes it. If Lambda fails, the message stays in the queue and is retried. They are decoupled — SQS buffers the work between producer and consumer.

Lambda is a serverless function: you upload code, and AWS runs it in response to an event. With SQS as the trigger, Lambda polls the queue automatically and invokes your function with a batch of messages. You pay only for execution time — no idle cost.

Azure analogy: Azure Service Bus + Azure Functions SQS ≈ Azure Service Bus Queue (Standard tier). Lambda ≈ Azure Functions (Consumption plan). The pattern is identical: queue decouples producer from consumer, function is triggered by the queue. Key difference: Azure Service Bus has more messaging features (topics, sessions, dead-lettering via portal); SQS is simpler but sufficient for most patterns.

Four Async Jobs in the Financial App

Trade Confirmation Email
ECS records trade → SQS message → Lambda → SES (email)
Don't block the API response waiting for SES. Retry on email failure without losing the trade.
Price Alert Notification
EventBridge (1 min) → Lambda → check prices → SQS → alert Lambda → push notification
Price checks run on a schedule, not per-request. Lambda cost: fractions of a cent per run.
Statement PDF Generation
ECS → SQS message → Lambda → generate PDF → S3 → notify user
PDFs can take seconds and use significant memory. Offloading avoids ECS timeout and resource contention.
Audit Log Archival
ECS writes events → SQS FIFO → Lambda → append to audit DynamoDB table
FIFO queue preserves event order. Audit trail must be complete and ordered for compliance.

Standard Queue vs FIFO Queue

Default choice
Standard Queue
· At-least-once delivery (may duplicate)
· Best-effort ordering (not guaranteed)
· Nearly unlimited throughput
· Use for: emails, notifications, reports
· Your Lambda must be idempotent
When order matters
FIFO Queue
· Exactly-once delivery (deduplication)
· Strict first-in-first-out ordering
· Max 3,000 messages/sec
· Use for: audit logs, trade event streams
· Name must end in .fifo

The SQS → Lambda Flow

Trade confirmation — end to end
ECS API handles POST /api/trades → Records trade in RDS (synchronous — user waits for this) → Puts message on SQS queue: { "trade_id": "uuid", "user_id": "uuid", "symbol": "AAPL", "quantity": 10 } → Returns HTTP 200 to user # API response time: ~50ms Meanwhile, asynchronously: SQS holds the message (up to 14 days if not processed) → Lambda polls the queue every 20 seconds (managed by AWS) → Lambda receives batch of 1–10 messages → For each message: Fetch trade details from RDS Fetch user email from RDS Call SES to send confirmation email → Delete message from queue (success) → On failure: message becomes visible again after visibility timeout → retry → After 3 failed retries → message moves to Dead-Letter Queue (DLQ)

Three Critical SQS Settings

SettingWhat it doesValue for financial app
Visibility Timeout How long a message is hidden from other consumers while being processed. If Lambda crashes before finishing, the message reappears after this timeout. Set to 6× your Lambda timeout. If Lambda runs up to 30s, set 3 minutes. Prevents duplicate processing during long runs.
Message Retention How long SQS keeps unprocessed messages before deleting them. 14 days (maximum). For financial events, you want the longest window to investigate failures.
Dead-Letter Queue (DLQ) A separate queue where messages go after N failed processing attempts. Essential for debugging — failed messages don't disappear. Always configure. Set maxReceiveCount = 3. Alert on DLQ depth > 0 via CloudWatch alarm.
Finance requirement: always have a DLQ and alarm on it A failed trade confirmation email sitting silently in a DLQ is a compliance gap. Configure a CloudWatch alarm on ApproximateNumberOfMessagesVisible on the DLQ — any message landing there should page your on-call engineer immediately. Never let messages silently disappear.

Lambda Function — Anatomy

trade_confirmation_handler.py
import json, boto3

ses = boto3.client("ses")

def handler(event, context):
    # Lambda receives a batch of SQS messages
    failures = []

    for record in event["Records"]:
        try:
            body = json.loads(record["body"])
            send_confirmation_email(body)
        except Exception as e:
            # Report this record as failed — SQS will retry it
            failures.append({"itemIdentifier": record["messageId"]})

    # Return failed message IDs — only these go back to queue
    # Successful messages are auto-deleted. Partial batch failure!
    return {"batchItemFailures": failures}


def send_confirmation_email(body):
    ses.send_email(
        Source="noreply@finapp.com",
        Destination={"ToAddresses": [body["user_email"]]},
        Message={
            "Subject": {"Data": f"Trade confirmed: {body['symbol']}"},
            "Body":    {"Text": {"Data": f"You bought {body['quantity']} shares of {body['symbol']}."}}
        }
    )
Return batchItemFailures — not a single exception If your Lambda raises an exception, the entire batch is retried — including messages that already succeeded. Use batchItemFailures to report only the specific records that failed. Successful records in the batch are deleted from the queue; failed ones are retried individually. This requires ReportBatchItemFailures enabled on the Event Source Mapping.

Lambda Configuration for Financial Processing

Terraform — Lambda + SQS trigger
resource "aws_lambda_function" "trade_confirmation" {
  function_name = "finapp-trade-confirmation"
  runtime       = "python3.12"
  handler       = "trade_confirmation_handler.handler"
  role          = aws_iam_role.lambda_exec.arn

  memory_size = 256    # MB — tune based on CloudWatch metrics
  timeout     = 30     # seconds — set DLQ visibility timeout to 6× this

  environment {
    variables = {
      "SES_REGION" = "us-east-1"
    }
  }
}

resource "aws_lambda_event_source_mapping" "sqs_trigger" {
  event_source_arn                   = aws_sqs_queue.trade_events.arn
  function_name                      = aws_lambda_function.trade_confirmation.arn
  batch_size                         = 10    # process up to 10 messages per invocation
  function_response_types            = ["ReportBatchItemFailures"]
  maximum_batching_window_in_seconds = 5
}

Lambda IAM Execution Role

Lambda needs its own IAM execution role — separate from ECS roles. Least privilege applies here too.

Lambda Execution Role needs:
  sqs:ReceiveMessage       # poll the queue
  sqs:DeleteMessage        # remove processed messages
  sqs:GetQueueAttributes   # read queue metadata
  ses:SendEmail            # send confirmation emails
  logs:CreateLogGroup      # write to CloudWatch Logs
  logs:PutLogEvents        # (required for all Lambdas)

ECS Task Role additionally needs:
  sqs:SendMessage          # put messages onto the queue
  on Resource: specific queue ARN only

Lesson takeaway SQS decouples slow/failure-prone work from your API response. Your ECS API puts a message on the queue and returns immediately — Lambda processes it in the background. Always configure a DLQ and alarm on it. Set visibility timeout = 6× Lambda timeout. Use batchItemFailures to retry only failed messages in a batch. Use FIFO queues when event order matters (audit logs). Lambda only needs sqs:ReceiveMessage + sqs:DeleteMessage — nothing else.
