RDS: Managed PostgreSQL for a Financial App

Multi-AZ, encryption, backups, and connecting from ECS Fargate

Your ECS containers are running in private subnets. Now they need a database. For a financial web application, the choice is Amazon RDS for PostgreSQL — a fully managed relational database with automated backups, Multi-AZ high availability, and encryption built in.

RDS handles the tasks that would otherwise consume engineering time: OS patching, engine upgrades, backup scheduling, and failover. You focus on schema design and query performance.

Multi-AZ: The Most Important RDS Setting

Multi-AZ runs a synchronous standby replica in a second Availability Zone. Every write to the primary is confirmed on the standby before it is acknowledged to your application. If the primary fails — hardware failure, AZ outage, OS crash — RDS automatically promotes the standby in approximately 60 seconds. Your application reconnects using the same endpoint; nothing else changes.

Finance requirement: Multi-AZ is non-negotiable A single-AZ RDS instance is a single point of failure. For a financial application handling trade orders or user balances, even a few minutes of downtime during a market event is unacceptable. Always enable Multi-AZ in production. The standby does not serve reads — it exists only for failover.
Azure analogy: Zone-redundant HA on Azure Database for PostgreSQL Flexible Server Identical concept — a synchronous standby in a second zone, automatic failover, same connection string. AWS calls it "Multi-AZ". Azure calls it "Zone-redundant high availability". The ~60 second failover time is also similar.

The DB Subnet Group

Before creating an RDS instance, you define a DB Subnet Group — a collection of subnets (in different AZs) where RDS is allowed to place instances. RDS picks which subnet to use; you just ensure the group spans at least two AZs.

DB Subnet Group: finapp-db-subnets
  Subnet 1: subnet-aaa  (10.0.5.0/24, us-east-1a)
  Subnet 2: subnet-bbb  (10.0.6.0/24, us-east-1b)

These are the DB-tier private subnets from Lesson 2.
No internet route. Reachable only from ECS security group.

Encryption

RDS encryption covers two surfaces — and both are required for any financial application:

SurfaceMechanismEnabled how
At rest AES-256 via AWS KMS. Encrypts storage, automated backups, read replicas, and snapshots. Enable at creation — cannot be added later. Use a customer-managed KMS key (not the default AWS key) for financial data.
In transit TLS 1.2/1.3 between your application and RDS. Set rds.force_ssl=1 in the Parameter Group. Your app must connect with sslmode=require in the connection string.
Encryption at rest must be enabled at creation You cannot encrypt an existing unencrypted RDS instance in place. The only path is: take a snapshot → copy the snapshot with encryption enabled → restore a new instance from the encrypted snapshot. Do it right the first time.

Automated Backups and Point-in-Time Recovery

RDS automatically takes a daily snapshot of your database and continuously archives transaction logs to S3. Together, these enable Point-in-Time Recovery (PITR) — restoring your database to any second within the backup retention window.

SettingRecommended valueWhy
Backup retention 14–35 days Financial regulations often require 90-day audit trails — longer retention means less gap to fill from other sources
Backup window Off-peak hours (e.g. 02:00–03:00 UTC) Brief I/O increase during snapshot; avoid market hours
Maintenance window Weekend off-peak Minor version patches and parameter changes apply here — may cause a brief Multi-AZ failover
Delete protection Enabled Prevents accidental terraform destroy or console click from wiping your production database

Connecting from ECS Fargate

Three things must align for your ECS container to reach RDS: the security group chain, the secret in Secrets Manager, and the connection string in your app.

1. Security group rule (from Lesson 2)

RDS Security Group inbound rule:
  Port:   5432
  Source: sg-ecs-tasks  ← the ECS task security group ID, not a CIDR

2. Store the connection string in Secrets Manager

Secret name: finapp/db-url
Secret value:
  "postgresql://finapp_user:PASSWORD@finapp-db.cluster-xyz.us-east-1.rds.amazonaws.com:5432/finapp?sslmode=require"

Note: sslmode=require — enforce TLS in the connection string itself

3. Reference in the Task Definition (from Lesson 4)

"secrets": [
  {
    "name":      "DATABASE_URL",
    "valueFrom": "arn:aws:secretsmanager:us-east-1:123456789012:secret:finapp/db-url"
  }
]

Your Python or Node app reads os.environ["DATABASE_URL"] as usual. The entire credential chain — from ECS startup to RDS authentication — is handled by AWS with no plaintext values in config files or environment variable dumps.

RDS Proxy — Connection Pooling for ECS

PostgreSQL maintains one OS process per connection. An ECS Service with 10 tasks, each running an app with a 5-connection pool, opens 50 connections to RDS. As the Service auto-scales to 50 tasks, that becomes 250 connections — which strains RDS and consumes memory.

RDS Proxy sits between your ECS tasks and RDS, maintaining a warm pool of connections to the database and multiplexing your application connections across it. Your tasks connect to the Proxy endpoint instead of the RDS endpoint directly.

With RDS Proxy
ECS Task 1 ─┐ ECS Task 2 ─┤ → RDS Proxy → RDS Primary ECS Task 3 ─┤ (10 connections (keeps a fixed, small ECS Task 4 ─┘ from 50 tasks) pool to the DB) Benefits for Fargate: · Scales to many tasks without exhausting DB connections · Faster failover during Multi-AZ promotion (Proxy retries, tasks don't see the blip) · Integrates with IAM authentication and Secrets Manager natively
RDS Proxy costs ~$0.015/vCPU-hour per RDS instance For a db.t3.medium (2 vCPU) running 24/7, that is about $22/month extra. Worth it at scale; optional for small traffic. Enable it from the start — retrofitting is easy, but connection exhaustion in production is painful.

RDS Instance Sizing

RDS instance classes follow the same family naming as EC2. For a financial app starting out:

InstancevCPURAMGood for
db.t3.micro 2 1 GB Dev / staging only — burstable CPU, too small for production
db.t3.medium 2 4 GB Production starting point for low-to-moderate traffic financial APIs
db.r6g.large 2 16 GB Memory-optimized — better for larger working sets (market data, time series)
db.r6g.xlarge 4 32 GB Higher-traffic financial apps; significant portion of DB fits in RAM

Start with db.t3.medium. Monitor CPU utilization, FreeableMemory, and DatabaseConnections in CloudWatch. Upsize only when you see sustained pressure — RDS instance changes on Multi-AZ cause a brief failover, not downtime.

Production Checklist

  • Multi-AZ enabled (not single-AZ)
  • Encryption at rest enabled at creation, using a customer-managed KMS key
  • rds.force_ssl=1 in Parameter Group; sslmode=require in connection string
  • RDS in DB Subnet Group spanning 2+ AZs, no internet route
  • Security group allows port 5432 only from ECS security group (by SG ID)
  • Connection string stored in Secrets Manager, referenced in ECS Task Definition "secrets"
  • Automated backups enabled, retention ≥ 14 days
  • Delete protection enabled
  • CloudWatch alarms on: CPU > 80%, FreeableMemory < 500 MB, DatabaseConnections > 80% of max
  • RDS Proxy configured if ECS service scales beyond ~5 tasks

Knowledge Check

Four questions on RDS.

1. Your Multi-AZ RDS primary instance fails at 2 AM. What happens?

2. You enabled encryption on an RDS instance after it was created — but the console says encryption is still disabled. Why?

3. Why should ECS tasks connect to the RDS Proxy endpoint rather than the RDS instance endpoint directly?

4. Your ECS container's DATABASE_URL must include sslmode=require. Where do you enforce this on the RDS side so that connections without TLS are rejected?

Lesson takeaway RDS PostgreSQL with Multi-AZ (automatic ~60s failover), encryption at rest via KMS (set at creation), forced TLS (Parameter Group + connection string), and Secrets Manager for credentials is the complete data layer for a production financial app. Use RDS Proxy once your ECS service scales beyond a handful of tasks. The DB Subnet Group places RDS in private subnets with no internet route — the only inbound traffic allowed is from the ECS security group on port 5432.
