Frontend on AWS: S3 + CloudFront + ACM

Hosting your SPA with a custom domain, HTTPS, CDN caching, and WAF — no servers

Your ECS backend is running, your RDS database is secured. The last tier is the frontend — the React or Vue SPA your users load in their browsers. On AWS, this is three services working together: S3 stores the built files, CloudFront delivers them globally with caching and TLS, and ACM provides the free TLS certificate.

There are no servers to manage. A deployment is: build → upload to S3 → invalidate CloudFront cache.

Single-domain trick: one CloudFront for both frontend and API The path-based routing above lets you serve app.finapp.com (frontend) and app.finapp.com/api/* (backend) from the same domain. This avoids CORS entirely — your React app calls /api/trades not api.finapp.com/trades. The same CloudFront distribution routes each path to the right origin.

Step-by-Step Setup

1
Create the S3 bucket — with public access fully blocked

The bucket is not a public website. CloudFront reads it privately using Origin Access Control. Block all public access settings — this is the correct modern pattern.

# Bucket name matches your app; region matches your ECS/RDS region
Bucket name:         finapp-frontend
Block public access: ALL FOUR checkboxes enabled
Versioning:          optional (useful for rollbacks)
Encryption:          SSE-S3 (default) is fine for a public SPA
2
Request a TLS certificate in ACM — in us-east-1

This is the single most common gotcha for Azure users moving to AWS. CloudFront is a global service and it only reads ACM certificates from the us-east-1 region, regardless of where your other resources live. If your app is in us-west-2, your ACM cert for CloudFront must still be in us-east-1.

Region:          us-east-1  ← mandatory, even if your app is elsewhere
Domain names:    app.finapp.com
                 *.finapp.com   (wildcard covers all subdomains)
Validation:      DNS validation (ACM gives you a CNAME to add to Route 53)

ACM auto-renews the cert — you never touch it again after validation.
3
Create the CloudFront distribution

Key settings that matter:

Origin:                S3 bucket (not the "website endpoint" URL)
Origin Access Control:  Create new OAC → CloudFront signs requests to S3
Viewer protocol:       Redirect HTTP to HTTPS
Allowed HTTP methods:  GET, HEAD (frontend is read-only)
Cache policy:          CachingOptimized for /assets/*
                       CachingDisabled for /api/*
Compress objects:      Yes (gzip + brotli, free)
Alternate domain:      app.finapp.com
SSL certificate:       Select the ACM cert from us-east-1
Security policy:       TLSv1.2_2021 (drops old TLS 1.0/1.1)
Default root object:   index.html
4
Attach the OAC bucket policy to S3

After creating the CloudFront distribution with OAC, AWS shows you a bucket policy to copy. Apply it to the S3 bucket. This is the only permission that allows CloudFront to read the bucket — nothing else can.

{
  "Statement": [{
    "Effect":    "Allow",
    "Principal": { "Service": "cloudfront.amazonaws.com" },
    "Action":    "s3:GetObject",
    "Resource":  "arn:aws:s3:::finapp-frontend/*",
    "Condition": {
      "StringEquals": {
        "AWS:SourceArn": "arn:aws:cloudfront::123456789012:distribution/EDFDVBD6EXAMPLE"
      }
    }
  }]
}
// The Condition locks this to YOUR specific distribution — not all CloudFront
5
Create Route 53 Alias record

Alias records are AWS-specific — they resolve to a CloudFront distribution without a CNAME (which means they work at the apex domain, e.g. finapp.com as well as app.finapp.com).

Record type: A (Alias)
Name:        app.finapp.com
Alias to:    CloudFront distribution → d1234abcd.cloudfront.net

The SPA Deep-Link Problem — and the Fix

This trips up almost every team on their first CloudFront SPA deployment. React Router, Vue Router, and similar libraries handle navigation client-side — routes like /dashboard or /trades/123 exist only in the browser, not as real files in S3.

When a user pastes https://app.finapp.com/dashboard directly into a new tab, CloudFront asks S3 for /dashboard. S3 returns a 404 (no such file). The user sees an error page instead of your app.

Fix: CloudFront Custom Error Response

Error code:        403 and 404
Response page:     /index.html
Response code:     200

Both 403 and 404 — S3 returns 403 (not 404) when OAC is used and the file doesn't exist.
Returning 200 with index.html lets React Router take over and render the right component.
Azure analogy: Azure Static Web Apps handles this automatically Azure Static Web Apps has built-in SPA routing support — you define routes in a staticwebapp.config.json. CloudFront requires the custom error response workaround above. It is a two-minute fix once you know about it, but it is invisible until a user tries to share a deep link.

Deploying a New Frontend Version

CloudFront caches content at its 400+ edge locations. After you upload new files to S3, users will continue to see the cached old version until the cache expires — or until you invalidate it.

Complete deploy sequence
# 1. Build your SPA npm run build → dist/index.html → dist/assets/main.a3f8b2c.js # content-hashed filename → dist/assets/style.9d4e1f2.css # 2. Upload to S3 (sync — only changed files) aws s3 sync dist/ s3://finapp-frontend/ --delete # 3. Invalidate CloudFront cache (only index.html needs it) aws cloudfront create-invalidation \ --distribution-id EDFDVBD6EXAMPLE \ --paths "/index.html" # Assets (JS/CSS) have content-hashed filenames — old cache is harmless # because the new index.html points to the new hash. Only index.html needs # invalidation. Invalidating /* costs more and is rarely needed.
Content hashing = safe long-term caching Modern build tools (Vite, webpack) rename JS and CSS files with a hash of their content: main.a3f8b2c.js. If the file changes, the hash changes, so the filename changes — CloudFront cannot serve a stale cached version of an asset because the new index.html references a filename that was never cached. Set a 1-year cache on /assets/* and a short cache (5 min) on /index.html.

Security Headers via CloudFront Response Headers Policy

For a financial app, you should add security headers on every CloudFront response. AWS provides a managed policy you can attach — no Lambda needed:

HeaderValueProtects against
Strict-Transport-Security max-age=31536000; includeSubDomains Protocol downgrade / MITM (forces HTTPS for 1 year)
X-Content-Type-Options nosniff MIME type sniffing attacks
X-Frame-Options DENY Clickjacking (embedding your app in an iframe)
Content-Security-Policy Custom per app XSS — restricts which scripts, styles, and origins are trusted
Referrer-Policy strict-origin-when-cross-origin Leaking URL parameters (e.g. trade IDs) in Referer headers

Attach the AWS-managed SecurityHeadersPolicy to your CloudFront distribution's default cache behavior. For Content-Security-Policy, create a custom response headers policy with your specific allowed origins.

Azure → AWS Frontend Map

ConceptAzureAWSKey difference
Static file storage Azure Blob Storage (static website) S3 bucket Both store static files. On AWS, keep the bucket private and serve via CloudFront — do not use S3's static website endpoint.
CDN / global delivery Azure CDN / Azure Front Door CloudFront CloudFront has 400+ edge locations. Integrates natively with S3 via OAC. Front Door is more similar to CloudFront in features.
TLS certificates App Service Certificate / Azure-managed ACM (AWS Certificate Manager) ACM certs are free and auto-renew. Must be provisioned in us-east-1 for CloudFront — regardless of where your app runs.
SPA hosting (managed) Azure Static Web Apps No direct equivalent You compose S3 + CloudFront manually. AWS Amplify Hosting wraps this with more automation if you want a closer Azure Static Web Apps experience.
DNS Azure DNS Route 53 Route 53 Alias records work at the apex domain (no CNAME limitation). Azure DNS uses ALIAS records similarly.
Private CDN-to-storage access Private Endpoint on Blob Storage Origin Access Control (OAC) OAC signs CloudFront requests to S3 so the bucket can stay fully private. The modern replacement for the older OAI (Origin Access Identity).
WAF Azure WAF on Front Door AWS WAF on CloudFront Both filter OWASP Top 10 at the edge. AWS WAF uses managed rule groups you subscribe to; Azure WAF uses built-in rulesets.
Cache invalidation CDN purge CloudFront Invalidation First 1,000 invalidation paths/month are free. Azure CDN purge is also free. Both propagate globally in ~1–2 minutes.

Production Checklist

  • S3 bucket: Block Public Access all enabled — no public bucket policy
  • OAC created and bucket policy restricts access to this specific CloudFront distribution only
  • ACM certificate requested in us-east-1 (even if app is in another region)
  • CloudFront: Viewer Protocol Policy = Redirect HTTP to HTTPS
  • CloudFront: TLS Security Policy = TLSv1.2_2021 (no TLS 1.0 or 1.1)
  • Custom Error Response: 403 + 404 → /index.html with 200 status (SPA deep links)
  • Security headers response policy attached (HSTS, X-Frame-Options, CSP)
  • Cache settings: /assets/* = 1 year, /index.html = 5 minutes
  • Deploy pipeline invalidates only /index.html (not /*)
  • Route 53 Alias record points to CloudFront (not a CNAME)

Lesson takeaway Frontend stack: S3 (private bucket, OAC policy) → CloudFront (TLS via ACM cert in us-east-1, path routing for /api/* to ALB, custom error response for SPA deep links, security headers) → Route 53 Alias (apex-domain capable). Deploy = aws s3 sync + invalidate /index.html. The S3 bucket is never public — CloudFront is the only door in.
