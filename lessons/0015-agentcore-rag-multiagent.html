AgentCore, RAG Internals, and Multi-Agent Systems

Three questions, one shape: what AgentCore is, how Knowledge Bases actually perform retrieval, and how to wire multiple agents together

Lesson 14 established the base call: your backend invokes a foundation model through Bedrock. This lesson goes one level deeper into three things you asked about directly — AgentCore (the platform for building real agents), the mechanics inside a Knowledge Base (RAG), and how to compose multiple agents into one system.

Naming note before we start AWS's original "Amazon Bedrock Agents" (the console feature with action groups and a built-in orchestrator) is now called Bedrock Agents Classic and is closed to new customers — existing users keep it, but AWS's own docs point new builds at AgentCore instead. Everything below reflects the current path.

What AgentCore Is

AgentCore is not one service — it's a set of independent, composable services for running agents in production. The key design choice: it's framework- and model-agnostic. You write your agent with Strands Agents SDK, LangGraph, CrewAI, or plain code, using Claude, GPT, Gemini, or any model — AgentCore supplies the infrastructure around it: secure execution, tool access, memory, and observability.

ComponentWhat it does
RuntimeServerless, session-isolated execution for your agent code — each conversation runs in its own microVM, with fast cold starts and support for long-running async agents.
GatewayWraps your existing Lambda functions and APIs as MCP (Model Context Protocol) tools, so any agent can call them without custom integration code.
IdentityAuthenticates agents and the users behind them, using your existing IdP (Cognito, Okta, Entra ID) — no separate identity system to build.
MemoryShort-term memory for one conversation, long-term memory that persists across sessions, optionally shared across multiple agents.
ObservabilityOpenTelemetry traces of every step an agent takes — which tool it called, what it retrieved, what it answered — viewable in CloudWatch.
Code Interpreter / BrowserSandboxed tools an agent can call to run code or navigate a website, without you hosting either.

In short: Bedrock (Lesson 14) gets you a model call. AgentCore gets you a production agent — one that keeps state across turns, calls your internal tools safely, and is traceable when something goes wrong.

How Knowledge Bases (RAG) Actually Work

Lesson 14 introduced Knowledge Bases as "grounds answers in your S3 documents." Here's the mechanism underneath that.

Ingestion — happens once, and on every update

1

Parse & chunk. Bedrock pulls documents from your S3 data source and splits them into smaller text chunks — small enough that each chunk is a coherent, retrievable unit.

2

Embed. Each chunk is passed through an embedding model, which turns the text into a vector — a list of numbers positioned so that semantically similar text ends up at nearby points in vector space.

3

Index. The vectors are written to a vector store — OpenSearch Serverless, S3 Vectors, Pinecone, or Redis. Bedrock keeps this index in sync automatically as your S3 documents change; you don't run a re-index job yourself.

Query — happens on every user question

Retrieval + generation
User question → embed the question with the same embedding model → similarity search in the vector store (nearest chunks) → top-k chunks + original question → foundation model → answer grounded in the retrieved chunks

Bedrock exposes this as two API shapes:

APIReturnsUse it when
RetrieveThe raw matching chunks, no model callYou want to build a custom prompt yourself, or feed chunks into an agent's own reasoning loop
RetrieveAndGenerateA finished answer, with source citationsYou want the simple case — one call, grounded answer back
Finance context Citations matter here as much as the answer. RetrieveAndGenerate returns which source chunks (and which S3 document) backed each part of the answer — the audit trail you need if a client or examiner asks "where did that number come from?"

Building a Multi-Agent System

There are two eras of Bedrock multi-agent design, and it matters which one you build on.

Bedrock Agents Classic (multi-agent collaboration)AgentCore-based (current)
StatusMaintenance mode — closed to new customersActively developed, recommended path
PatternOne supervisor agent, several collaborator agents, configured in the consoleYou write the orchestration in code (Strands, LangGraph), deploy each agent to AgentCore Runtime
FlexibilityFixed hierarchical shapeMultiple patterns — pick per use case (below)

The concept Bedrock Agents Classic pioneered is still the right mental model even on the new stack: give each agent a narrow, clearly-scoped job, and have something route between them. A Bedrock example is an online mortgage assistant — a supervisor that reads the question and hands it to an "existing mortgage" agent, a "new application" agent, or a "general Q&A" agent, each with only the tools and knowledge base it needs.

On AgentCore, the Strands Agents SDK gives you three orchestration shapes to choose from:

PatternShapePick it for
GraphEach node is a full agent (own prompt, own tools); edges define dependencies between themA fixed pipeline of specialists — e.g. "retrieve statement" → "analyze" → "draft response"
WorkflowA task pipeline, not full agents — lighter weight than GraphSteps that don't each need independent reasoning, just sequencing
SwarmPeer agents hand off to each other dynamically, no fixed supervisorOpen-ended problems where the right next specialist isn't known in advance
Example: finance-app multi-agent (supervisor pattern on AgentCore)

Orange = orchestration & policy layer (Runtime, Guardrails). Purple / green / blue = the three scoped collaborator agents, each with its own tool or Knowledge Base — no agent can reach another's resources directly.

Each specialist agent is scoped the same way you scoped IAM roles in Lesson 3 — its own Gateway tools, its own Knowledge Base, nothing broader. That containment is what keeps a multi-agent system auditable instead of a black box.

Production Checklist

  • Building anything new — start on AgentCore, not Bedrock Agents Classic (closed to new customers)
  • Each agent scoped to the minimum tools (via Gateway) and Knowledge Base it actually needs
  • Use RetrieveAndGenerate when you need citations back to the source document, not just an answer
  • Pick Graph for fixed pipelines, Swarm for open-ended routing — don't default to the most complex pattern
  • Observability (OTEL traces) turned on before production — multi-agent failures are hard to debug blind
  • Guardrails applied per-agent, not just once at the very end

Knowledge Check

Four questions on AgentCore, RAG internals, and multi-agent design.

1. You're starting a new agent project on Bedrock today. Which should you build on?

2. Put the Knowledge Base ingestion steps in order: (i) index in a vector store (ii) embed each chunk (iii) chunk the documents.

3. You need an answer plus the exact source document each part of it came from, for audit purposes. Which Bedrock API should you call?

4. You're building a system where the right next specialist agent genuinely can't be predicted in advance — agents need to hand off to each other dynamically. Which Strands orchestration pattern fits best?

Lesson takeaway AgentCore is the current, framework-agnostic platform for running production agents on AWS — Bedrock Agents Classic is legacy for new work. A Knowledge Base is chunk → embed → index at ingestion, and embed-query → similarity search → generate at query time, with RetrieveAndGenerate giving you citations for free. Multi-agent systems on AgentCore mean scoping each agent narrowly (its own tools, its own Knowledge Base) and picking Graph, Workflow, or Swarm to match how predictable your routing actually is.
