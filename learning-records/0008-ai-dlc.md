# AI-DLC Is a Methodology, Not a Service — AI Authors, Humans Decide

User asked for a lesson on the "AWS AI DLC framework" — what it is, how to use it, pros/cons. First non-service lesson in the series (methodology/process). Fits the user's adjacent work (they maintain teach-AI-SDLC, teach-10x, teach-2x repos).

**Evidence:** Direct three-part request. Researched current sources before writing (Jan 2026 cutoff, framework published 2025): AWS "AI-Driven Development Lifecycle for Financial Services" blog, "Building with AI-DLC using Amazon Q Developer" blog, and the awslabs/aidlc-workflows reference implementation + its docs site. Note a version discrepancy captured in the lesson: AWS's conceptual model is 3 phases (Inception, Construction, Operation); the reference implementation has since grown to 5 phases (adds Initialization, Ideation) with 11+ domain-expert agents.

**Implications:** Delivered as Lesson 19 (bonus track, tag "Methodology"). Key teaching points: Agile's bottleneck is human cognitive throughput; AI-DLC's vocabulary shift (sprint→bolt hours-to-days, epic→unit of work, solo authoring→mob elaboration/construction, 7-dev Scrum team→2-3-dev AI Pod, Definition of Done→steering files + tests); three phases with artifacts; how-to (add aidlc-workflows rules to repo, drive bolts from coding agent via /aidlc, clear approval gates, aidlc-docs/ + aidlc-state.md + audit.md land in repo); finance angle (steering files encode EU AI Act / dependency allowlists, intent→story→code→test traceability, pair velocity KPIs with assurance KPIs, risk-based change categorization so approval gates don't become the bottleneck). Pros/cons table included per request — headline con is AWS's own caveat: "amplifies existing capabilities, does not compensate for foundational gaps." Still process-level — user has not started building the app. Natural next steps: running a first bolt, writing steering files, or comparing to Kiro spec-driven / GitHub Spec Kit.
